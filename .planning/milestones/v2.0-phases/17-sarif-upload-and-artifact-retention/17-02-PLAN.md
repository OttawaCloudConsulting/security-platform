<objective>
Replace the `sca` job's `trivy convert` step with a second direct `trivy fs … --format sarif` run, and
carry the change into the local smoke gate together with a regression assertion that prevents it being
quietly reverted.

Purpose: RESEARCH Pitfall 3 measured, twice and with the byte-exact CI invocation, that
`trivy convert` writes `originalUriBaseIds.ROOTPATH = file:///…/trivy-fs.json/` — the INPUT FILE, not the
scan root — while `trivy fs --format sarif` writes the scan root correctly. On the runner that makes every
`trivy-fs.sarif` result resolve to `<workspace>/trivy-fs.json/fixtures/package-lock.json`, a path that does
not exist, and `checkout_path` relativization does not rescue it. `trivy-fs` is one of only three
annotation-capable sources this stack has (Criterion 2), so the broken base is not cosmetic. This change
lands BEFORE any upload step exists, so the first upload the repo ever performs is of a correctly-based
SARIF.

Output: a two-invocation SCA Trivy block in CI, a matching smoke-gate block with a ROOTPATH assertion, and
a local full-gate run proving Phase 15/16 scanners still find what they found.
</objective>

<notes>
**TARGET REPOSITORY.** `repos/security-platform/`, on the phase branch created in 17-01. All git operations
use `git -C repos/security-platform`.

**Do NOT touch the `container` job's `Convert to SARIF` step (security.yml:369-371).** Two reasons, both
load-bearing: (a) its 56 results point at `library/scan-fixture` 1:1 under any form, so there is no location
fidelity to preserve; (b) user decision D-01 satisfies Criterion 4 by pointing at `trivy convert` as the
phase's already-implemented documented conversion step — removing it everywhere would delete the thing
D-01 names. ADR-016 (17-06) will record that the surviving `trivy convert` lives in the `container` job.

**Do NOT chain the two Trivy runs in one `run:` block.** The first run exits 1 when it finds something,
and GitHub's default shell is `bash -e`. The workflow's own comment at security.yml:400-404 records this
trap; Phase 15 hit it with Gitleaks.

**Do NOT drop `--severity HIGH,CRITICAL` from either run**, and do not "simplify" the SARIF run to
`--exit-code 0`. Flag parity between the two invocations is the property that keeps the retained JSON and
the uploaded SARIF describing the same findings.

**The smoke gate is slow.** Run it once, at the end of Task 2, and read its summary — do not loop it.
If any Phase 15/16 sub-check that passed before this change now FAILS, STOP and REPORT rather than
adjusting the gate to make it green.
</notes>
