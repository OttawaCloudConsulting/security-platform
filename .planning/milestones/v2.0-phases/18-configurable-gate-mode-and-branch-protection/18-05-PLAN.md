<objective>
Flip the gate with one CLI command, prove the same pull request now fails all five checks, prove the
reporting guarantees survive, and put the repository back exactly as it was. Then put the one genuinely
irreversible question — whether this repository's `main` gets required checks — in front of the operator
instead of deciding it.

Purpose: this is Success Criteria 1, 2 and 3 in a single measurement. Criterion 3 ("switching requires no
change to workflow YAML") is only provable by changing nothing and observing a different outcome, which is
why the flip is done by re-running the SAME commit rather than pushing a new one: identical source, two
conclusions. And P-04 warns explicitly not to infer that uploads survive blocking mode from the report-only
run — a hard-failing scan step changes which steps GitHub runs, so the artifacts and SARIF have to be
counted again under blocking.

Output: a measured blocking run, a restored report-only repository, and a recorded operator decision on
required checks.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repository variable → every run in the repository | `GATE_MODE` is repo-wide and takes effect immediately on every branch, not just this PR |
| Local `gh` token (repo admin) → rulesets API | One PUT can make `main` unmergeable by anyone, with no self-service exit |
| Blocking scan failure → later steps | A hard failure changes which steps GitHub runs; reporting guarantees must be re-counted, not inherited |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-17 | Denial of Service | The repository left in blocking after an interrupted plan | mitigate | `gh variable delete` is unconditional and runs first on any error path; `gh variable list` showing no `GATE_MODE` is an acceptance criterion; a final restore run must conclude green |
| T-18-05 | Denial of Service | Self-lockout of `main` (P-06) | mitigate | No autonomous `--apply`; the decision is an explicit operator checkpoint with the recommended answer being no; bypass actor required in the UI first if they opt in |
| T-18-13 | Repudiation | Claiming "no YAML edit" without evidence | mitigate | The blocking run is triggered by an EMPTY commit: identical tree hash and an empty `git diff` between the two commits, both recorded |
| T-18-28 | Denial of Service | A re-run 409ing on duplicate v4 artifact names and turning jobs red for a non-gate reason | mitigate | `gh run rerun` is deliberately NOT used; each measured run gets a fresh run id via an empty commit, so the artifact namespace is fresh |
| T-18-18 | Repudiation | Inferring that uploads survive blocking from the report-only run (P-04) | mitigate | Artifact count, category set and the eleven assertions are re-measured on the blocking attempt |
| T-18-19 | Tampering | A collateral run (e.g. Dependabot) silently executing under blocking during the window | accept | Nothing is a required check and nothing auto-merges on this repo, so the effect is a red check on an unrelated PR; the window is kept short and reported with its start and end |

| T-18-SC | Tampering | npm/pip/cargo installs | accept | No package installed; `gh` and `git` only |
