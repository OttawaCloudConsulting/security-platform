<objective>
Open a REPLACEMENT validation pull request, flip `GATE_MODE` to `blocking`, prove that pull request now fails
all five checks on a byte-identical tree, delete the variable unconditionally, prove it passes again, and put
the paired evidence in front of a human.

Purpose: this is Success Criterion 2 — "that same pull request is observed failing its checks under blocking
mode and passing under report-only, both runs witnessed, not inferred". The only way to prove that the GATE
and nothing else changed the outcome is to change nothing else: the same commit content, an identical tree
hash, an empty `git diff`, and opposite verdicts. This plan also executes D-09: the repository is returned to
report-only before the phase closes, because Phase 18 D-07's rollout sequencing puts required-checks adoption
after blocking adoption, and that step is explicitly deferred past this phase.

**Why this plan was replanned, and what it means for SC2.** This plan was originally written to re-run PR #10
— the long-lived D-05 validation PR that 19-03 opened and 19-04 traced. On 2026-09-13T22:34:18Z, after 19-04
closed SC1 and SC3 and before SC2 or SC4 were measured, the operator merged PR #10 through the GitHub web UI
(merge commit `80e91de`) and its head branch `feature/phase-19-pipeline-validation` was auto-deleted. That
merge happened outside the planned flow — plan 07 was to be the only point in this phase where that decision
was taken. PR #10 and its branch therefore no longer exist to re-run, and SC2's literal wording ("that SAME
pull request") is no longer satisfiable. Its essential claim is, and that is what this plan proves: one pull
request, two gate modes, opposite verdicts, byte-identical trees, nothing edited between them. The
substitution is recorded as a deviation in this plan's SUMMARY, not papered over, and plan 07 consolidates it.

**Why the replacement PR's diff is a documentation correction and not a newly seeded finding.** PR #10's
merge put `fixtures/vulnerable.py` and `fixtures/secret.env` on `main`, so every branch cut from `main` now
checks out all five seeded fixture categories and every scanner — each of which scans the whole checkout, not
the diff — still reports them. The replacement PR needs a non-empty diff to exist as a PR; it does not need
to seed a finding, because the findings that turn the five checks red under blocking are already in the tree.
Seeding a new one would mean editing counts that `fixtures/README.md` on `main` states as measured facts
("`vulnerable.py` reports THREE findings, not five, and that is the correct number"), to manufacture a
condition that already exists. Instead the diff actions deferred item **D-19-A**: `fixtures/README.md`'s
bypass paragraph documents `git push --no-verify` as the only obstacle and omits the server-side GitHub Push
Protection layer that actually blocked 19-03's push. That is a real, measured, in-scope correction which
changes no measured count and gives plan 07's merge-or-close decision something worth landing.

Output: three runs on one identical tree, two opposite verdicts, a bounded and enumerated blast-radius
window, a repository with no `GATE_MODE` variable, and an operator confirmation.

Sequencing note: waves are strictly sequential. The replacement PR is opened under report-only FIRST so its
own green baseline is on the record before the flip — the same before/after shape D-05 step 1→2 called for,
carried onto a new PR. 19-03's and 19-04's evidence describes PR #10 and must not be re-derived from here.
</objective>

<notes>
**DELETE THE VARIABLE UNCONDITIONALLY.** `gh variable delete GATE_MODE` runs whether the measurement
succeeded, failed, or was interrupted. A repository left in blocking is the worst possible outcome of a
half-finished plan — worse than no measurement at all. If anything goes wrong mid-task, delete the variable
FIRST, then report.

**Why the D-09 revert is NOT gated behind a checkpoint.** Task 1 is a blocking human checkpoint that
AUTHORISES opening the window before it opens, and Task 3 is a blocking human checkpoint that VERIFIES the
repository was restored — but the `gh variable delete` itself sits inside Task 2 with no gate in front of it,
because a human gate between `set` and `delete` means an unanswered prompt leaves a live repository gating
every pull request. Task 3 is the D-09 checkpoint; it confirms the restore rather than permitting it. No task
boundary and no plan boundary may ever separate the `set` from the `delete`.

**Five red checks are the SUCCESS condition of Task 2**, not a failure. What would be a failure: fewer than
five red, a job that died before its scan step, a missing artifact, or a missing SARIF category.

**The baseline this plan pairs against is its OWN run 1, not 19-03's run `34786019516`.** Those are different
pull requests on different bases; pairing across them would smuggle in a second changed variable. Use 19-03
only for the expected SHAPE — the five frozen check-run names, the five artifact names, the eleven intolerant
upload-verify assertions. The per-job finding counts are EXPECTED to match 19-03's, because the scanned
fixture files are byte-identical on `main`; if a count differs, explain the difference rather than failing on
it, and never treat a match as required evidence.

**Do not merge and do not touch the ruleset.** Plan 07 owns the replacement PR's fate; required-checks
adoption is Phase 18 D-07 step 3 and is explicitly deferred past this phase (D-09).

**Do not edit any workflow file, and do not touch any fixture other than `fixtures/README.md`.** Editing a
workflow would destroy the entire argument — the point is that nothing but a variable changed between run 2
and run 3. Editing a fixture's content would change the finding set the whole phase is measured against.

**Do not delete, rename or push the stale local `feature/phase-19-pipeline-validation` branch.** Its commits
are already on `main` via PR #10's merge; leaving it is harmless and touching it is not this plan's business.

**`$SCRATCH` must be set inline in every command that uses it.** Shell state does NOT persist between
tool calls in this harness, so a `$SCRATCH` exported in one call is empty in the next. Prefix every
command and every verify invocation that references it with `SCRATCH=<absolute session scratchpad path>;`
in the SAME command. Use the scratchpad path from your own environment prompt — never `/tmp`, never a path
copied from this plan, and never anywhere inside either repository.
