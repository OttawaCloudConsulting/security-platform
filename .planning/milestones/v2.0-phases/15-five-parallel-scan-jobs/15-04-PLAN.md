<notes>
**TARGET REPOSITORY — and the one push that must never happen.**
The push target is the product repo checked out at `repos/security-platform/`. VERIFIED in Phase 14:
the OUTER documentation repo's `origin` points at the SAME URL, but their histories are DISJOINT —
different root commits, no merge base. `git push` from the outer repo would attempt to dump unrelated
history onto `security-platform`. Every git command here is scoped `git -C repos/security-platform`.
The Bash working directory resets between calls, so always use `-C`; never rely on a prior `cd`.

**Resolve the slug at runtime:**
`SLUG=$(git -C repos/security-platform remote get-url origin | sed -E 's#^.*github\.com[:/]##; s#\.git$##')`
Note `gh repo view` takes the slug POSITIONALLY (`gh repo view "$SLUG"`) while `gh pr` / `gh run` /
`gh api` use `-R "$SLUG"` or an explicit path.

**Select the run by identity, never by recency.** Phase 14 hit this: the branch carries a `Copilot` run
with event `dynamic` alongside the real one. Filter `gh run list --branch <branch> --json
databaseId,workflowName,event,headSha,status,conclusion` on `workflowName == "PR Security"` AND
`event == "pull_request"`. Same discipline for the PR: match by head branch, not "the newest PR".

**Use an explicit `--title` and `--body` on `gh pr create`, never `--fill`.** With multiple commits on
the branch, `--fill` derives the title from the branch name rather than a commit subject (Phase 14
learning).

**Five green checks is the expectation, and a red one is a STOP.** Under D-04 each scan step is expected
to be annotated as failed while its JOB concludes `success`. If any of the five check-runs concludes
`failure`, the `continue-on-error` landed on the job instead of the step, or a follow-up step is missing
`if: always()`, or a `run:` block chained two natively-failing commands. STOP → REPORT the raw log →
WAIT. Do not re-run the workflow hoping for a different result and do not patch the workflow from this
plan; a fix belongs in a revision of Plan 03.

**The GitGuardian check is expected and is not one of the five.** RESEARCH §Runtime State Inventory
confirms a `GitGuardian Security Checks` app posts its own check on PRs in this repo. Filter the
check-run list on the `security / ` prefix; assert the filtered count is exactly 5, not that the total
is 5.

**Merging is NOT this plan's job.** Plan 05 owns the human checkpoint and the merge. Leave the PR open.

**Anticipated first-run failure modes, with their diagnoses — report, do not improvise a fix.**
- SAST job dies at install: PEP 668 externally-managed-environment (Assumption A7). Fallback ladder is
  in 15-03-SUMMARY: `pipx install semgrep==1.177.0`, then `python -m pip --break-system-packages`.
- IaC job's `ls -l` step fails: Checkov 3.3.17 wrote different filenames than the action's
  comma-mapped `output_file_path` produced locally (Assumption A6). 15-02-SUMMARY has the measured
  answer; report the mismatch.
- Container job reports zero: check the Trivy log for `no longer supported by the distribution`, which
  would mean the wrong base image is in `fixtures/Dockerfile` (RESEARCH C-1).
- Secrets job reports zero: the checkout lost `fetch-depth: 0`, or the command used `dir` instead of
  `git` (RESEARCH C-5, Pitfall 4).
</notes>
