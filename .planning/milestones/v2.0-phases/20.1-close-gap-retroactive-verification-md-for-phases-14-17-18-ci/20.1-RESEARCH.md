## Summary

This phase writes three forensic verification documents. It writes **no code and changes no live
configuration**. Every claim in Phases 14, 17, and 18 is re-provable today because the evidence they
depend on — workflow YAML on `origin/main`, code-scanning analyses on PR merge refs, workflow run
artifacts, the branch ruleset, and Dependabot's PR history — is all still live and was successfully
re-queried during this research session. The single largest risk to this phase is **not** that a claim
turns out false; it is that a naive re-query returns an empty or 404 result that *looks* like a failure
but is correct-by-design (or that a shell-quoting slip makes a satisfied requirement look
unwired). This document enumerates seven such traps.

The most important is **PITFALL-1**: the pipeline is `on: pull_request` only, so
`code-scanning/analyses?ref=refs/heads/main` returns `[]`. A plan that verifies CICD-02 "against
`origin/main`" in the literal sense will conclude SARIF upload is broken. It is not — SARIF lives on
`refs/pull/N/merge` refs, and all six categories are present on the most recent PR (#13). The phase goal's
phrase "against live `origin/main`" must be read as *"against the state of the system as it exists today,
whose workflow definition is what is on `origin/main`"* — not as a literal ref filter.

Verification splits across two repositories. **Live GitHub state and workflow/script source belong to
`OttawaCloudConsulting/security-platform`.** Planning records, requirement tracking, ADRs, the blueprint,
and the adoption guide belong to this repo (`security_solution`). A local clone sits at
`repos/security-platform` and was proven byte-identical to live `origin/main` for all five load-bearing
files — but that identity is a *finding to re-prove*, not an assumption to inherit. Prescribe a Task 0
that re-runs the diff; only then may later tasks grep the working tree instead of paying an API round trip.

**Primary recommendation:** One PLAN.md with a Task 0 that pins a single immutable evidence snapshot
(PR #13 / head `c06d2729b123094bcbb48e03c1155b72c7727b8c` / run `34870572604`) and proves the local
clone matches live `origin/main`, followed by three per-phase authoring tasks that all cite that one
snapshot. Treat every command in §Verified Command Reference as copy-pasteable — each was executed
successfully during this research session and its real output is recorded here.

## Common Pitfalls

### PITFALL-1 (CRITICAL): `code-scanning/analyses?ref=refs/heads/main` returns `[]`

**What goes wrong:** A plan reads the phase goal's "against live `origin/main`" literally, queries
analyses filtered to `refs/heads/main`, gets an empty array, and reports CICD-02 as FAILED.

**Why it happens:** `pr-security.yml` declares `on: pull_request: {}` and nothing else. There is no
`push` trigger. The pipeline has therefore never run on a branch ref — only on PR merge refs. Live
confirmation: the unfiltered analyses list contains exactly `refs/pull/{8,9,10,11,12,13}/merge` and no
`refs/heads/*` entry whatsoever.

**How to avoid:** Query `?ref=refs/pull/13/merge` (the snapshot), or omit `?ref` entirely and group by
`.ref`. State in each document that main-ref emptiness is a designed consequence of the PR-only trigger
policy (D-02 of Phase 17), not a defect.

**Warning sign:** any empty JSON array from a code-scanning endpoint. Always re-query without the filter
before concluding absence.

### PITFALL-2: 6 SARIF categories ≠ 5 artifacts ≠ 5 check-runs

**What goes wrong:** A plan asserts "five scan jobs, therefore five of everything," then flags the
mismatch as drift.

**Why it happens:** Three different counting rules are in play:
- **6 SARIF categories** — `tflint` uploads its own category from inside the SCA job.
- **5 artifacts** — `semgrep-results`, `checkov-results`, `sca-results`, `trivy-image-results`,
  `gitleaks-results`. `sca-results` is a bundle containing tflint's and trivy-fs's outputs together.
- **5 `security / …` check-runs** — one per job; the caller job emits none of its own.
- **7 analyses on PR #13** because tflint's single SARIF carries **two drivers**, producing two analyses
  under one category (results_count 0 and 3) with a shared `sarif_id`.

**How to avoid:** Write the 6/5/5/7 asymmetry into each document as an explicit, expected structure.

### PITFALL-3: 12 check-runs on the head SHA, but only 5 are this pipeline's

**What goes wrong:** Phase 17's records refer to "twelve byte-exact check-run names." A plan greps for 12
`security / …` names, finds 5, and reports 7 missing.

**Why it happens:** The head SHA carries 12 check-runs from *three different apps*. Live on `c06d272`:
`Checkov`, `GitGuardian Security Checks`, `Semgrep OSS`, `Trivy`, `gitleaks`, `tflint`, `tflint-errors`
(third-party apps + `github-advanced-security` per-driver checks), plus the five `security / …` job
checks from the GitHub Actions app.

**How to avoid:** Always filter `select(.app.id == 15368)` when the question is "what does *our workflow*
report." Never build a required-check list from `code-scanning/analyses` — STATE.md:122 records that the
two endpoints **disagree on case** (`checkov`/`Gitleaks` in analyses vs `Checkov`/`gitleaks` in
check-runs).

**Good news, already verified:** all 12 names on `c06d272` match STATE.md:122's recorded set exactly —
**zero drift** since Phase 17. Report this as a positive finding.

### PITFALL-4: `branches/main/protection` returns 404 — by design

**What goes wrong:** A plan reads the classic branch-protection endpoint, gets
`{"message":"Branch not protected","status":"404"}`, and reports CICD-04 as unmet.

**Why it happens:** This repo uses **rulesets**, not classic protection. `set-required-checks.sh`'s header
states it outright: *"NEVER read the CLASSIC protection endpoint as evidence of anything — it 404s on this
repo BY DESIGN... The authoritative read-back path is always `rules/branches/main`."* STATE.md 14-02
already records this 404 as a known false negative.

**How to avoid:** Use `gh api repos/$R/rules/branches/main` and `gh api repos/$R/rulesets`. If you cite
the 404 at all, cite it as a confirmed-expected result.

### PITFALL-5: `gh variable list` returns empty — that is the documented default

**What goes wrong:** Empty output is read as "gate mode is not configured."

**Why it happens:** Phase 18 D-03 makes `report-only` the fallback precisely so that an unset variable is
the correct steady state. Phase 19 D-09 confirmed the variable was deliberately left unset at phase close.
Empty output means the `||` chain terminates at the `'report-only'` literal — exactly as designed.

**How to avoid:** Pair 06-a with 06-b in the same evidence cell so the empty result is self-explaining.
**Do not** set the variable to "test" it.

### PITFALL-6: `actions/checkout` SHA no longer matches Phase 14's recorded pin

**What goes wrong:** `14-VALIDATION.md` task 14-01-02 asserts
`actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0  # v7.0.0`. Live `origin/main` carries
`@3d3c42e5aac5ba805825da76410c181273ba90b1  # v7.0.1`. Re-running Phase 14's literal static gate FAILS.

**Why it happens:** Dependabot PR #5 bumped it on 2026-09-10 and it was merged. **This drift is the
proof that CICD-05 works.** The requirement is "Dependabot configured to keep GitHub Actions SHA pins
updated" — a pin that never moved would be the weaker result.

**How to avoid:** In `14-VERIFICATION.md`, verify the *invariant* (`@<40-hex>  # v<semver>` on every
`uses:`), not the *literal SHA*. Explicitly narrate the v7.0.0 → v7.0.1 transition as expected, sourced,
and desirable. This is the single most likely place for a careless plan to record a false FAIL.

### PITFALL-7 (CRITICAL): `grep -c` on a `${{ }}` pattern silently returns 0

**What goes wrong:** Counting the gate-mode conditionals with
`grep -c "continue-on-error: \${{ env.GATE_MODE == 'report-only' }}"` returns **0**, and CICD-06 is
reported FAILED — "gate mode is not wired to any step."

**Why it happens:** The pattern contains `{`, `}`, `$` and `'`. Even with `\$` escaped, the braces are
interpreted as regex interval syntax rather than literal characters, so the pattern never matches. The
correct count is **11**. Observed live this session: `grep -c …` → `0`; `grep -cF …` → `11`.

**How to avoid:** Always use `grep -F` (fixed string) when the pattern contains GitHub Actions
`${{ }}` expression syntax. Cross-check with a metacharacter-free pattern — `grep -c "# D-04"` returns
12 (11 conditionals + one unrelated `soft_fail: false  # D-04` comment at line 255), which independently
corroborates 11.

**Warning sign:** a `grep -c` returning exactly `0` for a pattern you can see with your own eyes in a
`grep -n` of the same file. This is the highest-severity trap in the whole phase because it produces a
*confident false negative* on a requirement that is in fact fully satisfied — and unlike PITFALLs 1-6,
nothing about the output hints that the tool, not the system, is at fault.

### Anti-Patterns to Avoid

- **Any mutating command.** No `gh variable set`, no `gh variable delete`, no
  `set-required-checks.sh --apply`, no `gh pr create`, no `gh pr merge`, no pushes to `security-platform`.
  CONTEXT's phase boundary says this phase "does NOT change scanning behavior, gate-mode wiring, or
  SARIF/branch-protection config." "Live re-query" means **read**, never **re-run**.
- **Opening a new PR to generate fresh evidence.** Unnecessary — PR #13 and runs back to Phase 14 are all
  still queryable with live artifacts. A new PR would also mutate repo state and invalidate the pinned
  snapshot.
- **Greping the local clone without first proving it matches live.** Valid only after the Task 0 diff.
- **Citing this repo's blueprint as evidence of pipeline behavior.** See §Repo Attribution Map.
- **Copying SUMMARY.md prose into the Evidence column.** D-01 forbids exactly this. Each Evidence cell
  must contain a command and its observed output.
- **Reporting a bare count as confirmation.** STATE.md:122's lesson: the per-category hypothesis predicted
  six new checks and six appeared — but for the wrong reason. Always verify *which* members produce a
  count, not just the count.
