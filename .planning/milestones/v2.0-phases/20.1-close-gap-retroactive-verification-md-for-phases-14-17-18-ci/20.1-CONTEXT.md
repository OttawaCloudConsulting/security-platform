# Phase 20.1: Close gap: Retroactive VERIFICATION.md for Phases 14, 17, 18 - Context

**Gathered:** 2026-09-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Phases 14 (Workflow Foundation and Action Pinning), 17 (SARIF Upload and Artifact Retention), and 18
(Configurable Gate Mode and Branch Protection) all completed with PLAN.md/SUMMARY.md/VALIDATION.md but
never got a VERIFICATION.md — unlike Phases 15, 16, 19, and 20 which all have one. This phase closes that
documentation gap by producing a VERIFICATION.md for each of the three phases, independently re-confirming
via live re-query (matching Phase 19's rigor) that requirements CICD-02 through CICD-06 are still true
against the current state of `origin/main` and GitHub. This phase does NOT change scanning behavior,
gate-mode wiring, or SARIF/branch-protection config — it verifies and documents what those three phases
already shipped, fixing only trivial drift found along the way.

</domain>

<decisions>
## Implementation Decisions

### Verification method
- **D-01:** Verify via live re-query, not by trusting existing SUMMARY.md/VALIDATION.md narrative alone.
  Independently re-check claims against live repo state (`gh api`, `gh run view`, `gh variable list`,
  branch-ruleset/required-checks reads, live `contents` API reads of `origin/main`) — same rigor as
  `19-VERIFICATION.md`. This catches drift since these phases closed (e.g., `gate_mode`/`GATE_MODE` value
  changes, renamed check-runs, Dependabot config edits) rather than just re-asserting old claims.

### Output structure
- **D-02:** One VERIFICATION.md per phase, written into each phase's own existing directory —
  `.planning/phases/14-workflow-foundation-and-action-pinning/14-VERIFICATION.md`,
  `.planning/phases/17-sarif-upload-and-artifact-retention/17-VERIFICATION.md`,
  `.planning/phases/18-configurable-gate-mode-and-branch-protection/18-VERIFICATION.md` — not one
  consolidated doc under `20.1-.../`. Matches the existing convention already followed by Phases 15, 16,
  19, and 20.

### Gap handling
- **D-03:** If live re-query finds a real defect (not just the missing-doc gap itself) — e.g. `gate_mode`
  has drifted from its documented default, a check-run was renamed, Dependabot config no longer matches
  what CICD-05 requires — fix it inline in this phase IF the fix is trivial (a config value, a doc
  correction, a stale reference). Anything non-trivial gets recorded in that phase's VERIFICATION.md Gaps
  Summary and in `deferred-items.md`, not silently dropped, and not fixed as part of this phase's scope.

### Success criteria for 20.1
- **D-04:** This phase is DONE when: (1) all three VERIFICATION.md files exist with a pass/fail status
  following the `19-VERIFICATION.md` format (Observable Truths table, live evidence, spot-checks,
  Requirements Coverage, Gaps Summary); (2) CICD-02, CICD-03, CICD-04, CICD-05, and CICD-06 are each
  independently re-confirmed true against live state — not merely re-stated from old SUMMARY/VALIDATION
  text; (3) any drift found is either fixed inline (D-03, if trivial) or explicitly logged as a gap.
  ROADMAP.md's placeholder goal and success criteria for Phase 20.1 have been rewritten to reflect this.

### Claude's Discretion
- Exact `gh`/`gh api` commands used per phase to re-query CICD-02 (SARIF upload — code-scanning/analyses),
  CICD-03 (JSON artifact retention — workflow run artifacts), CICD-04 (branch protection — rules/branches
  or ruleset API), CICD-05 (Dependabot SHA-pin updates — `.github/dependabot.yml` + recent Dependabot PR
  history), and CICD-06 (gate mode — `vars.GATE_MODE`/`continue-on-error` conditionals in `security.yml`)
  — follow the same query shapes `19-VERIFICATION.md` used for equivalent live checks.
- Whether all three VERIFICATION.md files are produced in one planning pass (one PLAN.md covering all
  three phases) or as three separate per-phase plans — pick whichever fits GSD's phase-plan conventions;
  either satisfies D-02's per-phase file requirement.

</decisions>
