<objective>
Build the `update` subcommand: a per-tool two-attempt loop that never trusts an installer's exit
code, continues past failures, falls back to the latest release within the pinned major, logs what it
could not fix, re-prints the version table, and sets the exit status accordingly.

Purpose: this is MAINT-02, the largest net-new capability in the phase. Everything it composes from
already exists after plans 02 and 03 — `attempt_install`, `resolve_latest_in_major`,
`log_update_failure`, `is_installed`, `add_result`/`print_summary`, `run_check`, and the six
`_install_*` functions. The risk here is not writing too little; it is writing a parallel
implementation of `run_installer` or `run_check` that drifts from the original.

Output: `update_one_tool()`, `update_all_tools()`, the dispatcher branch with selective per-tool
targeting, updated `usage()` and file-header comment, and offline tests for the whole state machine.
</objective>

### Truths (Decision Traceability)

<planner_decisions>
Resolutions of the open questions this plan depends on:

- **Open Q1 — a successful attempt-2 fallback is reported as a distinct `fallback` status.** It does
  **not** increment `FAIL_COUNT`, and `versions.conf` is **not** rewritten. `versions.conf` stays an
  intentional, user-owned artifact — its own header says "Edit versions here, then re-run", and
  silently mutating a pinned manifest would undercut the entire point of pinning. Instead the
  automatic post-update recheck is followed by an explicit note per fallback, so the `MISMATCH` the
  user sees in the table is self-explanatory and actionable.
- **Downgrade guard (T-13-04).** A resolved fallback is only installed when it sorts greater than or
  equal to the pin. A fallback that would move the tool backwards is rejected with a warning and the
  tool is treated as failed. This is a security control, not a nicety.
- **Open Q3 — selective per-tool update: YES.** `bash setup.sh update trivy`. After a partial
  failure, retrying one tool costs one API call instead of six against a 60/hr budget.
- **D-03** (continue updating the remaining tools on failure; collect per-tool results and report a
  summary, reusing `add_result`/`print_summary`) — implemented by the `|| true` on the
  `update_one_tool` call inside `update_all_tools`, by `update_one_tool` returning 1 rather than
  exiting, and by reusing the existing summary machinery rather than a parallel implementation.
- **D-04** (two-attempt sequence: exact pin, then latest release matching the pinned major, then give
  up and log) — implemented verbatim by `update_one_tool`'s steps 2-6, including the guard that a
  fallback identical to the pin is not retried.
- **D-06** (after `update` completes, automatically re-run the same version-check logic, reusing
  `run_check` rather than duplicating table printing) — the `update)` dispatcher branch calls
  `run_check` directly. The fallback notes print after it so the `MISMATCH` rows it shows are
  explained rather than alarming.
- **D-07** (plain-text failure log at `$REPO_ROOT`) — `update_one_tool` calls `log_update_failure`
  (built in plan 03) on the give-up path only.
- **D-08 exit contract.** `update` exits non-zero if and only if at least one tool failed both
  attempts. `FAIL_COUNT` drives it through the existing single exit gate. The post-update `run_check`
  must not influence it — that is what `PROBLEM_COUNT` (added in plan 03) is for.
- **D-05 retry: not implemented** (decided in plan 03; the two-attempt sequence is the retry).
</planner_decisions>

       repo name by indirect expansion from `$repo_var_name` (`${!name}` — verified working in bash
       3.2; only indirect *assignment* needs `eval`). Derive the major with `major="${pinned%%.*}"`.

       This is the only API call in the whole update run, and only on the failure path.

       - Empty `fallback`: `warn` that no `<major>.x` release could be resolved for the repo, plus the
         actionable rate-limit hint naming `GITHUB_TOKEN`/`GH_TOKEN` and the 60→5000 difference.

       - `fallback` equals `pinned`: `log` that the fallback resolved to the same version and is not
         being retried. Fall through to failure. A second identical attempt is guaranteed to fail the
         same way.

         below its pin and is being refused. Fall through to failure. Do not use a lexical comparison
