### Locked Decisions

#### Replacement tag
- **D-01:** Replace `scan-target:${{ github.sha }}` with the **fixed literal `scan-target:ci`** in both places in the container job of `security.yml`: `docker build ... -t` (~L988) and `trivy image` (~L994). Also update the comment at ~L947 that lists `${{ github.sha }}` as an interpolated value. This is a minimal diff and was the deferred-items proposal. A fixed tag is safe from collisions because the container job runs on `ubuntu-latest` (L915; unlike the DefectDojo jobs it is not routed via `vars.DEFECTDOJO_RUNS_ON`), so every run gets a fresh Docker daemon. A repo-qualified name and `docker save` + `trivy image --input` were both rejected.
- **D-02:** **Leave `${{ steps.docker.outputs.path }}` interpolation as is.** It is out of the dedup scope.
- **D-03:** If research finds that the image reference also lands in another hashed or stored field (for example `description` or `title`) besides `file_path`, **the fixed tag still fixes it**, because every field that echoes the image name gets the constant tag. The kind proof (D-06) decides. **Stop and ask the operator only if a SHA-bearing field survives the change.**
- **D-04:** Add a **static gate check**: the container job's build and scan lines must reference `scan-target:ci`, and must not use `github.sha` as the image tag. Add it to an existing workflow gate script (for example `scripts/check-workflow-uploads.sh`; the planner picks), with a **negative case** that proves the check fails on the old form. Measured: `github.sha` appears in `security.yml` only at L947 (comment), L988 and L994, so after the change any non-comment occurrence in that job is a regression.

## Summary

The dedup gap is real and the fix is sound, but the CONTEXT's root-cause attribution needs one correction: in DefectDojo 3.3.200 the `Trivy Scan` hash fields are `["title", "severity", "vulnerability_ids", "cwe", "description"]` (+ `service` always) — **`file_path` is not hashed**. The SHA reaches the hash through `description`, which the parser builds from `DESCRIPTION_TEMPLATE` containing `**Target:** {target}`, where `target = Results[].Target = "scan-target:<sha> (debian 12.15)"`. `file_path` carries the same string (stored, not hashed) because os-pkgs vulns have no `PkgPath`. Both fields get the constant under `scan-target:ci`, so D-01 fixes it; D-03's stop condition does **not** trigger (see "D-03 verdict").

In a real `trivy-image.json` (Trivy v0.74.0, two artifacts downloaded from runs at `30afdb9` and `72a6083`) the target string appears in exactly four places: `ArtifactName`, `Metadata.Reference`, `Metadata.RepoTags[]`, `Results[].Target`. `RepoDigests` is `null` (local build, never pushed) and `ImageID` was identical across both SHAs. The SARIF the job uploads is **byte-identical between the two SHAs except `runs[0].properties.imageName/repoTags`**: `artifactLocation.uri` is `library/scan-target` (tag stripped), the message has no tag, and there are no `partialFingerprints`. Code-scanning alerts are therefore unaffected by the tag (D-14 item 2 already measurable offline; re-run at release for the record).

Three CONTEXT assumptions are factually off and the planner must adjust: (1) there is **no "main push run"** — `pr-security.yml` triggers on `pull_request` only, and `ci/main` is reimported by `scheduled-security.yml` (cron 06:00 America/Toronto + `workflow_dispatch`), so D-07 steps 2 and 5 need an operator-approved `workflow_dispatch` (and the daily cron may get there first); (2) adoption-guide "~L396" is a line inside the frozen check-run code block, the upgrade line belongs in §12 "Deduplication and Triage" (L834-855); (3) Dependabot PRs #30/#31 are open and edit `uses:` pins in `security.yml` — merging either before the tag breaks the D-14 item 3 "only run: bodies changed" check.

**Primary recommendation:** Ship PR A = {security.yml L988/L994 → `scan-target:ci` + L947 comment; `IMAGE-TAG` check (CHECK_COUNT 20→21) in `check-workflow-uploads.sh`; `P-IMAGE-TAG` in the import proof with a generic ArtifactName rewrite; D-09 trivy-image assertion in `lifecycle-assert.sh` keyed on the finding `title` (= `"<VulnID> <PkgName> <InstalledVersion>"`, titlecased) with a `hash_code` diagnostic}, then run the live sequence with `workflow_dispatch` for the `ci/main` reimports and explicit ordering preconditions (PR A engagement deleted before the dispatch; throwaway PR and PR B opened only after the `ci/main` reimport lands).

### Pattern 1: IMAGE-TAG static check (D-04)
**What:** New check in `check-workflow-uploads.sh`, modeled on CURLRC (29.2) / SCHEME: locate `jobs.container`, the steps named `Build image from discovered Dockerfile` and `Run Trivy image scan` (they have no `id:`; match by `name`, fail if not exactly one each), assert the build `run` contains `-t scan-target:ci` and the scan `run` contains `trivy image scan-target:ci`, and that **no** `run:` in `jobs.container` contains `github.sha`. PyYAML drops comments, so the L947 comment can never trip it. Bump `CHECK_COUNT = 20` → `21`, add the name to the trailing comment list and a header-table line ("Phase 29.4 IMAGE-TAG").
**Negative case:** the 29.2/27-11 idiom — RED first on the unfixed tree (run the new gate against `origin/main`'s security.yml: must FAIL with IMAGE-TAG for both lines), then scratch copies with `WORKFLOWS_DIR=<scratch>`: (a) revert the build line only, (b) revert the scan line only, (c) `scan-target:${{ github.sha }}` in a new extra container step → each FAILs IMAGE-TAG; the real tree PASSes 21. Record in evidence. Note: no CI workflow runs `check-workflow-uploads.sh` today (`git grep` finds no caller), so "standing" here means a recorded RED + scratch negatives, as in 29.2-05.

### Pattern 2: P-IMAGE-TAG kind proof (D-06)
**What:** `prove_image_tag` called right after `prove_reparent` (L2982, inside `prove_dedup_triage`, so dedup is on and `async_wait` is set). Two **fresh products** (e.g. `proof/image-tag-sha`, `proof/image-tag-ci`) so the negative control cannot contaminate the positive one (dedup is product-wide).
- Build 4 report dirs each holding only `trivy-image.json` (P-REPARENT already imports a single-file dir; the committed body SKIPs the rest).
- Rewrite generically: read `src["ArtifactName"]` (in PR A this is already `scan-target:ci`; on older trees it is `scan-target:<sha>`), and replace that exact string in every JSON string value. Assert after rewrite: old string count 0, new string count == original count (4 in the measured artifact), and `Results[].Target`, `ArtifactName`, `Metadata.Reference`, `Metadata.RepoTags` all carry the new value.
- Negative: `scan-target:<PROOF_SHA>` → ci/main, `scan-target:<other 40-hex>` → `ci/proof/pr-image-sha`; assert every PR trivy-image finding is `duplicate=false, active=true` and count == ci/main count (> 0).
- Positive: `scan-target:ci` on both; assert every PR trivy-image finding is `duplicate=true, active=false`, `duplicate_finding` in ci/main ids, `file_path` starts with `scan-target:ci`; non-vacuous (count > 0, == ci/main count).
- Add a static assertion on the CI-produced artifact itself: `jq -r .ArtifactName dd-reports/trivy-image.json == "scan-target:ci"` (proves D-01 actually landed in scan output on PR A's run).
- `FIELDS` (L1691) lacks `file_path`; add it (additive; the slim() missing-key check will then require it, which the API provides).

**Why this case is needed:** the existing P-DEDUP-BRANCH imports the *same* `trivy-image.json` on both engagements (L2537-2548), so the kind proof was structurally blind to this defect (ADR-027 L278-288 records the same).

### Pattern 3: D-09 trivy-image assertion (lifecycle-assert)
**Key (Claude's discretion, recommended):** the finding `title`. The 3.3.200 parser sets `title = f"{vuln_id} {package_name} {package_version}"` (parser.py L357) and DefectDojo `titlecase()`s it on save (finding/models.py L25, L575) — e.g. stored `CVE-2026-53613 Bsdutils 1:2.38.1-5+deb12u3`. Both sides go through the same transform, so API-to-API comparison is exact. Any comparison to raw `trivy-image.json` triples must casefold.
**Locating the Tests:** PR side — reuse the existing live Test lookup (scan_type `Trivy Scan`, title `trivy-image`, exactly one). ci/main side — the SLIM snapshot has only `test_ids`; add an **additive** `tests: [{id,title,scan_type}]` to `cmd_snapshot` (the import-proof snapshot already records tests) and, for old snapshots that lack it, read `GET /api/v2/tests/?engagement=<snapshot engagement_id>` live (filter-guard as `engagement_findings` does).
**Verdict as a pure jq program** fed by files (PR findings, PR image test id, main findings, main image test id), so the same code runs live and offline:
- counterparts = ci/main image-Test findings with `is_mitigated != true and duplicate != true`, grouped by title;
- matched = PR image findings whose title has a counterpart; drift = the rest (recorded, not failed);
- bad = matched findings with `duplicate != true`, or `duplicate_finding` not in that title's counterpart ids, or `file_path` not starting with `scan-target:ci`;
  - scope note: the `file_path` clause holds because the measured image has one Result (`Class: os-pkgs`, no `PkgPath`, 60/60 findings). A `lang-pkgs` vuln carries `PkgPath` in `file_path` (parser L340-345), not the image ref. Apply the clause to os-pkgs findings only, or assert the `**Target:** scan-target:ci` line in `description` instead (that needs `description` read from the API; it is the hashed carrier anyway);
- FAIL if matched == 0 (vacuous) or bad > 0.
- Diagnostic (recommended): for each bad pair fetch both `hash_code` values (`hash_code` is in the 3.3.200 FindingSerializer — Meta excludes only `cve`, `inherited_tags`; finding/api/serializer.py L427-432). Equal hash but not duplicate → real dedup failure; different hash → Trivy DB content drift (severity/description/FixedVersion changed). See Open Question 1 for whether the latter fails.
**Snapshot fields:** if D-11 is to be re-checked offline later, add `hash_code` (and optionally `description`) to SLIM as additive keys; the API provides both.
**Check IDs:** replace `D11-STEP2-EXCLUSION-KEY` with e.g. `D11-STEP2-TRIVY-IMAGE-KEY` (exactly one image Test on each side) and `D11-STEP2-TRIVY-IMAGE-DEDUP` (the D-08 verdict); `D11-STEP2-DUPLICATES-POINT-TO-MAIN` keeps its logic for non-fixture, non-image findings (its vacuity message must stop mentioning "excluded").

### Anti-Patterns to Avoid
- **Regex-replacing `scan-target:[0-9a-f]{40}`** in the kind rewrite: breaks in PR A where the CI file is already `scan-target:ci`. Replace the exact `ArtifactName` value.
- **Matching counterparts across the whole ci/main engagement by title**: trivy-fs findings share the `Trivy Scan` parser and title shape; restrict to the `trivy-image` Test on both sides.
- **Counting mitigated old SHA-path findings as counterparts**: after the first upgrade reimport the ci/main image Test holds both sets.
- **Asserting `file_path` equality as the dedup proof**: `file_path` is not hashed; assert `duplicate`/`duplicate_finding` (and diagnose with `hash_code`).

## Common Pitfalls

### Pitfall 1: There is no "main push run" (D-07 steps 2 and 5)
**What goes wrong:** waiting for a push-triggered `ci/main` reimport that never comes.
**Why:** `pr-security.yml` `on: pull_request: types: [opened, synchronize, reopened, closed]` only; `ci/main` reimports come from `scheduled-security.yml` (`schedule` cron `0 6 * * *` America/Toronto + `workflow_dispatch`). Verified at origin/main; recent run list shows Scheduled Security on main and no push-triggered PR Security.
**How to avoid:** after each merge, an operator-approved `gh workflow run scheduled-security.yml --ref main`, then read the run's head SHA and the DefectDojo Import job result. The 06:00 cron can do the first post-upgrade import on its own: take the D-14.1 "before" snapshot **before merging PR A**, and record which run (cron or dispatch) performed the first import.
**Warning signs:** `gh run list --workflow scheduled-security.yml` head SHA ≠ the merge SHA.

### Pitfall 2: PR A's own engagement becomes the "original" of ci/main's new set
**What goes wrong:** PR A's PR runs import `scan-target:ci` findings into `ci/<PR A branch>` while ci/main is still SHA-path, so those PR findings are originals with low ids. If ci/main is reimported while that engagement still exists, ci/main's new findings become **inactive duplicates** of PR A's (dedup picks the oldest non-duplicate; deduplication.py L600-660, candidates exclude only `duplicate=True`).
**How to avoid:** precondition for the dispatch: PR A's `DefectDojo Cleanup` job (on `closed`) succeeded with outcome deleted (`Engagement.delete()` re-parents synchronously — ADR-026 decision 2 — so even a late delete heals, but the D-14.1 measurement would then be confusing). Likewise open the throwaway PR and PR B **only after** the ci/main reimport has landed, or their findings become originals instead of duplicates.
**Warning signs:** after dispatch, ci/main image findings with `duplicate=true`.

### Pitfall 3: Trivy DB content drift breaks the hash, not just add/drop
**What goes wrong:** `description` embeds Trivy's `Title`, `Description` text and `FixedVersion`; `severity` is hashed too. A DB update that edits any of these changes `hash_code` → the PR copy is not a duplicate (D-08 FAIL) and the ci/main reimport closes and re-creates (WR-04 not closed for that vuln).
**Measured:** 8 h apart (`30afdb9` 10:03Z vs `72a6083` 18:00Z, 2026-10-01): 60 vulns each side, 0 added, 0 dropped, **0 changes** in (Title, Description, Severity, CweIDs, FixedVersion, Status); only `References` and per-vuln `Fingerprint` differed (neither hashed). `[VERIFIED: local diff]`
**How to avoid:** run the throwaway PR immediately after the ci/main import (D-08 already says so); classify bad pairs with `hash_code`; scope the WR-04 claim in ADR-031/TRIAGE as "ids persist across main SHAs when the vulnerability's Trivy DB content is unchanged".

### Pitfall 4: Dependabot PRs #30/#31 edit security.yml
**What goes wrong:** both open PRs (codeql-action upload-sarif 4.38.2, checkov-action 12.3126.0) change only `.github/workflows/security.yml` `uses:` pins. Merged before the tag, the D-14.3 structural check (non-run structure identical to v1.2.0) fails and the release carries unreviewed surface.
**How to avoid:** hold both until after `v1.3.0`, or the plan explicitly enumerates them in the allowed diff (operator decision). Also: their PR runs are Dependabot (DD import refuses — `dd-gate` L1310) so they do not pollute DefectDojo.

### Pitfall 5: public.ecr.aws 429 on the base-image pull
**What goes wrong:** 29-18 saw `security / Container — Trivy Image` fail in `docker build` with `429 Too Many Requests` (public.ecr.aws debian:12-slim). Then no `trivy-image.json` → DD import SKIPs the image Test → D-08 finds zero overlap (correctly FAILs) and D-11/D-14.1 have no data.
**How to avoid:** treat as an infrastructure failure: STOP, report, operator decides on rerun (anti-slop rule). Check the container job conclusion before running any assertion.

### Pitfall 6: Adoption-guide "~L396" is inside the frozen check-run code block
**What goes wrong:** L396 `## security / Container — Trivy Image` is a comment line inside a ```` ```bash ```` block listing the five contexts that `check-adoption-guide.sh` asserts. Editing there breaks the gate or the copyable block.
**How to avoid:** put the D-15 line in §12 → "### Deduplication and Triage" (L834-855), next to "A PR shows only what it introduces" (L842-845, which is currently false for trivy-image and becomes true from v1.3.0). §12 spans L599-870 and is the `DEFECTDOJO-SECTION` gate scope (16 required strings, currently PASS 16/16).

### Pitfall 7: ADR-031 timing vs D-07 step 4 (CONTEXT correction — needs operator acknowledgment)
**What goes wrong:** D-07 step 4 lists ADR-031 in "PR B", but ADR-031 and the adoption guide live in **this** repo (not security-platform), and ADR-031 must record step-5 (WR-04) and step-6 (tag) evidence that does not exist at PR B time.
**How to avoid:** security-platform PR B = TRIAGE.md L14 + README L242. In this repo: adoption-guide line at PR B timing (after the live proof), ADR-031 + README index row **after the tag**. This deviates from locked D-07 step 4 as written; it is not planner discretion and the operator should acknowledge it.

### Pitfall 8: D-10 wording "replaces them once"
Since main has moved SHA at least four times since `2fda1ac` with daily cron imports, the old behaviour was "replaced on every new main SHA" (WR-04). After v1.3.0 it is once. Phrase the TRIAGE/README text so it is true for both histories.

### Pitfall 10: `assert-pr-duplicates` needs a non-Trivy fixture finding on the throwaway PR
**What goes wrong:** `--fixture-path` is a REQUIRED flag (lifecycle-assert L244), and `D11-STEP2-UNTRIAGED-EQ-FIXTURE` passes only when the PR engagement's Under Review set is non-empty and equals the findings under the fixture path (`($ur_ids | length) > 0 and $ur_ids == $fx_ids`). Trivy findings arrive `verified=true` and never match the Under Review filter. A throwaway PR that "touches no Dockerfile" and adds nothing else therefore FAILs step 2 regardless of trivy-image dedup.
**How to avoid (recommended):** the throwaway PR carries one non-Trivy fixture file, as 29-16 did (`phase29-d11-fixture/unsafe_pickle.py`, one Semgrep finding), and is run with `--fixture-path phase29-d11-fixture/`. This keeps the D11-STEP2 contract intact. (Alternative: a D-09 mode that skips the fixture check for an image-only measurement — more code, weaker contract.)

### Pitfall 9: 29.5 touches TRIAGE.md L44
Independent hunks (L14 vs L44), but if 29.5's PR is open at the same time, rebase/merge order must be explicit; the D-10 text must not mention the Under Review query.
