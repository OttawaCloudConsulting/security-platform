# Phase 29.4 Plan 03: P-IMAGE-TAG kind proof Summary

`defectdojo-import-proof.sh` now has P-IMAGE-TAG. It takes the CI trivy-image.json and writes two pairs of copies that differ only in the image target. With SHA tags, every PR trivy-image finding must stay an active non-duplicate (negative control, reproduces 29-16). With `scan-target:ci` on both, every PR trivy-image finding must be an inactive duplicate of a ci/main trivy-image finding (positive case). The rewrite program was proven offline on the real artifact: 4 occurrences in, 0 old and 4 new out.

## What was done

- **Identities:** `PROOF_IMAGE_SHA_PRODUCT`, `PROOF_IMAGE_CI_PRODUCT`, `PROOF_IMAGE_SHA_PR`, `PROOF_IMAGE_CI_PR` and `PROOF_IMAGE_OTHER_SHA` are readonly. They and `PROOF_SHA` are exported in prove_dedup_triage.
- **image_tag_rewrite SRC TARGET OUTDIR LOG:** a quoted 'PY' heredoc between the marker lines. It replaces the exact `ArtifactName` string, prints `old= new= original_count= old_after= new_after=` and the four locations, and exits as follows:
  - 3 when ArtifactName is missing or the old target occurs 0 times
  - 4 when an old occurrence survives, a new occurrence is missing, or a location lacks the target
  - the four-location check also runs when old == target
- **prove_image_tag:**
  1. A missing `trivy-image.json` gives `proof_fail` and `return 0`. There is no `proof_skip "P-IMAGE-TAG"`.
  2. Static D-01: `jq -r .ArtifactName` must equal `scan-target:ci`. It runs to the end either way.
  3. It builds four single-file report dirs. A failed rewrite gives `proof_fail` and `return 0`.
  4. It runs the negative case, then the positive case.
- **image_tag_case:**
  - ci/main is imported first, then settle, then the PR, then settle, then both snapshots.
  - A failed import or snapshot gives `proof_fail` and skips only that case.
- **image_tag_assert MODE:**
  - It keeps the one Test titled `trivy-image` with scan_type `Trivy Scan`, and fails when there is not exactly one.
  - Both modes require equal counts greater than 0.
  - Negative: every PR finding has `duplicate` false and `active` true.
  - Positive: every PR finding has `duplicate` true, `active` false, `duplicate_finding` among the ci/main image ids, and a `scan-target:` file_path that starts with `scan-target:ci`.
  - Up to 10 offenders are listed, plus one sample file_path pair.
  - It uses the say() pattern, the catch-all except, `tally_assert_log`, and the guard for an exit without a FAIL line.
- **FIELDS:** `"file_path"` was added.
- **Header:** both the prose list and the assertion-group list were updated.
- **Call site:** `prove_image_tag` runs right after `prove_reparent`.

## Known risk for plan 04

The Trivy Scan hash fields are title, severity, vulnerability_ids, cwe and description. In the artifact, all 60 (VulnerabilityID, PkgName, InstalledVersion, Target) tuples are distinct, but there are only 22 distinct titles. An intra-report hash collision cannot be ruled out offline. If one occurs, the negative case would show PR findings that are duplicates of other PR findings, and that would not be a tag effect. The offender list (dup_of ids) tells the two apart.
