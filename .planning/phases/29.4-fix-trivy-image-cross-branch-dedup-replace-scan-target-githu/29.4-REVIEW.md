## Summary

Scope: the Phase 29.4 diff hunks in `security-platform` (`30afdb9..aa48081`, released as v1.3.0) and the docs repository commits `e324b30` (adoption guide) and `fd68d67` (ADR-031 and the index row). Because v1.3.0 has already shipped, the caller treats these findings as advisory follow-up. The severity labels still follow the rubric.

The workflow change itself is correct and small. The build and scan both use `scan-target:ci`, `github.sha` is gone from the file, and JOB-SHAPE keeps the container job on `ubuntu-latest`, so the fresh-daemon dependency stated in ADR-031 is enforced. The defects are in the verification tooling added around it:

- The D-08/D-21 jq verdict in `defectdojo-lifecycle-assert.sh` gives a false FAIL in two reachable situations. I reproduced both by running the extracted `TRIVY_IMAGE_VERDICT` program on synthetic snapshots.

The docs (TRIAGE.md, README.md, adoption guide, ADR-031, ADR index) match the measured evidence they cite. I found no correctness defects in them.

## Critical Issues

### CR-01: TRIVY_IMAGE_VERDICT reports `hash_code_differs` whenever a title has more than one ci/main counterpart

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:605-618`
**Issue:** Counterparts are grouped by title only (line 605: `.[$c.title // ""] += [$c]`). The hash check (line 618) fails a PR finding if **any** counterpart's hash differs: `$hc and ($mh | any(. != $f.hash_code))`. The Trivy Scan title is `<vuln_id> <pkg> <version>`. The same title can appear in several `Results[]` Targets, for example one Go module vendored into two binaries, or one jar in two paths. ADR-031 says the description line `**Target:** <target>` is hashed, so those findings legitimately have different `hash_code` values. A correctly deduplicated PR finding matches exactly one of them, so every finding in such a group is reported as `hash_code_differs` and the verdict is FAIL.

Reproduced: I gave the extracted program two ci/main findings with the same title (hashes `HA` and `HB`) and two PR duplicates pointing at them with matching hashes. It returned `{"verdict":"FAIL","bad":[{"id":11,"reasons":["hash_code_differs"]},{"id":12,"reasons":["hash_code_differs"]}]}`.

The same grouping also makes the `duplicate_finding_not_counterpart` check (line 615) too loose. It accepts a PR finding that points at the wrong same-title counterpart.

This was not caught for two reasons. The live D-08 run had 60 unique titles in a single os-pkgs Result. The kind proof (`image_tag_assert`) checks `duplicate_finding in main_ids` and never compares hashes. ADR-031 "What was NOT verified" item 4 already admits that lang-pkgs and multi-Result images were never imported, and that is exactly the case that triggers this bug.

**Fix:** Pass when at least one counterpart has an equal hash, and require `duplicate_finding` to be one of those equal-hash counterparts. Alternatively, key the counterparts on `(title, file_path)`, since `file_path` equals the Target for os-pkgs and is `PkgPath` for lang-pkgs.
```jq
| ($cs | map(select(.hash_code == $f.hash_code)) | map(.id)) as $eq_ids
| [ (if $f.duplicate != true then "not_duplicate" else empty end),
    (if (($f.duplicate_finding // -1) | IN($cids[])) then empty else "duplicate_finding_not_counterpart" end),
    (if $hc and ($eq_ids | length) == 0 then "hash_code_differs" else empty end),
    (if $hc and ($eq_ids | length) > 0 and ((($f.duplicate_finding // -1) | IN($eq_ids[])) | not)
     then "duplicate_finding_not_equal_hash_counterpart" else empty end),
    ...file_path clause unchanged... ]
```
Add an offline replay case with two same-title counterparts that have different hashes. It should PASS when each PR copy points at its equal-hash twin, and FAIL when it points at the other one.

## Warnings

### WR-01: The verdict filters mitigated findings out of ci/main but not out of the PR side

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:603-604`
**Issue:** `$mc` (line 604) drops ci/main findings that are `is_mitigated` or `duplicate`, and the header explains why: "an upgrade reimport leaves mitigated old sets". `$pi` (line 603) keeps every PR finding in the trivy-image Test. `branch.json` comes from `engagement_findings` (line 680, unfiltered `/api/v2/findings/?test__engagement=`), so it contains mitigated findings. Two cases leave mitigated non-duplicate findings in the PR's image Test:
- A PR engagement that existed before the v1.3.0 upgrade. The PR's next reimport closes its SHA-tagged set.
- Any PR pushed more than once across a Trivy DB change.

These findings often still have the same title as a ci/main counterpart, so they land in `$matched` and fail with `not_duplicate`, `duplicate_finding_not_counterpart` and `hash_code_differs`.

Reproduced: a PR finding `{duplicate:false, is_mitigated:true, title:"CVE-2 libc 1.0"}` with an active ci/main counterpart of the same title returned `{"verdict":"FAIL","bad":[{"id":13,"reasons":["not_duplicate","duplicate_finding_not_counterpart","hash_code_differs"]}]}`.

The D-08 live run used a fresh throwaway PR engagement (#33), so it never reached this path.
**Fix:** Apply the same filter on both sides, and record the excluded rows as measured, not asserted:
```jq
($pr[0].findings | map(select(.test == $prtid and .is_mitigated != true))) as $pi
| ($pr[0].findings | map(select(.test == $prtid and .is_mitigated == true))) as $pi_mitigated
...
mitigated_pr: {count: ($pi_mitigated | length), ids: ($pi_mitigated | map(.id))},
```

### WR-02: The IMAGE-TAG gate accepts a SHA-suffixed tag, and it only reads `run:` bodies

**File:** `repos/security-platform/scripts/check-workflow-uploads.sh:726-754`
**Issue:** The required fragments `-t scan-target:ci` and `trivy image scan-target:ci` are matched as substrings (`run.count(fragment)`, line 743). The `github.sha` ban (line 750) reads only `run:` text and only the literal string `github.sha`. A regression of the form `-t scan-target:ci-${GITHUB_SHA}` / `trivy image scan-target:ci-${GITHUB_SHA}` brings the per-SHA tag back and still passes. Reproduced on a scratch copy via `WORKFLOWS_DIR=<scratch> bash scripts/check-workflow-uploads.sh` → `PASS - 21 checks, 0 failures`. The gate also misses `${{ github.sha }}` set through a step or job `env:` and then used in `run:` as `$TAG`. NO-INTERPOLATION does not cover the container job (see IN-01). ADR-031 decision 2 presents this gate as what "holds the tag", so it overstates what the gate guarantees.
**Fix:** Anchor the tag and widen the ban:
```python
import re
TAG_RE = {
    "Build image from discovered Dockerfile": re.compile(r'(?<!\S)-t\s+["\']?scan-target:ci["\']?(?=\s|$)'),
    "Run Trivy image scan": re.compile(r'\btrivy\s+image\s+["\']?scan-target:ci["\']?(?=\s|$)'),
}
# count len(TAG_RE[name].findall(run)) == 1
SHA_RE = re.compile(r'github\.sha|GITHUB_SHA', re.I)
# scan json.dumps(container_body) (run:, env:, with:, job env:) for SHA_RE, plus any scan-target:<not ci>
```
ADR-031 is Accepted and `docs/adr/` is append-only, so do not edit decision 2. Record any correction in a new record or errata entry.

## Info

### IN-01: The security.yml comment says NO-INTERPOLATION enforces the run-block allowlist across the whole workflow

**File:** `repos/security-platform/.github/workflows/security.yml:946-959`
**Issue:** This phase edited the sentence "The only context interpolations in any run: block in this workflow are ..." and it ends with "check-workflow-uploads.sh NO-INTERPOLATION enforces this." NO-INTERPOLATION (check 14, `check-workflow-uploads.sh:496-505`) only checks the DefectDojo run bodies (header line 36: "no ${{ }} inside a DefectDojo run: body"). Nothing enforces the container-job `run:` interpolations, which is why WR-02's env/run gap exists.
**Fix:** Limit the claim to the DefectDojo jobs, or extend NO-INTERPOLATION to an allowlist across every job.

### IN-02: Two different definitions of "file_path on scan-target:ci"

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:2552` vs `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:616-617`
**Issue:** The kind proof accepts `fp.startswith("scan-target:ci")`, which also matches `scan-target:ci-<sha>` or `scan-target:cifoo`. The live verdict requires `== "scan-target:ci"` or a prefix of `"scan-target:ci "`. The proof is the looser of the two, and it is the one that "proves" D-03.
**Fix:** In the proof, use `fp == CI_TAG or fp.startswith(CI_TAG + " ")`.

### IN-03: The P-IMAGE-TAG positive case never compares hash_code

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:2488-2570`
**Issue:** `image_tag_assert positive` infers "no SHA-bearing hashed field survives (D-03)" from `duplicate is True` and `duplicate_finding in main_ids`. It never reads `hash_code`, which `FIELDS` (line ~1710) does not request. That is good evidence, but it is indirect. The lifecycle verdict has a direct hash comparison and the kind proof does not, so the offline/kind layer cannot catch CR-01-style mistakes in the hash predicate.
**Fix:** Add `hash_code` to the proof's `FIELDS`, and in positive mode assert that every PR finding's `hash_code` equals the hash of its `duplicate_finding` target.
