# Phase 29.4: Fix trivy-image cross-branch dedup (replace scan-target github.sha tag) - Context

**Gathered:** 2026-10-01
**Status:** Ready for planning

<domain>
## Phase Boundary

**Goal (ROADMAP only says `[Urgent work - to be planned]`; this is the goal):** `security.yml` stops tagging the scanned container image `scan-target:${{ github.sha }}`. As a result, identical image content produces identical `Trivy Scan` findings on every branch and every `main` commit. trivy-image findings on a PR engagement then dedupe against `ci/main`, and `ci/main` trivy-image findings, with their dispositions, survive a new `main` SHA. This closes Phase 29 follow-up (b) and 29-REVIEW WR-04. For the `trivy-image` Test it makes DDOJO-03 ("repeated findings across scans/tools collapse") true, a property ADR-026 claimed but the 29-16 live measurement showed absent.

The phase also **cuts the batched v1 release** that 29.2 D-02 handed over (STATE.md "Phase 29.4 must release the Phase 29.2 `security.yml` change"): tag `v1.3.0`, and move `v1`. The tag carries 29.2's `security.yml` TLS hardening (curl `-q` as argv[1], the `ssl_verify_result` check, no curl stderr in `dd-import`/`dd-delete`) and 29.4's tag change. 29.3 is on `main` (`30afdb9`) but adds nothing to the released surface (29.3 D-20).

**Root cause, measured in 29-16:** the Trivy Scan parser puts the image reference in each finding's `file_path` (`scan-target:17fd99dc… (debian 12.15)` on the PR engagement against `scan-target:2fda1ac… (debian 12.15)` on `ci/main`). The `Trivy Scan` dedup algorithm is `hash_code` (`values.yaml` L125). A PR merge SHA never equals the default branch SHA. So all 59 trivy-image findings were active non-duplicates, while the other 96 pre-existing findings deduped.

All code changes are in `OttawaCloudConsulting/security-platform` (local clone `repos/security-platform/`). That clone currently sits on `fix/phase-29.3-chart-gates` (HEAD `36100a1`). 29.4 branches from `main` at or after `30afdb9`. `v1` and `v1.2.0` are still at `fdabac9`.

NOT in this phase:
- Overriding `DD_HASHCODE_FIELDS_PER_SCANNER` for `Trivy Scan`. ADR-026 D-07 forecloses it, and the fix is to replace the tag.
- Moving the Dockerfile `steps.docker.outputs.path` interpolation into `env:` (D-02).
- The TRIAGE.md "Under Review" query that hides `verified=true` Trivy findings (WR-03). That is Phase 29.5. It edits TRIAGE.md L44, while this phase edits L14. Flag the ordering if both are in flight.
- The 29.6 reopen race and 29.7 bookkeeping.

</domain>

<decisions>
## Implementation Decisions

### Replacement tag
- **D-01:** Replace `scan-target:${{ github.sha }}` with the **fixed literal `scan-target:ci`** in both places in the container job of `security.yml`: `docker build ... -t` (~L988) and `trivy image` (~L994). Also update the comment at ~L947 that lists `${{ github.sha }}` as an interpolated value. This is a minimal diff and was the deferred-items proposal. A fixed tag is safe from collisions because the container job runs on `ubuntu-latest` (L915; unlike the DefectDojo jobs it is not routed via `vars.DEFECTDOJO_RUNS_ON`), so every run gets a fresh Docker daemon. A repo-qualified name and `docker save` + `trivy image --input` were both rejected.
- **D-02:** **Leave `${{ steps.docker.outputs.path }}` interpolation as is.** It is out of the dedup scope.
- **D-03:** If research finds that the image reference also lands in another hashed or stored field (for example `description` or `title`) besides `file_path`, **the fixed tag still fixes it**, because every field that echoes the image name gets the constant tag. The kind proof (D-06) decides. **Stop and ask the operator only if a SHA-bearing field survives the change.**
- **D-04:** Add a **static gate check**: the container job's build and scan lines must reference `scan-target:ci`, and must not use `github.sha` as the image tag. Add it to an existing workflow gate script (for example `scripts/check-workflow-uploads.sh`; the planner picks), with a **negative case** that proves the check fails on the old form. Scope the check to the container job. Measured: `github.sha` appears in `security.yml` only at L947 (comment), L988 and L994, so after the change any non-comment occurrence in that job is a regression.

### Proof
- **D-05:** **Kind proof plus a live homelab proof** are both required before the release. The 29-16 gap was measured live, so it is closed live.
- **D-06:** **Kind proof** in `scripts/defectdojo-import-proof.sh`: take one real `trivy-image.json` and write **two copies that differ only in the image target** (`ArtifactName` and every other place the target string appears). Import them into two engagements in the proof's existing main-first order.
  - **Negative control:** with SHA-style tags (two different values), the trivy-image findings are active non-duplicates. This reproduces the 29-16 result.
  - **Positive case:** with `scan-target:ci` on both, every trivy-image finding on the second engagement is a duplicate of a finding on the first.
  - Follow the existing `proof_pass` / `proof_fail` idiom. The label is Claude's discretion (for example `P-IMAGE-TAG`).
  - The live proof run on kind (`defectdojo-import-proof.yml`) must end PROOF PASS on the PR.
- **D-07:** **Release sequence (no tag before live evidence):**
  1. PR A merges to `main` untagged. It carries the `security.yml` change (D-01), the gate (D-04), the kind proof (D-06) and the lifecycle-assert change (D-09).
  2. The `main` push run reimports `ci/main` with `scan-target:ci`.
  3. **Immediately afterwards**, a throwaway PR (it touches no Dockerfile) runs. Measure it with `assert-pr-duplicates` (D-08).
  4. PR B merges. It carries TRIAGE.md, README, the adoption-guide line and ADR-031 (D-10, D-15).
  5. PR B's `main` push run re-imports `ci/main` at a new SHA. This is the WR-04 evidence (D-11).
  6. Tag `v1.3.0` and move `v1`.

  Every push, PR and merge needs operator approval, as in earlier phases.
- **D-08:** **Live assertion:**
  - Every trivy-image finding on the PR engagement that has a `ci/main` counterpart, matched by (vulnerability id, package, installed version), must be a **duplicate pointing at that `ci/main` finding**, and its `file_path` must start with `scan-target:ci`.
  - Trivy DB updates between the two runs can add or drop CVEs. A PR trivy-image finding with no `ci/main` counterpart is **recorded as measured DB drift, not a failure**.
  - **Zero overlap is a FAIL**, so the assertion can never pass vacuously.
  - Run the PR right after the `ci/main` import to keep the drift window small.

### Exclusion and caveat text
- **D-09:** In `scripts/defectdojo-lifecycle-assert.sh`, **remove the trivy-image exclusion** from `assert-pr-duplicates` and **replace it with a dedicated trivy-image assertion** that implements D-08. This replaces `D11-STEP2-EXCLUSION-KEY` and the `excluded_measured` block, ~L740-800.
  - Rewrite the "TRIVY-IMAGE EXCLUSION" header block (~L52-62).
  - Non-trivy-image findings keep their existing `D11-STEP2-DUPLICATES-POINT-TO-MAIN` assertion.
  - Re-run the existing offline replay or negative control against the new logic. The planner decides how, for example by replaying the 29-16 `step2-assert.json` evidence, where the old SHA data must now FAIL the trivy-image check.
  - This assertion is the live proof tool for D-07 step 3.
- **D-10:** Rewrite the **TRIAGE.md L14** caveat ("Dedup is product-wide, except for container-image findings") and its twins in the defectdojo `README.md`.
  - New text: dedup is product-wide. Since `v1.3.0` the image is tagged `scan-target:ci`. Findings imported before that release carry SHA paths, and the first `ci/main` reimport replaces them once.
  - This text goes in **PR B, after the live proof**, so `main` never claims something unproven. This follows the 29-18 PR B pattern.

### WR-04
- **D-11:** **Measure WR-04 live.** Take two `ci/main` imports at different `main` SHAs, both with `scan-target:ci`: the PR A merge and the PR B merge (D-07 steps 2 and 5). Assert that the `ci/main` trivy-image finding ids **persist**: the reimport keeps them, and nothing is closed and re-created except for DB drift, which is measured. WR-04 is closed on this evidence, not by reasoning.

### Release and consumer impact check
- **D-12:** The version is **`v1.3.0`**. Consumers can see the change in scan output (`file_path`, and one-time DefectDojo churn), so it is not a patch. This follows the v1.2.0 precedent. The release moves `v1` to the same SHA (ADR-018, 27 D-16).
- **D-13:** **Decoupled from 29.2.** If the 29.4 kind or live proof fails, hold or revert the 29.4 change, tag the 29.2 content alone as **`v1.2.1`** and move `v1`, then re-plan 29.4. The security fix does not wait on the dedup fix.
- **D-14:** The **v1 consumer impact check** has full scope. Record every item as a measurement with command and output:
  1. **DefectDojo one-time churn.** On the first `ci/main` reimport after the upgrade, `close_old_findings=true` (security.yml ~L1541) should mitigate the old SHA-path trivy-image findings and create the new `scan-target:ci` set. Measure before and after: active and mitigated counts, and whether the old ids are mitigated rather than left active. If they stay active, stop and report. FP and risk-acceptance on the old findings are lost once.
  2. **Code-scanning alerts.** Download two retained `trivy-image-results` / `trivy-image.sarif` from different SHAs. Diff them to see whether the image tag appears in `artifactLocation.uri`, `partialFingerprints` or the message. Record whether alerts churn once and then stabilise, or are unaffected.
  3. **Unchanged surfaces.** Run `git diff v1.2.0..<release-sha> -- .github/workflows/security.yml`. It must touch only `run:` bodies (29.2's DefectDojo bodies and 29.4's L988/L994) and comments. These must be byte-unchanged: `on.workflow_call` inputs and secrets, the five `security / …` job names (required-check lists depend on them), SARIF `category:` values (including `trivy-image`), and artifact `name:` values (including `trivy-image-results`). Reuse existing gates (for example `check-workflow-uploads.sh`) at the release SHA where they already assert these.
  4. **29.2 readback at the tag.** `git show <release-sha>:.github/workflows/security.yml` carries `-q` as curl's first argument and the `ssl_verify_result` check in `dd-import`/`dd-delete`. `git rev-parse v1^{}` and `git rev-parse v1.3.0^{}` both equal the release SHA. This closes the ADR-029 and 29.2 SUMMARY claim that `v1` does not yet carry the fix.
  5. **Actual `v1` consumers.** Enumerate the callers of `security-platform/.github/workflows/security.yml@v1`, for example with `gh search code` and the platform's own callers. The list bounds the blast radius.
  6. **No-Dockerfile consumers are a no-op class.** `found=false` skips the build and scan, so they see no change. State this explicitly.
- **D-15:** **The upgrade note goes in three places:** ADR-031, the `v1.3.0` release notes, and **one line in `docs/adoption-guide.md`** (in this repo) about the one-time trivy-image churn on upgrade. Unlike 29.2 D-07, consumers can see this change. The `bash scripts/check-adoption-guide.sh` gate must pass. The adoption-guide line goes in with PR B's timing, after the live proof.

### Amendments after research (2026-10-01, operator-approved)
- **D-17 (amends D-07 steps 2 and 5):** Pushing to `main` does not reimport `ci/main`. Only `scheduled-security.yml` reimports it, on its cron or on `workflow_dispatch`. Each of D-07 steps 2 and 5 is therefore an **operator-approved `workflow_dispatch` of Scheduled Security**, run right after the merge. The D-14.1 "before" snapshot and the WR-04 baseline are taken **before PR A merges**, because the cron could run the first post-upgrade import on its own. Before the dispatch, confirm that PR A's DefectDojo Cleanup deleted the PR A engagement.
- **D-18 (amends D-07 step 4 and D-16):** **ADR-031 and its `docs/adr/README.md` row are written after `v1.3.0` is tagged**, in this repo, so that the ADR records the WR-04 and tag evidence. PR B still carries the TRIAGE.md L14 and README twin rewrites (D-10). The adoption-guide line (D-15) lands in this repo with PR B's timing.
- **D-19 (amends D-15 location):** The adoption-guide upgrade line goes in **§12 "Deduplication and Triage"** (~L834-855), not at ~L396 (that location is a frozen code block). The L842 claim ("A PR shows only what it introduces") becomes true with this fix.
- **D-20 (amends D-07 step 3):** The throwaway PR **carries one non-Trivy fixture file**, following the 29-16 pattern (for example `unsafe_pickle.py` under a fixture dir). `assert-pr-duplicates` runs with `--fixture-path`. Every existing step-2 assertion stays intact.
- **D-21 (refines D-08):** A trivy-image PR finding that matches its `ci/main` counterpart by title but has a **different `hash_code` is a FAIL**. The diagnostic prints both hashes. Only a finding with no title counterpart counts as DB drift.
- **D-22 (Claude's discretion, release hazard):** Hold open Dependabot PRs that change `security.yml` `uses:` pins (#30, #31 at research time) until after the tag, so that D-14.3 stays clean. The release checkpoint re-enumerates them.

## Existing Code Insights

### Reusable Assets
- `defectdojo-import-proof.sh` already imports `trivy-image.json` as `Trivy Scan` / `trivy-image`, and runs main-first two-engagement dedup cases (P-DEDUP-BRANCH, P-CROSSTOOL, P-REPARENT). The D-06 case slots into this structure with the `proof_pass` / `proof_fail` idiom.
- `assert-pr-duplicates` in `lifecycle-assert.sh` already reads the PR and `ci/main` snapshots, identifies the trivy-image Test live (scan_type `Trivy Scan`, title `trivy-image`), and records `main_trivy_image_file_paths`. The D-09 assertion reuses that Test lookup.
- The `snapshot` subcommand in `lifecycle-assert.sh` can capture the `ci/main` finding ids before and after for D-11 and D-14 item 1.

### Established Patterns
- `security.yml` is the released reusable workflow. Any change to it needs an additive v1.x tag and a `v1` move with an impact check (ADR-018, 27 D-16).
- Docs follow evidence: docs that claim behaviour land in a second PR after the live proof (29-18 PR B).
- Push, PR, merge and tag all need operator approval, followed by an `origin/main` readback (29.2-08, 29.3).
- Static gates come with a standing negative case (29.3 chart gates).

### Integration Points
- The container job is on `ubuntu-latest`. The DefectDojo import job (`vars.DEFECTDOJO_RUNS_ON`, ARC) consumes `trivy-image.json` from the artifact, so the tag change reaches DefectDojo only through the report content.
- `close_old_findings=true` on reimport decides what happens to the old SHA-path findings on the first upgrade import.
