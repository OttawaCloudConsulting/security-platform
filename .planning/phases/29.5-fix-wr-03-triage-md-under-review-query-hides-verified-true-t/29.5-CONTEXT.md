# Phase 29.5: Fix WR-03: TRIAGE.md Under Review query hides verified=true Trivy findings - Context

**Gathered:** 2026-10-04
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase makes TRIAGE.md's Under Review query and state table true for Trivy findings. The fix is at the source. The `dd-import` step in `security.yml` sends `verified=false` explicitly, so that every parser lands findings unverified. "Verified" then means "a triager confirmed this finding is real" for all 8 reports. The phase also covers:

- the proof that the fix works;
- the measurement of what happens to findings that already read `verified=true`;
- the TRIAGE.md line 44 rewrite;
- the assert-script and gate changes that keep the fix in place;
- the `v1.4.0` release, with its `v1` move and upgrade notes.

Out of scope: notifications, SLA, GitHub alert sync, the native `under_review` flag, and any change to the dedup hash fields.

**The problem is measured, not inferred.** The Phase 29 live `ci/main` baseline (`.planning/phases/29-defectdojo-live-validation/evidence/main-baseline-snapshot.json`, 155 findings) showed:

- Test 3 (Trivy fs, `fixtures/package-lock.json`): 6 findings, all `verified=true`.
- Test 4 (Trivy image, `scan-target:<sha>`): 59 findings, all `verified=true`.
- The 6 other Tests (dependabot/checkov, checkov main.tf, gitleaks, npm audit, pip-audit, tflint SARIF): 90 findings, all `verified=false`.

The canonical Under Review query (`TRIAGE.md:85`, `verified=false`) therefore hides 65 of 155 findings (42%). These are exactly the Trivy findings.

</domain>

<decisions>
## Implementation Decisions

### Fix mechanism
- **D-01:** The import sends **`verified=false` explicitly**, so "untriaged" means the same for every parser. Add `"verified=false"` to the `fields` list in the `dd-import` body of `security.yml` (~L1540-1553). The TRIAGE.md Under Review query (L85) and the six-state table stay **as written**. Rejected: dropping `verified` from the query (it loses the "confirmed real" state), and a `triaged` tag (it needs a manual step on every finding).
- **D-02:** **The scope is all scans.** The field goes on every one of the 8 report imports. It is not keyed to a parser or `scan_type`. The other parsers already arrive `verified=false`, so nothing changes for them. **Note:** `dd-import` calls **only** `/api/v2/reimport-scan/` with `auto_create_context=true` (security.yml ~L1350-1354, L1559). A first run and every later run use the same endpoint, so "both endpoints" means this one call.
- **D-03:** **Root cause, found by research.** The researcher reads the DefectDojo 3.3.200 source to find out why Trivy Scan findings land `verified=true` when the request sends no `verified` field. Two candidates: an import or reimport default, or the Trivy parser setting `verified` itself. The researcher also finds out whether an explicit `verified=false` on `reimport-scan` is honoured for new findings, or overridden by the parser. ADR-032 records the cause as "read from source" or as "unknown". It does not record a guess.
- **D-04 (stop condition):** **If the kind proof or the source shows that the Trivy parser overrides `verified=false`**, so that Trivy findings still land `verified=true`, **stop the phase and bring the evidence to the operator.** No fallback is pre-chosen: not a triage tag, and not a query that drops `verified`. This follows the 29.4 D-03 stop-and-ask precedent.

### Existing findings and the Verified guarantee
- **D-05:** **Measure, then decide**, for findings imported before the fix. The 65 live `ci/main` Trivy findings read `verified=true`. Whether a `reimport-scan` with `verified=false` resets them is **unmeasured**.
  - If reimport resets them: no extra step is needed. Record the measurement.
  - If reimport does not reset them: add an **operator-run, one-time reset**. It is a `PATCH {"verified": false}` on active, undispositioned, non-duplicate findings in the **Trivy Scan Tests only** (`trivy-fs` and `trivy-image` titles) on `ci/<default>`. Document it in TRIAGE.md and in the upgrade notes.
  - The reset is safe because, before the fix, Verified on Trivy findings carried no triage meaning (ADR-026 "Trivy originals arrive Verified" tradeoff). The operator approves the live run.
  - The reset follows the runbook's existing token idiom: the token comes from a file, goes into a 0600 header file, and is used with `curl -q`, https only (ADR-025, ADR-029).
- **D-06 (hard requirement):** **A Verified set by a triager survives reimport.** TRIAGE.md L36 ("Verified is preserved") must stay true. The kind proof checks it: `PATCH {"verified": true}` on a finding, reimport with the new body, then read the finding back. It must still be `verified=true`.
- **D-07 (stop condition):** **If `reimport-scan` with `verified=false` clears a Verified that a triager set**, stop the phase and bring the evidence to the operator. The operator **did not** pre-approve a first-run `import-scan` branch in `dd-import`, because it would change the 27 D-07/D-09 reimport-only design. The operator also did not pre-approve rewriting L36. Research expects that 3.3.200 applies `verified` only to findings that reimport creates, but that is **unverified**.

### TRIAGE.md wording
- **D-08:** **Keep the six states and the L85 query as written. Rewrite L44** ("Trivy findings arrive Verified") as a measured statement:
  - from `v1.4.0`, the import sends `verified=false`, and findings from every parser arrive unverified;
  - before `v1.4.0`, Trivy findings arrived `verified=true`, so they were absent from Under Review;
  - what happened to those pre-upgrade findings (the D-05 outcome), and the reset step if one is needed.

  Setting Verified (L36) stays the way to record "confirmed real". Correct L31, L35 and L42 only if the measurements contradict them. The STATE 28-06 rule applies: the runbook must match evidence, not predicted behaviour.
- **D-09:** Say which claims are measured in kind and which are measured live. The live check is a `ci/main` readback only (D-12). New Trivy findings may not appear live in the window, so "new findings arrive `verified=false`" can rest on kind evidence. If it does, label it that way.

### Evidence standard
- **D-10:** **Kind proof** in `scripts/defectdojo-import-proof.sh`. Add a new P-label; the name is Claude's discretion, for example `P-VERIFIED-FALSE`. It asserts that, after the committed `dd-import` body runs, **every finding from all 8 reports reads `verified=false`**.
  - **Negative control:** the old body, without the field, lands the Trivy Scan findings `verified=true`. This reproduces 28-05 and the Phase 29 live split.
  - Use the existing `proof_pass` / `proof_fail` idiom. The live proof workflow `defectdojo-import-proof.yml` must end PROOF PASS on the PR.
- **D-11:** **Measure the reimport-reset question in kind first, then live.**
  - **Kind:** import with the old body (Trivy `verified=true`), then reimport the same reports with the new body. Read `verified` on the **same finding ids**. In the same proof, run the D-06 check: a triager-set `verified=true` survives the new-body reimport.
  - The kind result decides D-05 and the D-07 stop **before PR A merges**.
- **D-12:** **The live check is a `ci/main` readback only.** No throwaway PR engagement: the operator chose this over the 29.4 D-20 pattern.
  - Before PR A merges, snapshot the `ci/main` Trivy finding ids and their `verified` state.
  - After the first post-merge `ci/main` reimport, read them again.
  - Record before and after for the 65 (or current) Trivy ids, and the `verified` state of any new Trivy findings.
  - Following 29.4 D-17, the post-merge reimport is an **operator-approved `workflow_dispatch` of Scheduled Security**. Pushing to `main` does not reimport `ci/main`. Take the "before" snapshot before the merge, because the cron could run the reimport first.
  - If the D-05 reset is needed, run it after the readback and read back again.

### Assert script and gate
- **D-13:** In `scripts/defectdojo-lifecycle-assert.sh`, **keep the L788 query verbatim**, because it still mirrors TRIAGE.md L85. **Rewrite the L852 failure text** ("note: Trivy findings arrive verified=true and never match this filter, so the fixture must come from a non-Trivy parser") so that it matches behaviour from `v1.4.0` on. **Do not add a new live-readback subcommand.**
- **D-14:** **Add a static gate with a negative case.** The `dd-import` body must send `verified=false`, and a negative case must prove that the check fails when the field is removed. Host it in an existing workflow gate script, for example `scripts/check-workflow-uploads.sh`. The planner picks the script. This follows 29.4 D-04.

### Release and sequencing
- **D-15:** **Split into two PRs, as in 29.4 D-07.**
  1. **PR A** merges to security-platform `main` untagged. It carries the `security.yml` change (D-01), the gate (D-14), the kind proof (D-10, D-11) and the lifecycle-assert text (D-13).
  2. The operator dispatches Scheduled Security. Read back `ci/main` (D-12). Run the one-time reset if D-05 requires it, then read back again.
  3. **PR B** carries the TRIAGE.md L44 rewrite (D-08) and the reset procedure if one is needed. `main` never claims something unproven.
  4. Tag **`v1.4.0`** and move `v1` (ADR-018).
  5. Write **ADR-032** in this repo **after the tag**, as in 29.4 D-18.

  Every push, PR, merge, dispatch and live PATCH needs operator approval.
- **D-16:** **The version is `v1.4.0`, a minor release.** Consumers see a change in triage semantics: Trivy findings now enter Under Review. The live tags today are `v1.3.0`, `v1.2.0`, and `v2.0`, which is a milestone annotation, not a workflow release. The release needs a **v1 consumer impact check** scoped like 29.4 D-14, with each item recorded as a command and its output:
  - `git diff v1.3.0..<release-sha> -- .github/workflows/security.yml` touches only the `dd-import` `run:` body and comments. These are byte-unchanged: `on.workflow_call` inputs and secrets, the five `security / …` job names, SARIF `category:` values and artifact `name:` values.
  - `git rev-parse v1^{}` equals `git rev-parse v1.4.0^{}`, and both equal the release SHA.
  - Consumers that do not enable the DefectDojo import are a no-op class.
  - Enumerate the actual `@v1` consumers.
- **D-17:** **The upgrade note goes in three places:**
  - ADR-032;
  - the `v1.4.0` release notes;
  - **one line in `docs/adoption-guide.md` §12, subsection "Deduplication and Triage"** (~L834-860). It uses PR B timing, and `bash scripts/check-adoption-guide.sh` must pass.

  The note says that Trivy findings now enter Under Review. It also states the D-05 outcome for findings imported before the upgrade.

### Records
- **D-18:** Write a **new ADR-032** that records:
  - the cause (D-03);
  - the `verified=false` field and why;
  - the kind proof and the live readback evidence;
  - the D-05 outcome;
  - the impact check;
  - the `v1.4.0` release.

  In its own text, it supersedes the ADR-026 "Trivy originals arrive Verified" tradeoff and closes 28-REVIEW WR-03. Add its row to `docs/adr/README.md`. ADR-026 stays **byte-unchanged**, because ADRs are append-only.

### Claude's Discretion
- The kind-proof P-label names, their place in the harness order, and how the "old body" negative control is produced (for example, a copy of the extracted body with the field removed).
- Which gate script hosts D-14, and the wording of its failure message.
- The exact form of the one-time reset (a script subcommand or a documented API recipe), if D-05 requires it.
- The plan and wave split, within the D-15 sequence.

</decisions>

## Existing Code Insights

### Reusable Assets
- `defectdojo-import-proof.sh` already runs the committed `dd-import` body against kind DefectDojo 3.3.200. It already reads `verified` per finding (FIELDS ~L1710), and already PATCHes findings (FP body ~L3158). The new P-labels reuse its import, reimport and readback helpers.
- `defectdojo-lifecycle-assert.sh` has `api_get_all`, `engagement_findings` and snapshot capture (`main-*-snapshot.json` with a `verified` field). These fit the D-12 before and after snapshots without a new subcommand.
- The `ci/main` snapshots in `.planning/phases/29-defectdojo-live-validation/evidence/` show the snapshot JSON shape. The snapshots carry `test_ids` but not Test titles: map Tests by `file_path` or title, or read `/api/v2/tests/`.

### Established Patterns
- `--form-string` for every non-file field in `dd-import` (a branch name starting with @ must not make curl read a file). The new `verified=false` field joins the `fields` list and inherits this.
- Gate plus negative case for every invariant (29.3, 29.4 D-04).
- Every live step is approved by the operator. Untagged merges come first, and the tag follows only after live evidence.
- ADRs are append-only. The new ADR is written after the tag, and it supersedes older decisions in its own text.

### Integration Points
- `security.yml` is the reusable workflow behind `security-platform/.github/workflows/security.yml@v1`. The change reaches every `v1` consumer that enables the DefectDojo import when `v1` moves.
- `pr-security.yml` and `scheduled-security.yml` call `security.yml`. Only the scheduled run reimports `ci/main`.
