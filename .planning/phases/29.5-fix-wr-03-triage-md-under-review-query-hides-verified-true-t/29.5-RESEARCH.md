## Summary

**The root cause, read from source:** the DefectDojo 3.3.200 Trivy parser sets `verified` itself. `TrivyParser.convert_trivy_status()` (`dojo/tools/trivy/parser.py` L80-157) maps each vulnerability's Trivy `Status` to finding fields:
- `affected`, `fixed`, `will_not_fix`, `fix_deferred`, `end_of_life` and `not_affected` map to `verified: True`;
- `unknown` and `under_investigation` map to `verified: False`;
- a missing status maps to `{}`, which leaves the model default `verified=False` (`dojo/finding/models.py` L225).

The parser splats these fields into `Finding(..., **status_fields)` at L384. The captured 29.4 trivy-image report has statuses `affected` 49, `fix_deferred` 7, `fixed` 3 and `will_not_fix` 1. All of them map to True, which matches the measured 59/60 `verified=true`. No import default is involved.

`CommonImportScanSerializer.setup_common_context` (`dojo/api_v2/serializers.py` L639-642) passes `verified=None` when the request has no `verified` key, and `None` means "keep the parser's value". When the request does have the key, the importer (`default_importer.py` L248-250) and the reimporter's new-finding path (`default_reimporter.py` L1292-1294) **overwrite** the parser value. The fix therefore works as designed for new findings, and the D-04 stop is not expected to trigger.

**Behaviour on matched findings is not uniform. This is the point the planner must not miss.** The reimporter routes each matched finding through `process_matched_finding` (L1023-1045):
- **Active and still reported** (the common case, `else` branch L1250-1252): `verified` is **not touched**.
  - So the 65 active live Trivy findings stay `verified=true` after the first new-body reimport. The **D-05 one-time reset is predicted to be needed**.
  - So a triager-set Verified on such a finding **survives**. **D-06 is predicted to hold.**
- **Reactivation of a mitigated match** (L1155-1164): if `self.verified is not None`, then `existing_finding.verified = self.verified`. This is unchanged code, but before the fix `self.verified` was `None`, so the path left `verified` alone. After the fix, a regressed finding comes back `verified=false`, **even if a triager had verified it before it was closed**. This is a narrow form of "reimport clears a triager-set Verified", and the CONTEXT's expectation ("applies `verified` only to findings that reimport creates") does not hold for it. The operator must decide whether it triggers D-07.
- **The report itself closes a match** (L1227-1228, L1247-1248): `verified` is overwritten to `false`, but the finding is being closed anyway (inactive). This path is low impact.

**Primary recommendation:** Add `"verified=false",` to the `dd-import` `fields` list. Prove it in kind with a fresh-product old-body versus new-body sequence that measures four things on the same finding ids:
1. new findings;
2. pre-fix Trivy originals;
3. a triager-Verified active finding;
4. a triager-Verified finding that is mitigated and then reactivated.

Put an explicit operator checkpoint on result 4 (D-07) and on result 2 (D-05) before PR A merges.

### Finding 1: Why Trivy lands `verified=true` (D-03)

| Step | File:line | What it does |
|---|---|---|
| Parser status map | `dojo/tools/trivy/parser.py` L80 (`convert_trivy_status`), L109-155 (map), L157 (`return status_mapping.get(trivy_status, {})`) | `affected`, `fixed`, `will_not_fix`, `fix_deferred`, `end_of_life` and `not_affected` map to `"verified": True`. `unknown` and `under_investigation` map to `False`. Any other status maps to `{}`. |
| Applied per vuln | `parser.py` L353 (`status_fields = self.convert_trivy_status(vuln.get("Status", ""))`), L384 (`**status_fields` in `Finding(...)`) | The parser sets `verified` on the unsaved finding. |
| Request without `verified` | `dojo/api_v2/serializers.py` L639-642 | `if "verified" in self.initial_data: context["verified"] = data.get("verified") else: context["verified"] = None`. |
| Importer option | `dojo/importers/options.py` L86, L617-626 | `validate_verified`: bool, not required, default `None`. |
| Model default | `dojo/finding/models.py` L225 | `verified = models.BooleanField(default=False, ...)`, which is why the other parsers land `false`. |

**Verdict:** the parser sets `verified` itself, and the API passes the parser's value through unchanged when the request omits the field. This is not an import or reimport default. **Read from source.**

The data agrees. `29.4/evidence/29.4-04-pr-a-trivy-image/trivy-image.json` has Trivy `Status` values `{"affected":49,"fix_deferred":7,"fixed":3,"will_not_fix":1}`, and every one of them maps to True.

### Finding 2: An explicit `verified=false` is honoured for new findings (D-04)

There are two code paths:

| Call | Path | Override |
|---|---|---|
| First call for a Test (no Test yet; `auto_create_context=true`) | `serializers.py` L866-879: `ReImportScanSerializer.process_scan` falls back to `get_importer` (**DefaultImporter**, with `close_old_findings` forced False) | `default_importer.py` L248-250: `if self.verified is not None: unsaved_finding.verified = self.verified` |
| Every later call | `serializers.py` L858-865: **DefaultReImporter** | New, unmatched findings: `default_reimporter.py` L1292-1294, the same override |

`ReImportScanSerializer.set_context` (L802-807) delegates to `setup_common_context`, so the `"verified" in self.initial_data` logic applies to reimport too. The parser value is computed first and then overwritten, so **the parser cannot override `verified=false`**. D-04 is not expected to fire. The kind proof is the confirming measurement.

**Multipart parsing:** the body sends `--form-string verified=false`. DRF's `BooleanField` parses the string `"false"` to `False` [ASSUMED: DRF FALSE_VALUES]. The same mechanism already carries `close_old_findings=true` and `auto_create_context=true` successfully, which is MEDIUM supporting evidence. The kind proof settles it.

### Finding 3: Existing matched findings (D-05, D-06), as predictions from source

`default_reimporter.py` `process_matched_finding` L1023-1045 dispatches on the existing finding's state:

| Existing finding state | Method | `verified` written? | Prediction under the new body |
|---|---|---|---|
| FP, OOS or Risk Accepted | `process_matched_special_status_finding` L1047-1081 | No | Unchanged. |
| Mitigated (`is_mitigated`) and reported again | `process_matched_mitigated_finding` L1083-1192, reactivate block L1153-1164 | **Yes**: a duplicate gets `verified=False`. Otherwise `active=True` and `if self.verified is not None: existing_finding.verified = self.verified` | **Reactivated findings become `verified=false`.** |
| Active, and the report marks it mitigated | `process_matched_active_finding` L1220-1235 | **Yes**, L1227-1228 | It is closed, with `verified=false`. |
| Active, and the report marks it FP, RA or OOS | L1237-1255 | **Yes**, L1247-1248 | It is closed, with `verified=false`. |
| **Active, and still reported (the common case)** | `else` L1250-1252 (`unchanged_items`) | **No** | **`verified` is preserved.** |

The predictions:
- **D-05:** the 65 active live Trivy findings (5 `trivy-fs` and 60 `trivy-image` in `29.4-main-after-pr-b-snapshot.json`) **stay `verified=true`** after the first new-body reimport. The one-time reset is needed. *Prediction; kind and live measure it.*
- **D-06:** a triager `PATCH {"verified": true}` on an active finding that the next report still contains is **preserved**. *Prediction; kind measures it.*
- The first live new-body call for `ci/main` is a **reimport**, because the Test exists, so the DefaultImporter fallback and its override (L248-250) never run there. Nothing in that call can reset the 65.
- `close_old_findings` (`mitigate_finding`, `base_importer.py` L1229-1260) does not write `verified`. A finding that is mitigated because it is absent keeps its `verified` until it is reactivated.

### Finding 4: The reactivation path clears a triager's Verified (a D-07 decision for the operator)

Under the new body, `self.verified` is `False` on every call. The sequence is:

1. A triager verifies finding X on `ci/main`.
2. The scanner stops reporting X, and `close_old_findings` mitigates it (`verified` is still true).
3. X regresses, and the next reimport matches it as mitigated and reactivates it (L1153-1164).
4. `existing_finding.verified = False`.

Before the fix, step 4 left `verified=true` (`self.verified` was `None`).

| Consideration | Points toward |
|---|---|
| L36 says "Verified is preserved. The finding stays open until it is fixed." The reactivated finding was **fixed** and has now regressed. L40 says that a reopen "is intended". | Not a D-07 violation: a regression re-entering Under Review is arguably correct. |
| D-07 says literally: "if `reimport-scan` with `verified=false` clears a Verified that a triager set, stop". Behaviour changed from the pre-fix state. | A D-07 trigger in the narrow regression path. |
| It affects only findings that were fixed and then came back. The common active case is unaffected. | Low blast radius. |
| Side benefit: 121 mitigated, `verified=true` Trivy findings on live `ci/main` (1 `trivy-fs` and 120 old SHA-tagged `trivy-image`) self-correct if they ever reappear, and stay out of the D-05 reset scope. | — |

**Recommendation:** do not rule on this in planning.
- Add a dedicated kind P-label that measures the reactivation case.
- Make the plan **stop at a `checkpoint:human-verify`** that presents the result to the operator before PR A merges. This follows the D-07 stop-and-ask rule.
- If the operator accepts it, D-08 needs a matching sentence for the L36 and L40 rows ("A reopened finding returns to Under Review"). That is an L36/L40 correction only on evidence, which the 28-06 rule allows. It is not a pre-approved rewrite.

### Finding 5: Duplicates are always `verified=false`

`dojo/finding/deduplication.py` L131 (`set_duplicate`) and L178-182 set `new_finding.verified = False`. The import-proof comment at L3075-3080 confirms that `trivy-fs` and `trivy-image` cross-duplicates occur inside one engagement, because they share the `Trivy Scan` type. Consequences:
- The **negative-control** assertion ("old body: Trivy lands true") must range over **non-duplicate** Trivy findings, and should also require a count above 0.
- The **positive** assertion ("new body: every finding false") may include duplicates.

## Common Pitfalls

### Pitfall 1: Duplicates confound the verified assertions
**What goes wrong:** the negative control fails because some Trivy findings are duplicates, which are `verified=false` regardless of the body.
**How to avoid:** filter on `duplicate == false` for the "lands true" assertion and require a count above 0. Use a fresh product per case.
**Warning signs:** the negative-control count of true findings is below the Trivy finding count by roughly the number of fs/image overlaps.

### Pitfall 2: Reading before async dedup settles
**What goes wrong:** a duplicate is still unmarked when the snapshot is read.
**How to avoid:** call `wait_dedup_settled` after each import (`async_wait` is set in the bootstrap).

### Pitfall 3: A vacuous negative control
**What goes wrong:** the "old body" strip matches nothing, so both runs use the new body. The negative control then fails, or it passes for the wrong reason.
**How to avoid:** the P-VERIFIED-BODY exact-one-line diff check, plus the expectation that the old-body Trivy findings read true (a count above 0).

### Pitfall 4: A cron reimport lands between the before-snapshot and the merge
**What goes wrong:** the before-snapshot is no longer the pre-fix state, or the cron imports the new body before the snapshot.
**How to avoid:** take the snapshot immediately before the merge, check `gh run list` just before the dispatch, and record the timestamps (29.4-05 Step 1 pattern).

### Pitfall 5: Live has no new Trivy findings in the window
**What goes wrong:** "new findings arrive `verified=false`" cannot be shown live.
**How to avoid:** label that claim **measured in kind** in TRIAGE.md and ADR-032 (D-09). Record "0 new Trivy findings" live if that is what happened.

### Pitfall 6: The reactivation semantics are not surfaced
**What goes wrong:** the plan proceeds as if D-07 cannot trigger, and the runbook then claims "Verified is preserved" without qualification.
**How to avoid:** add the P-VERIFIED-REACTIVATE measurement and an operator checkpoint before PR A merges (Finding 4).

### Pitfall 7: Open Dependabot PRs touching security.yml
