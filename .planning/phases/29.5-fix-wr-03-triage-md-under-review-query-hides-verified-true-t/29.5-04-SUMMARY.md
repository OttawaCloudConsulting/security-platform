## What was built

- **`vf_patch_verified LABEL ID BOOL`**
  - Uses the admin write shape: header by path, a JSON body in a 0600 file removed after use, and `api_call`.
  - It fails if rc != 0 or the HTTP code is not 200, and also if the response does not echo `verified=BOOL`. On failure it calls `proof_fail` and returns 1. It never aborts.
- **`vf_measure MODE READ IDS [PART]`** is a Python heredoc with modes `reset`, `persist` and `triager`. It uses the `PROOF_VF_` env prefix and writes through `tally_assert_log` with a non-zero-exit guard, as `verified_assert` does.
- **`vf_old_continue`** runs only if the old-body negative control ran; otherwise it records a named FAIL for RESET and TRIAGER (a). Steps:
  1. Select the pre-fix Trivy ids: non-duplicate and verified=true, by the plan 03 Trivy rule.
  2. Select N: the lowest-id active, non-duplicate, non-Trivy finding with verified=false (gitleaks or semgrep preferred). PATCH N to true.
  3. Run the committed-body reimport and read back `T_TRUE + N`.
  4. Print `still_true=<n> of <m>` and whether that equals the prediction, then the TRIAGER (a) verdict.
  5. PATCH every still-true id to false, run another reimport, and assert they all stay false. If no id was still true, record "not applicable (0 still true)".
- **TRIAGER (b)** runs between the two NEWREIMPORT calls. Y is the lowest-id active, non-duplicate trivy-fs finding in S1 with verified=false; Y is PATCHed to true and read after call 2. If that PATCH fails, only the Y readback is skipped, not call 2 or the NEWREIMPORT assertion.
- **`vf_reactivate`** uses `gitleaks-results.json` (REACTIVATE_REPORT from the 29.5-03 evidence) and records a FAIL if that report is absent. The FULL and TRIM single-report dirs are built from it. The `vf_drop_one` output and its log are written outside the import dir. It runs steps 0 to 5 as planned and prints active, is_mitigated and verified after steps 2 to 5. The PASS line prints X's id, its test_title, step 3, step 4 and step 5 values, and the source prediction.
- **NEWREIMPORT failure handling:** a failed trivy-fs drop no longer ends `prove_verified` early. REACTIVATE still runs.
- **Stale comment** (now around L3880) rewritten: the committed body sends verified=false, and the FP PATCH still sends verified=false because findings imported before v1.4.0 can carry verified=true. The FP PATCH body is unchanged.
- **Header and `prove_verified` doc** now name the three new labels and `proof/verified-reactivate`.
- **`vf_drop_one`:** the SC2329 disable is removed and its doc comment updated, because its caller has landed.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2] PATCH response must echo the written value**
- `vf_patch_verified` also requires the response's `verified` to equal BOOL. Without this, a 200 that did not take would show up as a false D-07 STOP or a false RESET reading.

**2. [Rule 2] REACTIVATE mechanics also checked at steps 2 and 3, and X must be non-duplicate**
- Step 2 non-reactivation and a step 3 readback that is not verified=true or active=true now FAIL as mechanics. X must read duplicate=false in S0.
- Each of these would otherwise make the D-07 value meaningless. The verified values at steps 4 and 5 are still printed and never asserted.

**3. [Rule 2] X identified via findings_by_ids**
- X is identified from findings_by_ids on the S0-active ids, not from the S1 snapshot. The snapshot endpoint's handling of inactive findings is not proven.

**4. [Rule 1] Early `return 0` on a NEWREIMPORT drop failure removed**
- Without this change REACTIVATE would be skipped silently. That path now also records a named FAIL for TRIAGER (b).

**5. TRIAGER (b) Y also requires verified=false in S1**
- With this condition, a true reading after call 2 can only come from the PATCH, which is the plan's own rationale.
