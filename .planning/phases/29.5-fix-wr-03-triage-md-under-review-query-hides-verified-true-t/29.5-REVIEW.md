## Summary

Scope: the Phase 29.5 changes in `security-platform` (`git diff v1.3.0..HEAD`, HEAD `9456cbb` = v1.4.0 tree) and the
docs-repo artifacts (ADR-032, its index row, the adoption-guide v1.4.0 bullet).

The functional change is correct. It is one line, `"verified=false",`, in the `dd-import` `fields` list
(security.yml L1554), and it is posted through `--form-string` on every reimport-scan call. The lifecycle-assert
edit only changes text. The P-VERIFIED proof group is careful. It fails closed on mechanics, restores
`DEDUP_B_IMPORT` on every path, and checks that each PATCH took effect.

Two things were reproduced in a scratchpad:

1. The VERIFIED-FALSE static gate passes when the field is commented out in place.
2. The reset recipe's jq scope filter widens when `ENG` is malformed.

The reset recipe in TRIAGE.md is byte-identical to the one run live (checked by diffing the bash block against
`29.5-reset-recipe.md`). Its transport safety is sound:
- an https-only `case` guard
- `--proto =https --proto-redir =https`
- `curl -q` first
- a `ssl_verify_result == 0` check
- the token is sent through a 0600 header file, never argv
- an EXIT trap
- a client-side re-check of every server filter
- fail-closed pagination
- a `yes` prompt before any write
- stop on the first non-200

The weak points are not about transport. They are about scope and verification: there is no time bound, no check of
the engagement's name, the PATCH result is not checked, and the block is shaped for pasting.

No Critical findings. Neither top warning produces a wrong result on the shipped path. The gate bypass is still
caught by the kind proof (`verified_strip` uses `startswith`, so it refuses a commented line). Over-reach by the
reset errs toward more review, not less. The reasoning is stated in each finding.

## Warnings

### WR-01: VERIFIED-FALSE gate (check 22) passes when the field is commented out inside the list

**File:** `repos/security-platform/scripts/check-workflow-uploads.sh:781-808`
**Issue:** All three sub-checks match substrings of the raw `run:` text:
- `run.count('"verified=false",')`
- `run.count("verified=")`
- the `fields_at < verified_at < close_at` position test

None of them tells Python code from a Python comment. Reproduced: in a scratch copy of the workflows I changed line
1554 to `# "verified=false",  # every parser ...`. Then `WORKFLOWS_DIR=<scratch> bash scripts/check-workflow-uploads.sh`
printed `PASS - 22 checks, 0 failures`. The workflow would then send no `verified` field, and Trivy findings would
again land `verified=true`. That is the exact regression check 22 exists to block.

Only the kind proof catches this, because `verified_strip` matches with `startswith` and would refuse to strip, so
P-VERIFIED-BODY fails. The kind proof is a heavier, PR-only layer. ADR-032 Decision 2 lists three scratch negatives
(deleted, `verified=true`, moved after `]`). This fourth case is not among them, so the coverage claim there is
incomplete.

**Fix:** match on the code part of each line, not the raw text:
```python
def code_part(line):
    # dd-import fields are plain string literals; a '#' before the first quote starts a comment
    s = line.lstrip()
    return "" if s.startswith("#") else s
lines = run.splitlines()
field_lines = [i for i, l in enumerate(lines) if code_part(l).startswith(VERIFIED_FIELD)]
# require len(field_lines) == 1 and the fields_open_line < field_lines[0] < close_line,
# using the same line-index scan already used for close_at
```
Add the commented-in-place case as a scratch negative in the gate's self-test evidence.

### WR-02: Reset recipe has no time bound and can erase triager-set Verified on post-upgrade Trivy findings

**File:** `repos/security-platform/kubernetes/defectdojo/TRIAGE.md:122-126, 168-179`
**Issue:** The section is titled "after upgrading to v1.4.0" and the text says "Run this once". But the selection is
"every active, open Trivy finding on the engagement that reads `verified=true`", not "findings imported before
v1.4.0". From v1.4.0, the only way a Trivy finding gets `verified=true` is a triager's confirmation. An adopter who
upgrades, triages some new Trivy findings to Verified, and runs the reset days later has those decisions silently
cleared. The printed id list cannot show which ids were parser-set and which were triager-set, so the stated undo
("set `verified` back to `true` on those ids") would also re-verify the pre-upgrade parser values that the reset is
meant to clear.

This is a WARNING, not a BLOCKER, because the error goes the conservative way: findings return to Under Review. It is
still a loss of triage data, and the published recipe gives no warning about it. The adoption-guide bullet (L852-856)
does not mention the timing either.

**Fix:** state the precondition in the prose: "Run it after the first v1.4.0 `ci/<default>` import and before anyone
marks a Trivy finding Verified." Optionally, also bound it by time on the client side: take an operator-supplied
`CUTOFF` (the timestamp of the first v1.4.0 import) and keep only findings created before it. Check which creation
field DefectDojo 3.3.200 exposes on `/api/v2/findings/` (`created` vs `date`) before writing the filter.

### WR-03: `ENG` is spliced into the jq program unvalidated, and the engagement is never confirmed to be `ci/<default>`

**File:** `repos/security-platform/kubernetes/defectdojo/TRIAGE.md:132, 162-164`
**Issue:** `select(.engagement == '"$ENG"' and ...)` builds jq source text from the shell variable. Reproduced: with
`ENG='42 or true'`, the filter selects a Trivy Test whose `engagement` is 99, because jq parses it as
`.engagement == 42 or (true and ...)`. Most malformed values fail closed somewhere else: curl rejects the space, an
empty value is a jq syntax error. But the safety rests on that accident, not on a check.

Separately, the Scope paragraph says "the `ci/<default>` engagement only", and nothing enforces it. If an operator
types the id of a PR engagement, or an engagement in another product, the recipe resets that engagement without
complaint. The only scope guard is the operator's typing of a number.

**Fix:**
```bash
[[ "$ENG" =~ ^[0-9]+$ ]] || { echo "FAILED: ENG must be a numeric engagement id" >&2; exit 1; }
EXPECT_NAME="ci/main"   # the ci/<default> engagement name
dd_api GET "$DD/api/v2/engagements/$ENG/" 200
jq -e --arg n "$EXPECT_NAME" '.name == $n' "$BODY" >/dev/null \
  || { echo "FAILED: engagement $ENG is $(jq -r .name "$BODY"), not $EXPECT_NAME" >&2; exit 1; }
TESTS="$(jq -c --argjson eng "$ENG" '[.results[] | select(.engagement == $eng and .scan_type == "Trivy Scan" and (.title == "trivy-fs" or .title == "trivy-image")) | .id]' "$BODY")"
```
(Run the engagement GET before the tests GET, because `$BODY` is overwritten on each call.)

### WR-04: Reset PATCH is accepted on HTTP 200 without checking that `verified` changed

**File:** `repos/security-platform/kubernetes/defectdojo/TRIAGE.md:186-190`
**Issue:** `dd_api PATCH ... 200 '{"verified": false}'` treats any 200 as success and prints `reset $id`. The
project's own proof harness says why that is not enough. `vf_patch_verified` (defectdojo-import-proof.sh
L2960-2987) checks that the response echoes the new value: "a PATCH that answered 200 without taking can then never
pass for a reimport effect". The live run relied on a separate readback (`after_open_trivy_true 0`), but an adopter
running the published recipe gets no such check. A serializer that drops the field, or a proxy that answers 200,
would print 65 `reset` lines and change nothing.

**Fix:**
```bash
for id in $IDS; do
  dd_api PATCH "$DD/api/v2/findings/$id/" 200 '{"verified": false}'
  jq -e '.verified == false' "$BODY" >/dev/null \
    || { echo "FAILED: PATCH $id answered 200 but reads verified=$(jq -r .verified "$BODY")" >&2; exit 1; }
  echo "reset $id"
done
```
Optionally re-run the Step 2 query at the end and require 0 candidates.

### WR-05: Reset block uses `set -euo pipefail` and bare `exit`, yet sits next to paste-style examples with no "run as a file" instruction

**File:** `repos/security-platform/kubernetes/defectdojo/TRIAGE.md:126-129, 141, 192-193`
**Issue:** The API examples just above (L76-117) use the same `DD`/`HDR`/`ENG` setup and are meant to be pasted into
an interactive shell. This block looks the same, and the prose says only "Run this once". If it is pasted:
- Every `exit 1` path, plus `Nothing to reset` (`exit 0`) and `Not confirmed`, closes the operator's terminal.
- On success, `set -e`, `-u` and `pipefail` stay on in their login shell.
- The `EXIT` trap does not fire until that shell ends, so `$BODY` (finding data) and, on failure paths, `$HDR` (the
  token) stay in `$TMPDIR` for the life of the shell.

The Step 4 comment says "the EXIT trap removes the header file", and the next line removes it by hand anyway. That is
redundant, and it does not clean up `$BODY`. The live run was not pasted: 29.5-08-SUMMARY says it ran from a scratch
file with stdin from a gate process. So only the documented usage is wrong.

**Fix:** add one sentence before the block: "Save the block as `reset-verified.sh` and run it with
`bash reset-verified.sh`; do not paste it into an interactive shell." This also matches the project's
explicit-interpreter rule. Delete the Step 4 `rm -f "$HDR"` and its comment, or change the comment to say the trap
removes both temporary files.

### IN-01: Recipe discards curl's error text and gives unclear failures for common operator errors

**File:** `repos/security-platform/kubernetes/defectdojo/TRIAGE.md:142, 150, 153, 163, 171`
**Issue:**
- `2>/dev/null` throws away curl's transport error. security.yml captures `%{errormsg}` for the same purpose.
- If `TOKEN_FILE` is missing, `printf "$(cat ...)"` does not trip `set -e`, so the header holds an empty token, and the
  first call fails with an unexplained `http 401`.
- A result with more than one page fails closed (correct), but tells the operator nothing about what to do next.

**Fix:** add `%{errormsg}` to `-w`. Add `[ -s "$TOKEN_FILE" ] || { echo "FAILED: token file missing or empty" >&2; exit 1; }`. In the pagination failure messages, suggest what to do (for example, raise `limit` or narrow by test).

### IN-06: P-VERIFIED-NEWREIMPORT identity match uses a loose substring test

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:2920`
**Issue:** `(f["component_name"] == pkg or pkg in title)`. A short package name, such as `ms` or `qs`, can occur in an
unrelated title, so the identity check is weaker than its comment claims. The `len(new) == 1` check limits the risk.
**Fix:** require `f["component_name"] == pkg` and `vid in f["vulnerability_ids"]` (both normalised by
`snapshot_engagement`), with the title used only as a fallback when `vulnerability_ids` is empty.
