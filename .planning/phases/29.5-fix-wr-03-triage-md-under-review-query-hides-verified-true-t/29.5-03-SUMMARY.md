# Phase 29.5 Plan 03: P-VERIFIED kind proof, first half, Summary

`defectdojo-import-proof.sh` now has a `prove_verified` group that runs last in `prove_dedup_triage`, after `prove_image_tag`. It contains three cases:

- **P-VERIFIED-BODY** builds the old body (the committed dd-import body with only the `"verified=false",` line removed) and checks that the stripped line is the only difference.
- **P-VERIFIED-FALSE** imports all 8 reports twice with the committed body. After each call it checks that the engagement holds exactly the 8 expected Tests and that every finding reads verified=false. As a negative control, it then imports the same reports once with the old body. In that run, non-duplicate Trivy findings must read verified=true and every non-Trivy finding must read verified=false.
- **P-VERIFIED-NEWREIMPORT** (D-04) checks that a finding created on the reimport path also reads verified=false. The finding comes from a vulnerability whose Status the parser maps to verified=true.

All helpers were proven offline on the real reports from Scheduled Security run **37230464825** (headSha aa48081, 2026-10-04T20:00:58Z). These cases have not yet run in kind.

## What was built

- Four readonly products, exported for the Python heredocs: `proof/verified-new`, `proof/verified-newreimport`, `proof/verified-old`, `proof/verified-reactivate`.
- `verified_strip SRC DST` removes one exact line (never a regex). It exits 3 if zero or several lines match, and then writes no DST. It returns 1 if chmod or `bash -n` fails.
- `vf_drop_trivy_fs SRC_DIR OUT_DIR` removes the first vulnerability, in document order, that has a unique triple and a Status that maps to True. It records the removed entry in `OUT_DIR.removed.json`, which sits outside the import dir. Exit 3 means no candidate; exit 4 means the count is wrong.
- `vf_drop_one SRC_FILE OUT_FILE` handles a top-level array (gitleaks) or an object with `.results[]` (semgrep). Exit 3 means no unique element or fewer than 2 elements, exit 4 means the count is wrong, and exit 5 means the shape is wrong.
- `verified_assert MODE` is one read-side Python script (env prefix `PROOF_VF_`) with three modes: positive, negative and newreimport. Its output goes through `tally_assert_log` and the existing non-zero-exit guard.
- The negative control saves `DEDUP_B_IMPORT` and points it at the old body for exactly one `verified_import_settle` call. It restores the variable straight after that call, before `BODY_RC` or the snapshot result is checked. `VF_OLD_SNAP` stays global so plan 04 can continue the product.
- `prove_verified` contains no `proof_abort` or `disposition_write`. Every failure is a named `proof_fail`.
