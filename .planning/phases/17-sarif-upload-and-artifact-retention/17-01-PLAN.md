<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → GitHub code scanning API | The `GITHUB_TOKEN` crosses here; its scope is set entirely by the two `permissions:` blocks this plan edits |
| Caller workflow → called (reusable) workflow | Permission set flows one way and can only be reduced; a grant made on the wrong side of this boundary is silently ineffective |
| Repo contents (untrusted PR branch) → workflow file itself | A `pull_request` run executes the workflow from the PR head, so a permission widening is itself reviewable content |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | Elevation of Privilege | `permissions:` blocks in both workflow files (ASVS V4) | mitigate | Grant exactly `contents: read` + `security-events: write` + `actions: read`; gate check 3 fails the build on `contents: write`, `pull-requests: write`, `actions: write`, `id-token: write`, `write-all`, `read-all` |
| T-17-02 | Elevation of Privilege | Grant placement — workflow-level vs job-level in the caller (V1/V4) | mitigate | OD-1: job-scoped grant so only the `security` job holds `security-events: write`; asserted by the inline yaml parse in Task 2 |
| T-17-03 | Tampering | Action tag reassignment on the two new actions (V14) | mitigate | ADR-004 full 40-hex SHA pins; gate check 4 asserts every `uses:` in both files is 40 lowercase hex characters |
| T-17-04 | Information Disclosure | `gitleaks --redact` removed, publishing raw credentials into a world-downloadable artifact (V12) | mitigate | Gate check 9 fails if any `gitleaks` run block lacks `--redact` |
