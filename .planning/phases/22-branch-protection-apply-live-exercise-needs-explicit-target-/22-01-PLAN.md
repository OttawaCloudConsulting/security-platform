  <action>
    Create `22-poll-merge-state.sh` in the phase directory. It takes three positional arguments —
    repo slug, PR number, and the previously-recorded merge state (empty string for a first read) —
    and polls `gh pr view "$PR" -R "$REPO" --json mergeStateStatus --jq .mergeStateStatus` until the
    value is neither `UNKNOWN` nor equal to the previous value, then prints the settled value on
    stdout and exits 0.

    Three properties are mandatory and each one is there because omitting it has a named failure mode:

    1. The post-loop assertion must test BOTH conditions — value is not `UNKNOWN` AND value differs
       from the passed-in previous value — and `exit 1` otherwise. 22-RESEARCH's published loop tests
       only the first, so twenty iterations that all return a stale prior value pass its guard. A
       stale `BLOCKED` read is exactly what arms Pitfall 7, where `gh pr merge` succeeds and lands the
       exercise branch on a real repository's `main`.
    2. Iteration count and sleep interval come from `POLL_ITERATIONS` (default 20) and `POLL_SLEEP`
       (default 5), read from the environment, so the stale path can be exercised cheaply in Task 1's
       own negative test.
    3. `set -euo pipefail`, no `|| true` anywhere, and the timeout message prints the last observed
       value and the previous value so a human reading the transcript can tell "never settled" from
       "settled but unchanged".

    Carry a header comment giving the three-way exit contract: 0 settled, 1 never settled or settled
    stale, 2 the `gh` call itself failed. Never set the executable bit; the file is invoked as
    `bash .planning/phases/22-.../22-poll-merge-state.sh ...` everywhere in this phase.

    Then create the evidence directory `22-evidence/` under the phase directory with a `.gitkeep`, and
    record in the SUMMARY that this directory is shared by plans 01 through 05 rather than following
