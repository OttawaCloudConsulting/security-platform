<objective>
Put the target repository back exactly as it was found, and prove it. Close the exercise pull request
unmerged and delete its branch, then PUT the ruleset document reconstructed from the capture taken
before anything was touched, and verify the restored rule types are byte-identical to the pre-exercise

carries no `.github/workflows/` at all, so five required checks left in place would sit permanently
pending on every future pull request — a real, indefinite lockout of work that has nothing to do with
this exercise. The audit finding asks for the refusal to be witnessed, not to be made permanent.

Output: a closed pull request, a deleted branch, a restored ruleset proven by an empty diff, and a
clean evidence directory ready to commit.

This task runs REGARDLESS of how plan 04 ended. Only its branch is conditional: if plan 03 recorded a
non-zero exit from the forward `--apply`, the ruleset was never modified, no rollback PUT is performed,
and the task instead verifies and records that the live state already equals the capture. Re-PUTting a
byte-identical document in that case would write a misleading "restored" line into the evidence.
</objective>

The PUT body schema is exactly six keys. `GET /rulesets/{id}` returns server-owned fields the PUT
schema does not accept — `id`, `node_id`, `source`, `source_type`, `created_at`, `updated_at`,
`_links`, `current_user_can_bypass` — so the raw GET response is NOT a valid PUT body:
  name, target, enforcement, conditions, bypass_actors, rules

Ruleset administration is not governed by the ruleset. `bypass_actors: []` and
`current_user_can_bypass: "never"` control REF UPDATES, not RULESET WRITES. An operator with
`admin: true` can always PUT the previous document back, even from inside a fully locked repository.
That is why this restore is reliable — provided the before-document was captured first, which plan 01
did.
</interfaces>
