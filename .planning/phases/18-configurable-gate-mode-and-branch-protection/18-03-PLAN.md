<objective>
Write the executable half of CICD-04: a read-modify-write helper that adds `required_status_checks` (five
byte-exact contexts, pinned to the GitHub Actions app) and a `pull_request` rule to the existing ruleset,
carrying every rule already present forward untouched. Dry run by default; the live `PUT` happens only
under an explicit `--apply`, and this plan never passes it.

Purpose: `PUT /repos/{o}/{r}/rulesets/{id}` REPLACES the whole document. A body carrying only the new rule
silently deletes `deletion` and `non_fast_forward` from `main` — a security regression dressed as a
security improvement. The recipe has to be read-modify-write, and it has to be a reviewed artifact rather
than a paragraph someone retypes under pressure. `required_status_checks` alone also does not require a
pull request (P-09 / ADR-002), so the helper adds both rules or the gate stays bypassable by direct push.

Output: a committed, never-executable helper script proven non-destructive offline, with no live write.
</objective>

<notes>
**Never set the executable bit** (project rule `defensive-protocol-v2-anti-slop.md`). The script is
invoked as `bash scripts/set-required-checks.sh`. Say so in its header, as its neighbours do.

**This plan performs no live write.** `--apply` is implemented and left unused. Whether to require checks
on THIS repository's `main` is 18-05's operator decision: with seeded fixtures plus blocking plus
`bypass_actors: []`, all five checks go red on every PR and `main` locks against every PR including the
revert.

**Never invent bypass-actor ids.** The script carries `bypass_actors` forward from the fetched document
verbatim and never synthesises an entry. An operator who wants an admin bypass adds it in the GitHub UI
(Settings then Rules then Rulesets then Default then Bypass list) BEFORE `--apply`; read-modify-write then
preserves it. Fabricating an `actor_id` is exactly the class of guess this project's rules forbid.

**No silent fallbacks.** If the GET fails, if the document has no `rules` key, or if a context is missing
from the verification SHA, exit non-zero with the raw cause. No `or {}`, no `try/except: pass`.
</notes>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local `gh` token (repo admin) → GitHub rulesets API | A single PUT can remove every protection on `main`; the token has admin and the ruleset has no bypass actors |
| Check-run name strings → required-context matching | A byte that differs produces a permanently-pending required check rather than an error |
| Script defaults → operator intent | A helper that writes by default would turn a curiosity-driven run into a branch lockout |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-04 | Tampering | `PUT /rulesets/{id}` replacing the whole document (P-05) | mitigate | Read-modify-write built from the fetched document; in-script assertion that no pre-existing rule type was dropped; the negative case is demonstrated in Task 2, not assumed |
| T-18-03 | Denial of Service | A mistyped context creating a permanently-pending required check (P-07) | mitigate | Contexts copied from `commits/{sha}/check-runs`, never retyped; U+2013 absence asserted; `--verify-sha` preflight mandatory under `--apply` |
| T-18-05 | Denial of Service | Self-lockout of `main` (P-06) | mitigate | No live write in this plan; `--apply` needs `--verify-sha` plus an explicit lockout acknowledgement; the decision itself is 18-05's operator checkpoint |
| T-18-06 | Elevation of Privilege | Direct push to `main` bypassing the gate entirely (P-09 / ADR-002) | mitigate | The `pull_request` rule is added in the same document as `required_status_checks`, never separately |
