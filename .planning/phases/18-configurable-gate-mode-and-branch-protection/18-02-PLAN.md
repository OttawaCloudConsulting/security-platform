<objective>
Apply the resolved gate mode: replace all eleven literal `continue-on-error: true  # D-04` values with
the fail-closed comparison, repair the three SCA step guards that blocking mode would otherwise skip, and
correct the caller workflow's two comments — including the one whose stated reason is factually wrong.

Purpose: this is the plan that makes CICD-06 real. The comparison is written `== 'report-only'` and not
`!= 'blocking'` because a typo must fail CLOSED: `reportonly` yields `false`, tolerance is off and the job
goes red loudly. `!= 'blocking'` fails open — the same typo leaves the repo un-gated while branch
protection reports green, which is the exact failure CICD-06 exists to prevent.

The hidden cost D-04's "just flip the flag" framing conceals is step sequencing. Three SCA scan steps
carry an `if:` with no status function, so GitHub's implicit `success()` skips them once an earlier step
in the job fails hard — while their `always()`-guarded verify steps still run and fail on an unmatched
glob, producing a traceback that reads like infrastructure breakage rather than "the scan never ran".
Fixing those three guards is part of this plan, not a follow-up.

Output: a workflow whose gate is entirely flag-driven, with report completeness preserved in both modes.
</objective>

<notes>
**Fail closed, always.** Write `== 'report-only'`. Never `!= 'blocking'`, never a negation, never
`fromJSON` gymnastics. The comparison already yields a boolean and actionlint type-checks it.

**Do not touch the eleven ADR-001 `continue-on-error: true` lines on upload steps.** They must remain
literal `true`: `check-workflow-uploads.sh` checks 5 and 6 assert `step.get("continue-on-error") is True`
and an expression string would fail them — which is the gate correctly defending an accepted ADR.

**The `always() &&` change alters report-only behaviour too, deliberately.** Today those three steps also
skip when an earlier NON-tolerated step (e.g. "Verify Trivy filesystem SARIF upload landed") fails. After
this change they run. That is more complete reports, but it is a behaviour change: record it in the
SUMMARY as intended, not as an incidental diff.

**Preserve each step's per-tool reason suffix.** The file's voice is tool-specific comments; the
verification grep passes either way, so nothing else catches a silent loss of "exit 2 means findings".

**No `with:` block in `pr-security.yml`.** A committed literal would defeat the phase goal — demonstrating
blocking would then require a YAML edit on a branch and every later flip another one. Omission is the
mechanism, not an oversight.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `env.GATE_MODE` → each scan step's tolerance | The single expression that decides whether a finding blocks a merge |
| Scan step failure → later steps in the same job | GitHub's implicit `success()` silently changes which steps run once a step fails hard |
| Caller YAML → called workflow inputs | A committed literal here would permanently override the repo-variable path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
