<notes>
**Why the workflow runs on the very PR that adds it.** The `pull_request` event reads workflow files
from the PR's *merge commit* (`GITHUB_SHA` = base ⊕ head, `GITHUB_REF` = `refs/pull/<N>/merge`), so a
workflow introduced by a PR runs on that same PR. This is why criteria #1-#3 are observable before any
merge — and why criterion #4 (Dependabot) is not: Dependabot reads config only from the default branch.

**Look for the run under the CALLER's name, not the callable file's.** A run initiated by the caller
appears in the Actions tab as `PR Security` (from `pr-security.yml`), with the called workflow's jobs
nested inside. Searching for `Security Scans` will find nothing and would falsely fail criterion #1.

**Do not gate on the `actions/workflows` API listing BOTH files.** RESEARCH suggests asserting both
workflows are registered server-side. Pre-merge this will likely show only `pr-security.yml`: the
endpoint lists default-branch workflows plus those with runs, and a callable workflow has no runs of
its own. Assert only `pr-security.yml` here. The both-registered assertion belongs in Plan 03, post-merge.

**Assumption A3 is being tested here.** RESEARCH assumes the check surfaces as
`<caller-job-name> / <called-job-name>`. That is unverified. Capture whatever string GitHub actually
emits, verbatim, and do not normalise or reformat it — Phase 18 will reference it exactly.

**Slug at runtime.** Resolve with `gh repo view --json nameWithOwner -q .nameWithOwner`. Do not hardcode
`OCC-github/security_solution` or `OttawaCloudConsulting/security-platform` — those two disagree and the
mismatch is an unresolved open question (see Plan 03 notes).

**Failure handling.** If the run fails, or no run appears at all, STOP → REPORT → WAIT per
`.claude/rules/defensive-protocol-v2-anti-slop.md`. Do not re-push hopefully. "No run appeared at all"
specifically means GitHub could not parse a workflow file — check the repo's Actions tab for a red
"workflow file issue" banner and report the raw message.
</notes>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local working tree → remote `origin` | Committed content leaves the workstation; the gitleaks pre-push hook is the last local control |
| PR event payload → workflow run | Contributor-controlled event data enters the run context |
| GitHub Actions runner → repository | The run holds a `GITHUB_TOKEN` scoped by the caller's `permissions` block |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-08 | Information Disclosure | `git push` of the Phase 14 branch | mitigate | Push runs the repo's gitleaks pre-push hook; `--no-verify` is explicitly forbidden in Task 1, so a block must be reported, not bypassed. |
| T-14-09 | Information Disclosure | Unrelated dirty working-tree files leaking into the public PR | mitigate | Plan 01 staged explicit paths only; Task 1 asserts the PR diff carries no `.claude/` noise. Repo is PUBLIC. |
| T-14-03 | Elevation of Privilege | `GITHUB_TOKEN` scope on the live run | mitigate | Verified live: the run executes under the `permissions: contents: read` block set in both workflow files. |
| T-14-10 | Spoofing | Misreading which workflow produced the run | mitigate | Runs are matched on `workflowName == "PR Security"` AND `event == "pull_request"`, not on a filename guess (Pitfall 7). |
| T-14-11 | Denial of Service | A failing run being re-pushed repeatedly to "see if it passes" | mitigate | STOP → REPORT → WAIT is mandated in `<notes>` and in Task 2 step 2; `gh run watch --exit-status` makes failure non-silent. |
| T-14-06 | Information Disclosure | Fork-PR secret exposure | accept | Plain `pull_request` trigger only (D-04): read-only token, no secret access on fork PRs. |
| T-14-SC | Tampering | npm/pip/cargo installs | accept | No registry packages are installed by this plan — it performs only `git` and `gh` operations. No `[ASSUMED]`/`[SUS]` packages exist, so no legitimacy checkpoint is required. |
</threat_model>
