**The closest analog is the one you must NOT copy.** CONTEXT.md line 61 claims the reference workflow's
jobs "can be adapted almost verbatim". RESEARCH falsified that: five of its commands are stale or wrong
against current tool versions, and it was written for `on: pull_request` with `security-events: write`,
neither of which is legal here. Take *structure and comment style* from the analog; take *commands*
from RESEARCH §Code Examples. 15-PATTERNS.md §1 has the line-by-line prohibition table.

**Report-only placement rule (D-04) — the single most important detail in this plan.**
`continue-on-error: true` goes on the **step**, never the **job**. Step-level: the step is annotated as
failed, the job concludes `success`, the check is green, the PR stays mergeable, and Phase 18 restores
blocking by flipping one flag. Job-level: the job concludes `failure` and the check renders RED, which
cannot cleanly become a required check later. Every tool keeps its native failing flags — Semgrep
`--error`, Checkov `soft_fail: false`, Trivy `--exit-code 1`. Do not swap any of them for a soft-fail
variant; those flags are load-bearing for Phase 18 (Chesterton's Fence).

**Corollary — never chain two natively-failing commands in one `run:` block.** GitHub's default shell is
`bash -e`, and under D-04 every scanner is *expected* to exit 1, so a two-command `run:` silently drops
the second command. This bites Gitleaks specifically (no dual-output flag): chaining the SARIF and JSON
invocations means the JSON file is never written and the `ls -l` evidence step then fails the job. Two
separate steps, the second carrying `if: always()`. `continue-on-error` tolerates the *step*; it does
not disable `-e` *inside* the step. Every follow-up step (SARIF conversion, `ls -l`) needs `if: always()`
for the same reason.

**No `upload-sarif`. No `upload-artifact`. This is a decision, not an option.** A called workflow can
only DOWNGRADE the caller's permissions, and `pr-security.yml` grants `contents: read`, so
`security-events: write` is unobtainable here (RESEARCH Pitfall 5). `upload-sarif` would either 403 or —
worse, under `continue-on-error` — silently succeed while uploading nothing. Artifact retention is
CICD-03 / Phase 17 and is listed in CONTEXT.md §Deferred Ideas. Success Criteria #4 only requires files
on the runner; the `ls -l` evidence step satisfies it. Do not widen `pr-security.yml` either — that file
is explicitly unchanged this phase.

**Deliberate severity-filter choice — do not "fix" it (RESEARCH Pitfall 7, Assumption A3).** Both Trivy
steps carry `--severity HIGH,CRITICAL`, which filters the *report file*, not just the exit code. That is
intentional: D-04 says preserve the reference workflow's native severity semantics so Phase 18 can flip
gating back on unchanged, and the reference passes `severity: 'HIGH,CRITICAL'`. Record in the SUMMARY
that Phase 17 must decide whether DefectDojo wants full-severity data, and that the fix would be either
dropping `--severity` from the report run and moving the threshold to the `--exit-code` gate, or adding
a second full-severity run. Do not change it silently here.

**Known risk: the Gitleaks binary checksum may trip the repo's own pre-push Gitleaks hook.** The install
step embeds a 64-character hex SHA-256, which `generic-api-key` style rules can match. This is a
FALSE POSITIVE with a specific, correct remedy: a FINGERPRINT entry in `.gitleaksignore` of the form
`file:rule-id:start-line` — obtained from the tool's own JSON output. It is NOT a path glob;
`.gitleaksignore` rejects path globs outright (RESEARCH C-3). Task 2 dry-runs the pre-push hook so this
surfaces here, not at push time in Plan 04. If it fires, add the fingerprint, and note that this is the
first legitimate `.gitleaksignore` entry in the repo — D-03's original path-glob idea remains wrong.

**Assumption A7 — name the fallback rather than discovering it on the runner.** `pip install
semgrep==1.177.0` on `ubuntu-latest` may hit PEP 668's externally-managed-environment guard. The
fallback, in order: `pipx install semgrep==1.177.0` (pipx is preinstalled on GitHub-hosted Ubuntu
runners), then `python -m pip install --break-system-packages semgrep==1.177.0`. Put the primary command
in the workflow and record the fallback ladder in the SUMMARY so Plan 04 does not have to invent it.

**Assumption A6 — use Plan 02's measured answer.** If 15-02-SUMMARY records that Checkov 3.3.17 wrote
different filenames than `checkov-results.json` / `checkov.sarif`, use the ACTUAL names in both the
action's `output_file_path` and the IaC job's `ls -l` step. Do not carry forward the assumed names.

**`versions.conf` stays untouched.** It pins `TRIVY_VERSION="0.69.3"` / `GITLEAKS_VERSION="8.30.0"` for
the *workstation* and is generated by `workstation/setup.sh`; a hand edit would be overwritten. The CI
pins here (Trivy `v0.74.0`, Gitleaks `8.30.1`) deliberately differ. Note the split in the workflow header
or the SUMMARY; whether the two should converge is a later-phase decision.
