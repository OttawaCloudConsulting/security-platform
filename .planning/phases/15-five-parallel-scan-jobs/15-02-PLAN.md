<objective>
Build the local gate that proves all five scanner invocations produce real, non-empty results against
the real checkout — before a single line of them is committed to workflow YAML. `scripts/smoke-scans.sh`
runs the exact CI-shaped commands for Semgrep, Checkov, Trivy filesystem, Trivy image and Gitleaks, and

job to write machine-readable output. An empty report that reads as "clean" is the exact failure mode
the project's anti-slop rules call out. This script is the compensating control, and it is reusable
every time a fixture, tool version, or flag changes in Phases 16-19.

<notes>
**TARGET REPOSITORY.** The script lands at `repos/security-platform/scripts/smoke-scans.sh` — a NEW
top-level `scripts/` directory in the *target* repo, not in the outer documentation repo. It ships with
the thing it tests, and being outside `fixtures/` it is covered by the repo's own `shellcheck` hook
(`types: [shell]`, which matches on the shebang). All git operations use `git -C repos/security-platform`.
Never `git push` from the outer repo (disjoint histories, same remote URL — see 15-01 notes).

**PLACEMENT DELTA vs RESEARCH.** RESEARCH's smoke block opens with `cd repos/security-platform`, an
OUTER-repo path. That is wrong once the script lives inside the target repo. Replace the literal `cd`
with the repo-root idiom already used in-repo: `REPO_ROOT="$(cd "$(dirname "$0")/.." && pwd)"`, then
`cd "$REPO_ROOT"`. The script must work from any working directory.

**THE `set -e` TRAP — this is the whole reason the script needs care.** Every one of the five scanners
is *expected* to exit 1; that expected non-zero exit IS the assertion. Under `set -euo pipefail`,
RESEARCH's `semgrep … ; echo "exit=$?"` form aborts the script at the first scanner and the remaining
four never run. Use `rc=0; <scanner> … || rc=$?` per command — `|| true` is wrong here because it
discards the very exit code being asserted. This is the same failure class as the workflow's "never
chain two natively-failing commands" rule (Plan 03).

**Assert direction, not magnitude.** RESEARCH's measured counts (2 Semgrep findings, ~12 Checkov failed
checks, 9 npm vulns, 222 image vulns, 9 Gitleaks findings) were taken with specific flag sets and drift
as advisories publish. Gate on `exit == 1` and `report is non-empty`, and PRINT the counts for the
SUMMARY. Do not gate on a specific number — brittle thresholds create self-inflicted red runs.

**One measured count IS load-bearing and must be printed both ways.** RESEARCH's "9 npm vulnerabilities"
came from an UNFILTERED `trivy fs`, while the CI SCA job carries `--severity HIGH,CRITICAL` (Pitfall 7).
Run `trivy fs` twice — once unfiltered to record the total, once with the exact CI flags — and gate on
the FILTERED run exiting 1. If the filtered run yields zero, STOP and REPORT: the CI job would go green
with an empty report, which fails Success Criteria #2. (Expected to hold: `minimist@1.2.0` carries a
CRITICAL and `lodash@4.17.15` carries HIGHs.)

**Where the SAST and secrets findings come from — do not "fix" them.**
- Semgrep's real result is the repo's own `cicd/.github/workflows/security.yml`, which contains a
  `curl … | sh` Grype installer that `p/default` flags as `yaml.github-actions.security.gha-curl-pipe-shell`.
  That reference file is a non-active path and stays as-is; removing it would empty the SAST job.
- Gitleaks' real result is git HISTORY, not the working tree: `gitleaks git .` → 9 findings, exit 1;
  `gitleaks dir .` → 0 findings, exit 0 (RESEARCH C-5, Pitfall 4). The script must use `git` mode.

**Carry Open Question Q1 to the user.** Assumption A4 says the 9 history findings are fake Phase-05
secrets-detection test strings, not live credentials — strong indirect evidence, never directly
confirmed. Task 2 enumerates them (rule ID + file path, values redacted) so the user can confirm. If
any looks like a live credential, that is an active incident, not CI noise: STOP and REPORT immediately.
They are harmless report-only noise this phase, but Phase 18's gate mode will block on them and will
need a `--baseline-path` or a fingerprint-based `.gitleaksignore` entry — the fingerprint form
(`file:rule-id:start-line`) is the ONLY form `.gitleaksignore` accepts (RESEARCH C-3).

**No executable bit, ever.** Per `.claude/rules/defensive-protocol-v2-anti-slop.md` §Script Safety: do
not `chmod +x`. The shebang is documentation. Every invocation is `bash scripts/smoke-scans.sh`, and
the `Usage:` block in the header must show it that way.

**Write reports to `mktemp -d`, never into the repo.** Stray `*.json` / `*.sarif` files in the checkout
would be picked up by the next scan run and would pollute `git status`. Do not add ignore entries to
`.gitignore` to work around this — use a temp directory and clean up.
</notes>
