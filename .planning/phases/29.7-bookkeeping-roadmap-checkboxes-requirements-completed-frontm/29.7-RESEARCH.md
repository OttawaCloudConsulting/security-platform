## Summary

This phase is records-only. Most of it is mechanical: tick 3 checklist lines, add 7 checklist lines and 7 table rows, add one frontmatter key to 4 files, make 3 wording fixes, write one ledger file, resolve stragglers, and annotate the audit. Research measured every target, and every scope fact in CONTEXT.md holds. Two things CONTEXT did not know change what the planner builds. Both conflict with locked decisions and need operator confirmation.

1. **D-05 conflicts with the gsd-sdk parser.** gsd-sdk's frontmatter parser does not strip trailing YAML comments. With the D-05 form (`requirements-completed: [NEXUS-05]  # backfilled ...`), `gsd-sdk query summary-extract` returns `["[NEXUS-05]  # backfilled ..."]`: one string, not the ID. `summary-extract` is the call `/gsd:audit-milestone` uses to read this key (workflow `audit-milestone.md:118`). The re-audit that CONTEXT defers would therefore still fail to see the five backfilled IDs as array elements. Moving the comment to its own line directly above the key (form B) parses correctly in both gsd-sdk and yq.
2. **D-01 + D-04 conflict with gsd-sdk's ROADMAP mutators.**
   - `phase.complete` and `roadmap.update-plan-progress` assume the active milestone sits after the last `</details>`, as in the canonical GSD template. This ROADMAP puts the active milestone first, inside `<details open>`. As a result, the phase-checklist tick never fires in this ROADMAP. That is the root cause of Phase 23 deferred item 8.
   - D-04 assumes "the normal phase-completion step ticks it". Measured in scratch, it does not, in either the current layout or the D-01 layout.
   - Moving the 29.x blocks inside `<details open>` (D-01 as written) has a second cost: `phase.complete` will also stop updating 29.7's `**Plans:**` line.
   - A template-conformant layout fixes all of this. In that layout the shipped `<details>` blocks come first, and v3.0 sits uncollapsed under a `### 🔄 v3.0 ...` heading after the last `</details>`. Measured in scratch, the tooling then ticks the checklist line, the Plans count, the plan line and the table row correctly.

The scratch-copy recipe for D-12 works. gsd-sdk resolves the project root to the start directory whenever that directory contains `.planning/`. The copy must therefore be named `.planning`, not `planning-copy` as CONTEXT suggests. Every mutator re-test in this session ran in a `mktemp -d` copy. The real `.planning/` was proven unchanged after every batch (`git status --porcelain` diff empty, `shasum -c` OK on ROADMAP.md and STATE.md).

**Primary recommendation:** Plan the phase as CONTEXT describes, with two operator rulings up front: (1) the D-05 comment placement (recommend form B) and (2) the ROADMAP layout (recommend the template-conformant layout, option C below). Use `roadmap.analyze` (read-only) as the structural oracle and `xcheck.sh` (below) as the 3-source oracle. Hand-set the STATE.md frontmatter progress block under D-02, because every state mutator silently rewrites it.

### Pattern 1: Scratch-copy recipe for mutating gsd-sdk handlers (D-12)

**How gsd-sdk finds `.planning/` (source-verified):**
- `gsd-sdk query` takes `--project-dir <dir>` from anywhere in argv (`sdk/dist/cli.js:24-37`; default `process.cwd()`).
- It then calls `findProjectRoot(projectDir)` (`sdk/dist/query/query-runtime-context.js:14`).
  - **If `<dir>/.planning` is a directory, `<dir>` is the root, and no walk-up happens** (`sdk/dist/query/helpers.js:484-489`).
  - Otherwise it walks up to 10 levels, stopping at `$HOME`. It picks a parent with `.planning/` when inside a git repo or when `config.json` names `sub_repos`/`multiRepo` (`helpers.js:514-566`).
- A workstream can re-route `.planning/` via `--ws` or the `GSD_WORKSTREAM` env var (`query-runtime-context.js:15-25`). Unset it.

### Anti-Patterns to Avoid
- **Trusting `updated`/`recorded` fields from state mutators.** `state.update-progress` returns `updated:false` and still rewrites STATE.md frontmatter (measured). Always diff the file.

- **Naming the scratch copy anything but `.planning`.** `findProjectRoot` would then walk up.

## Common Pitfalls

### Pitfall 1: D-05 trailing comment makes gsd-sdk read the key as a string
**What goes wrong.** gsd-sdk's frontmatter parser keeps the whole line, comment included. The commented forms that already exist show it:
- `gsd-sdk query frontmatter.get .planning/phases/24-*/24-10-SUMMARY.md requirements-completed` returns `{"requirements-completed": "[NEXUS-02, NEXUS-04]  # Marked only after git ls-tree origin/main evidence — see Task 3."}`.
- `summary-extract ... --fields requirements_completed --pick requirements_completed` returns `["[NEXUS-02,NEXUS-04]#Markedonlyafter..."]` (whitespace stripped by `tr` in this capture).
- An uncommented key (27-10) returns `["DDOJO-02"]`.

**Scratch test** (25-07 copy; the variant decides how `summary-extract` reads the key):

| Variant | `summary-extract` | yq `.[]` |
|---|---|---|
| A, the D-05 form: `requirements-completed: [NEXUS-05]  # backfilled ...` | `["[NEXUS-05]#backfilled..."]` (string) | `NEXUS-05` |
| **B: `# backfilled Phase 29.7 (v3.0 audit item 7); closure first recorded under provides` on the line above, then `requirements-completed: [NEXUS-05]`** | **`["NEXUS-05"]`** | **`NEXUS-05`** |
| C: no comment | `["NEXUS-05"]` | `NEXUS-05` |
| D: block list with item comment | `["NEXUS-05#backfilledPhase29.7"]` | — |

**How to avoid.** Use form B. It is the same text, so the retro note survives, and both parsers read the ID. This needs an operator ruling because D-05 is locked (Open Question 1).
**Warning sign.** The `summary-extract` readback returns an element that contains `#`.

### Pitfall 2: every STATE mutator silently rewrites the frontmatter progress block
**What goes wrong.** Measured in scratch on the current tree: `record-session` (both forms), `add-decision --summary`, `update-progress` (even when it reports `updated:false`) and `record-metric` (flag form) each rewrote:
- `status: ready_to_plan` → `planning`;
- `completed_plans: 133` → `75`.

None of them reported the change. After the 29.x blocks are moved (layouts B and C), the same rewrite yields `total_phases: 14, completed_phases: 13, total_plans: 133, completed_plans: 133, percent: 93`. These values are self-consistent but differ from the current hand-set `7/7/75/133/100`.

**Consequence.** The orchestrator's end-of-step `state.record-session --stopped-at ...` will rewrite these fields after this phase's plans run, whatever this phase hand-sets.

**How to avoid.** Under D-02, hand-set the STATE.md frontmatter `progress:` block to the post-move truth in the same plan as the ROADMAP move. After any orchestrator `record-session`, diff lines 1-15 of STATE.md, not just the body.

### Pitfall 3: the D-04 checklist tick will not happen automatically
See Pattern 3. In layouts A and B, `phase.complete 29.7` leaves `- [ ] **Phase 29.7: ...` unticked. This was measured on both. D-04 as written therefore needs either layout C or an amended close-out step (Open Question 2).

### Pitfall 4: tool-written dates and counts overwrite history
If anyone runs `roadmap.update-plan-progress <N>` or `phase.complete <N>` on an already-complete phase, it re-stamps the row with today's date. On the current layout, `phase.complete 29` also stamps 29.1's Plans line through a prefix match: `phase-lifecycle.js:901` lacks the `(?=[:\s])` lookahead that `roadmap-update-plan-progress.js:93` has. Never run either against the real ROADMAP in this phase.

### Pitfall 5: summary-tag consistency in layout B
Under layout B, the `<summary>` must keep the literal `v3.0`, with no further `<details>` nested inside, or `extractCurrentMilestone`'s fallback (`roadmap.js:~200-236`) falls through to `stripShippedMilestones` and drops the block. Changing "Phases 23-29" to e.g. "Phases 23-29.7" in the summary is safe.
