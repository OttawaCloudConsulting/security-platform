<objective>
Add the `doctor` subcommand and settle the exit-code contract for both `check` and `doctor`.

Purpose: MAINT-03 asks specifically whether every tool "is on PATH and can execute its version
command". The existing `get_installed_version` structurally cannot answer that — its `|| true`
discards the version command's exit status and collapses "the binary is broken" and "the output
format changed" into the single string `(unknown)`. `doctor` therefore needs its own code path, not
another column on `check`'s table. This also matches the ecosystem convention: `doctor` = "does my
environment work", `check`/`outdated` = "am I on the right version".

Output: `tool_health()`, `run_doctor()`, the `doctor` dispatcher branch, `PROBLEM_COUNT` wiring that
gives `check` and `doctor` real exit codes without breaking `update`'s, and offline tests using
symlink stubs.
</objective>

<planner_decisions>
Decision traceability for this plan:

- **D-02** (`check` already exists as `run_check` and substantially satisfies MAINT-01) — honoured:
  `run_check`'s table format is unchanged and `run_doctor` copies its shape rather than replacing it.
  The only change to `run_check` is `PROBLEM_COUNT` bookkeeping, which does not alter its output.
- **D-06** (the post-update recheck reuses `run_check`) — this plan must not break that reuse. It is
  the reason `run_check` increments `PROBLEM_COUNT` but never `FAIL_COUNT`: the `check)` branch maps
  the counter, the `update)` branch deliberately does not, so `update`'s exit status stays governed
  by D-08 alone.
- **D-08** (`update` exits non-zero only when a tool failed both attempts) — preserved by that same
  separation; a successful fallback showing as `MISMATCH` in the recheck must not flip `update` to 1.
- **D-01** (target path and subcommand style) — `doctor` is registered as a subcommand in the existing
  `install|configure|setup|check` dispatcher, never as a `--doctor` flag.

Resolutions of the open questions this plan implements. All four were explicitly left to the planner.

- **`doctor` is a distinct subcommand, not a column on `check`.** Justification is technical, not
  cosmetic: `get_installed_version` discards exactly the exit status MAINT-03 requires. Status
  vocabulary is `OK` / `NOT_ON_PATH` / `BROKEN` / `UNPARSEABLE`, deliberately different from
  `check`'s `ok` / `MISSING` / `MISMATCH`.
- **Open Q2 — exit contract.** `check` → 0 when every tool is `ok`, 1 when any is `MISSING` or
  `MISMATCH`. `doctor` → 0 when every tool is `OK`, 1 when any is `NOT_ON_PATH`, `BROKEN`, or
  `UNPARSEABLE`. `update` → unchanged from plan 04 (non-zero only on double failure). The mechanism
  is `PROBLEM_COUNT`: `run_check` and `run_doctor` increment it; the **dispatcher** decides whether to
  map it into `FAIL_COUNT`. The `check)` and `doctor)` branches map it; the `update)` branch does
  not. This is what prevents the post-update recheck from double-counting and from flipping a
  successful fallback into a failed run.
- **Pitfall 5 — `check` exports `$INSTALL_DIR` onto PATH; `doctor` does not.** Without the export,
  a user whose shell profile lacks `~/.local/bin` gets `check` → all MISSING → exit 1, while the
  identical machine inside `update`'s recheck (where PATH is already exported) shows all ok. Same
  tool, two answers — unacceptable once `check` has a real exit code. `check` answers "am I on the
  right version", so it should look where the tools are installed. `doctor` answers "does my
  environment work", so it must use the user's real PATH untouched — exporting there would mask the
  exact failure MAINT-03 exists to detect.
- **`check_prerequisites` is skipped for `doctor`.** It hard-`exit 1`s before the dispatcher when
  git, curl, or python3 is missing. A health-check command that dies without printing anything when
  python3 is absent is the opposite of what `doctor` is for. `doctor` reports prerequisite status in
  its own table instead.
</planner_decisions>

| user's `PATH` → `tool_health` | Binaries found on an attacker-influenced PATH are executed with `--version` |
| tool stdout/stderr → record parsing | Untrusted program output is parsed and echoed into a pipe-delimited record |
| command-line arguments → dispatcher | User-supplied tokens select the subcommand |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-07 | Spoofing / Elevation of Privilege | `tool_health` executing whatever `command -v` finds first on PATH | accept | MAINT-03 requires executing each tool's version command; the PATH searched is the user's own, and `doctor` deliberately does not prepend `$INSTALL_DIR`. Only `--version` / `version` is ever passed, never user-supplied arguments. Anyone who can plant a binary on the user's PATH already has code execution as that user, so this adds no new capability |
| T-13-18 | Tampering | tool output containing `\|` corrupting the `STATUS\|DETAIL\|VALUE` record | mitigate | The detail field is sanitised of `\|` before the record is echoed, and only the first line of output is carried. ASVS V5 |
| T-13-19 | Denial of Service | a broken binary aborting the health check under `set -euo pipefail` | mitigate | The version command is captured via an `if`/`\|\|` condition rather than a bare call; no `set +e` bracket is used; a test asserts the caller survives a `/usr/bin/false` stub |
| T-13-20 | Denial of Service | `check_prerequisites` aborting `doctor` before it reports | mitigate | The prerequisite gate is skipped for `doctor` only, which instead reports git/curl/python3 status in its own table and counts each missing one as a problem |
| T-13-21 | Information Disclosure | raw tool output echoed into the report | accept | Only the first line of a version command's output is shown, truncated; these tools emit version banners, not secrets. Showing the raw line is required so a changed output format is visible to a human (Pitfall 8) |
| T-13-05 | Denial of Service (self-inflicted) | GitHub rate limit | mitigate | `doctor` makes zero network calls: it does not call `ensure_versions_conf`, `resolve_latest_version`, or `gh_api_get`. Asserted by a grep criterion over the `run_doctor` body |
| T-13-08 | Elevation of Privilege | test stub creation | mitigate | Stubs are symlinks to existing system executables; no file gains an executable bit; asserted by both a `grep -rn chmod` and a `find -perm -u+x` criterion |
| T-13-SC | Tampering | npm/pip/cargo installs | accept | Phase installs no packages; this plan adds none |
