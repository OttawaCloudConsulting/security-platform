    **(a) Quick Start fenced block.** Add lines to the existing `# Or run individual steps:` block,

    - `bash setup.sh update` — update outdated tools to the pinned versions
    - `bash setup.sh update trivy` — update a single named tool
    - `bash setup.sh doctor` — verify every tool is on PATH and can run its version command
    Note that the tool name must come *after* the `update` keyword, because argument parsing is

    **(b) New "Maintenance" section**, placed immediately after "Version Management". It must cover,
    in prose a developer can act on:
    - **`check`** — prints installed vs expected versions plus prerequisites. Exits 0 when every tool
      matches its pin, 1 when any is missing or mismatched. It searches `~/.local/bin` in addition to
      the user's PATH, because it answers "am I on the right version", not "is my shell configured".
    - **`update`** — updates every tool whose installed version differs from its pin, or just the
      named tool. Tools already at their pin are skipped. A failing tool does not stop the others.
      For each tool it tries the exact pinned version first; if that fails it resolves the latest
      release within the same major version and tries that, and it refuses a fallback that would move
      the tool backwards. It never rewrites `versions.conf`. After the run it automatically re-prints
      the `check` table.
    - **The four result statuses** a user will see in the summary table: `ok` (already current),
      `installed` (updated to the pin), `fallback` (installed at a same-major version because the pin
      was unavailable — the follow-up table will show `MISMATCH` and a `NOTE:` line explains it), and
      `FAILED`.
    - **What to do about a `fallback`** — edit `versions.conf` to adopt the version that actually
      installed, then re-run. This is deliberately a manual step so the pinned manifest stays
      user-owned.
    - **`update-failures.log`** — written to the root of the repo `update` was run in, plain text,
      one line per tool that failed both attempts. Recommend adding it to that repo's `.gitignore`,
      and state that it contains only tool names and version strings — no credentials.
    - **Exit codes** — a small table: `check` 0/1 on version currency; `update` 0/1 on double failure
      only (a `fallback` is not a failure, and the automatic post-update recheck does not affect the
      status); `doctor` 0/1 on environment health.
    - **`doctor`** — reports per tool one of `OK`, `NOT_ON_PATH`, `BROKEN` (present but its version
      command failed), or `UNPARSEABLE` (ran but emitted no recognisable version), plus whether
      `~/.local/bin` is on PATH and whether git/curl/python3 are present. It uses the real PATH
      untouched, which is the point — and it makes no network calls at all.
    - **`GITHUB_TOKEN`** — set `GITHUB_TOKEN` or `GH_TOKEN` (or be logged in to `gh`) to raise the
      GitHub API limit from 60 to 5000 requests per hour. Explain when the script calls the API at
      all: generating `versions.conf` on first run, resolving hook versions, and the update fallback
      path. State that the token is sent as a request header and is never written to the failure log.

    **(c) "Version Management" subsection.** The existing "To update:" list offers only "delete

    `bash setup.sh update` as the third and now-preferred option, and cross-reference the new

    **(a) ARCHITECTURE.md — "Version Resolution" section.** Extend it to describe what now exists:
    - All GitHub API calls route through a single `gh_api_get` wrapper that adds an
      `X-GitHub-Api-Version` header and, when a token is available from `GITHUB_TOKEN`, `GH_TOKEN`, or
      `gh auth token`, an `Authorization: Bearer` header. The token is resolved lazily on first use
      and is never placed in a URL or written to any log.
    - JSON parsing is whitespace-tolerant because GitHub serves compact JSON for some repositories
      (hadolint) and spaced JSON for others (gitleaks). State this as the reason, so nobody
      "simplifies" the pattern back.
    - `resolve_latest_version` resolves the newest release for a repo; `resolve_latest_in_major`
      resolves the newest non-prerelease release within a given major version, using a strict
      `^major.N.N$` filter and a numeric field sort. Note that the strict filter is a security
      control: it is what prevents an arbitrary upstream tag string from reaching a download URL or a
      `pipx install` spec.
    - `resolve_latest_in_major` is called only on the update failure path, at most once per failed tool.

    **(b) ARCHITECTURE.md — "File Structure" section.** Add the `workstation/tests/` directory with
    its `run-tests.sh` runner, the `test_*.sh` case files, and `fixtures/` holding recorded GitHub
    JSON in both formatting styles. Note the runner glob-sources every `test_*.sh`, so adding a case
    file needs no runner edit.

    **(c) ARCHITECTURE.md — a short new `###` subsection under "Design Decisions"** covering the
    check/update/doctor split. Record three decisions with two or three sentences of rationale each:
    - `doctor` is separate from `check` because `get_installed_version` discards the version command's
      exit status, which is precisely what a health check must report; and because the ecosystem
      convention (`npm doctor`/`npm outdated`, `brew doctor`/`brew outdated`) maps cleanly onto
      "does my environment work" versus "am I on the right version".
    - Update success is determined by re-probing the installed version, never by the installer's exit
      code, because `pipx install` exits 0 while doing nothing when the package name is already present.
    - A successful same-major fallback is reported as its own status and does not rewrite
      `versions.conf`, keeping the pinned manifest an intentional, user-owned artifact.
