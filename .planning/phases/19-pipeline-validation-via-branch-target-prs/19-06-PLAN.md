<objective>
Open a second, separate pull request that changes nothing under `fixtures/` and observe all five scan jobs
conclude `success` — Success Criterion 4, and D-06.

Purpose: SC4 asks for "a clean pull request with no seeded findings passes all five jobs green". The phrase
that will mislead an executor is "no seeded findings". `fixtures/` is permanent and lives on `main`, so
every pull request in this repository checks out a tree full of deliberately vulnerable content and produces
findings in all five jobs, forever. A job is green only because report-only sets `continue-on-error: true`
on its scan step. D-06's "no seeded findings" therefore means "this PR seeds nothing new" — the clean branch
changes one inert, non-fixture file — and SC4's evidence is phrased as *five `security / …` check runs
concluded `success`*, never as zero findings.

Output: a second PR, its run's five green conclusions, an empty `gh variable list` read at run time, and the
non-zero finding counts recorded alongside the green verdict so nobody later reads "green" as "clean".

**What changed since this plan was first written.** It originally ran while PR #10 — the long-lived D-05
validation PR — was still open, and therefore predicted that a branch cut from `main` would carry NEITHER
`fixtures/vulnerable.py` NOR `fixtures/secret.env`. That is no longer the situation. On
2026-09-13T22:34:18Z the operator merged PR #10 through the GitHub web UI (merge commit `80e91de`), before
SC2 or SC4 were measured, and its head branch was auto-deleted. Both fixtures are now on `main`, so this
clean branch inherits all five seeded categories and the SAST and Secrets numbers this plan records are the
POST-merge ones: `semgrep-results.json` WILL carry `fixtures/vulnerable.py` results and
`gitleaks-results.json` WILL carry `fixtures/secret.env` findings, the latter because the `secrets` job runs
`gitleaks git .` with `fetch-depth: 0` — a history scan. RESEARCH Q3 recommended exactly this ordering (clean
PR after the fixtures reach `main`, so it shows the steady state); the project arrived at it by accident
rather than by reversing D-10, and the SUMMARY must say so in those terms.

Sequencing note: waves are strictly sequential. This plan runs while the REPLACEMENT validation PR opened by
plan 05 is still OPEN. That ordering is D-10's and is unchanged: a validation PR is merged or closed "once
all four success criteria are captured", and SC4 is one of the four, so it must be captured before plan 07
decides that PR's fate.
</objective>

<notes>
**Green does not mean clean, and the SUMMARY must not say it does.** Record the finding counts from this
run's artifacts alongside the five `success` conclusions. That contrast IS the point: the pipeline reports
findings and still lets the PR merge, because the repository is in report-only.

**This is the POST-merge clean-PR case.** Expect `fixtures/vulnerable.py` in the Semgrep results and
`fixtures/secret.env` in the Gitleaks results. If either is ABSENT, that is a finding worth stopping over —
it would mean the fixtures did not reach `main` or a scanner stopped seeing them — not a detail to smooth
over.

**Do not delete or modify anything under `fixtures/`.** A "clean" branch made by deleting fixtures would
destroy the permanent baseline every other criterion in this phase rests on. `fixtures/README.md` in
particular is mid-flight on plan 05's open PR.

**Verify `gh variable list` is empty AT RUN TIME.** Plan 05 deleted the variable, but SC4's evidence needs
the state during THIS run, not an inherited claim. If a `GATE_MODE` variable is present, STOP and report —
do not delete it silently and do not proceed with a contaminated measurement.

**Do not touch the replacement validation PR from plan 05.** It stays OPEN until plan 07.

**Close the clean PR at the end of this plan.** Its one-line README change is not wanted on `main`; it
exists only to give the pipeline a non-fixture diff to run against. Closing it is stated here so plan 07's
D-10 decision concerns the replacement validation PR only.

**Second-order effect to record, not to solve.** Because `fixtures/` is permanent, this repository cannot
itself adopt blocking mode live (Phase 18 D-07 step 3) without first excluding `fixtures/` from the
scanners. Report-only is currently the only state in which this repo's own PRs can merge green. That belongs
in the SUMMARY as an input to Phase 20, not as a problem for this plan to fix.

**`$SCRATCH` must be set inline in every command that uses it.** Shell state does NOT persist between
tool calls in this harness, so a `$SCRATCH` exported in one call is empty in the next. Prefix every
command and every verify invocation that references it with `SCRATCH=<absolute session scratchpad path>;`
in the SAME command. Use the scratchpad path from your own environment prompt — never `/tmp`, never a path
copied from this plan, and never anywhere inside either repository.
