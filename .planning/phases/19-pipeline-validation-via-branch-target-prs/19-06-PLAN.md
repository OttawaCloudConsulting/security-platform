<objective>
Open a second, separate pull request that changes nothing under `fixtures/` and observe all five scan jobs
conclude `success` — Success Criterion 4, and D-06.

Purpose: SC4 asks for "a clean pull request with no seeded findings passes all five jobs green". The phrase
that will mislead an executor is "no seeded findings". `fixtures/` is permanent and lives on `main`, so
every pull request in this repository checks out a tree full of deliberately vulnerable content and produces
findings in all five jobs, forever. A job is green only because report-only sets `continue-on-error: true`
on its scan step. D-06's "no seeded findings" therefore means "this PR seeds nothing new" — the clean branch
changes one inert, non-fixture file — and SC4's evidence is phrased as *five `security / …` check runs
concluded `success`*, never as zero findings.

Output: a second PR, its run's five green conclusions, an empty `gh variable list` read at run time, and the
non-zero finding counts recorded alongside the green verdict so nobody later reads "green" as "clean".

Sequencing note: waves are strictly sequential. This plan runs while the validation PR is still OPEN. That
ordering is deliberate and is D-10's: the validation PR is merged or closed "once all four success criteria
are captured", and SC4 is one of the four, so it must be captured first. RESEARCH Q3 recommended the
opposite order (clean PR after the fixtures merge, so it shows the steady state). That recommendation was
CONSIDERED AND REJECTED because D-10 is a locked decision and Q3 itself states either order satisfies SC4.
The consequence must be recorded: because the fixtures have not merged to `main` yet, this clean PR's
`gitleaks-results.json` will NOT contain `fixtures/secret.env` — its secrets findings come only from the
pre-existing history.
</objective>

findings and still lets the PR merge, because the repository is in report-only.

**Do not delete or modify anything under `fixtures/`.** A "clean" branch made by deleting fixtures would
destroy the permanent baseline every other criterion in this phase rests on.

the state during THIS run, not an inherited claim. If a `GATE_MODE` variable is present, STOP and report —
do not delete it silently and do not proceed with a contaminated measurement.

**Close the clean PR at the end of this plan.** Its one-line README change is not wanted on `main`; it
exists only to give the pipeline a non-fixture diff to run against. Closing it is stated here so plan 07's
D-10 decision concerns the validation PR only.

**Second-order effect to record, not to solve.** Because `fixtures/` is permanent, this repository cannot
itself adopt blocking mode live (Phase 18 D-07 step 3) without first excluding `fixtures/` from the
scanners. Report-only is currently the only state in which this repo's own PRs can merge green. That belongs
in the SUMMARY as an input to Phase 20, not as a problem for this plan to fix.
