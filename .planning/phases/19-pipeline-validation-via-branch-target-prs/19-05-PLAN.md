<objective>
Flip `GATE_MODE` to `blocking`, prove the SAME pull request now fails all five checks on a byte-identical
tree, delete the variable unconditionally, prove it passes again, and put the paired evidence in front of a
human.

Purpose: this is Success Criterion 2 — "that same pull request is observed failing its checks under blocking
mode and passing under report-only, both runs witnessed, not inferred". The only way to prove that the GATE
and nothing else changed the outcome is to change nothing else: the same commit content, an identical tree
hash, an empty `git diff`, and opposite verdicts. This plan also executes D-09: the repository is returned to
report-only before the phase closes, because Phase 18 D-07's rollout sequencing puts required-checks adoption
after blocking adoption, and that step is explicitly deferred past this phase.

Output: three runs on one identical tree, two opposite verdicts, a bounded and enumerated blast-radius
window, a repository with no `GATE_MODE` variable, and an operator confirmation.

Sequencing note: waves are strictly sequential. This plan produces the only two extra runs on the validation
PR; plan 03's and plan 04's evidence describes the first run and must not be re-derived from these.

<notes>
**DELETE THE VARIABLE UNCONDITIONALLY.** `gh variable delete GATE_MODE` runs whether the measurement
succeeded, failed, or was interrupted. A repository left in blocking is the worst possible outcome of a
half-finished plan — worse than no measurement at all. If anything goes wrong mid-task, delete the variable
FIRST, then report.

**Why the D-09 revert is NOT gated behind a checkpoint.** The planning guidance for this phase asks for
checkpoints on irreversible actions including the revert. The revert is handled differently, deliberately:
Task 1 is a blocking human checkpoint that AUTHORISES opening the window before it opens, and Task 3 is a
blocking human checkpoint that VERIFIES the repository was restored — but the `gh variable delete` itself
sits inside Task 2 with no gate in front of it, because a human gate between `set` and `delete` means an
unanswered prompt leaves a live repository gating every pull request. Task 3 is the D-09 checkpoint; it
confirms the restore rather than permitting it. No task boundary and no plan boundary may ever separate the
`set` from the `delete`.

**Five red checks are the SUCCESS condition of Task 2**, not a failure. What would be a failure: fewer than
five red, a job that died before its scan step, a missing artifact, or a missing SARIF category.

**Do not merge and do not touch the ruleset.** Plan 07 owns the PR's fate; required-checks adoption is
Phase 18 D-07 step 3 and is explicitly deferred past this phase (D-09).

**Do not edit any workflow file.** Editing one would destroy the entire argument — the point is that
nothing but a variable changed.

**Push with `--no-verify`.** The pre-push gitleaks hook still fires on the branch because `secret.env` is in
its history. Never add a `.gitleaksignore` fingerprint.
</notes>
