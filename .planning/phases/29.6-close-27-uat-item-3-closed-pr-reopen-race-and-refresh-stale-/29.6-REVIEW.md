see it. This is not evidence that the race was lost: every PR stayed BLOCKED. But it undercuts Decision 2, the
Consequences claim and the "sub-second window" framing. Several smaller factual inaccuracies follow.

## Critical Issues

### CR-01: Variant (b) evidence shows the close run's skipped check runs ending up newest for a red required context, and staying that way; the ADR omits this and draws conclusions that assume the opposite

**File:** `docs/adr/adr033-closed-pr-reopen-race-does-not-merge-on-skipped-checks.md:32, 61-63, 171-174, 210-215`

**Issue:** The ADR's Context (line 32) and 27-RESEARCH Pitfall 8 model the risk as a transient window. In that
model, the reopen run "supersedes" the close run's skipped runs once it queues. The cited evidence contradicts that
model for variant (b).

- `29.6-race-b1/checkruns-final.json`: close-suite Checkov `skipped` has id `113280955772`. The reopen-suite Checkov
  `failure` has id `113280907712`. Close-suite Gitleaks (`113280931996`) is also newer than its reopen counterpart.
- `29.6-race-b3/checkruns-final.json`: close-suite Semgrep `skipped` (`113287866366`) is newer than reopen Semgrep
  `failure` (`113287831272`). Container and Gitleaks are inverted too.
- `29.6-race-b2/checkruns-final.json`: SCA and Gitleaks are inverted (green contexts only).
- The `final` line of `29.6-race-b1/timeline.jsonl` (11:18:36Z) has `newest`, computed by the phase's own
  `_snap_newest` (`max_by(.id)`), as Checkov `skipped` from close suite `102319651891`. The `final` line of
  `29.6-race-b3/timeline.jsonl` (11:37:33Z) has Semgrep `skipped` from close suite `102325408925` as newest. Both are
  red contexts, and both final snapshots were taken minutes after the reopen run had completed.
- Each PR stayed `BLOCKED` only because the other red context's newest run was the reopen run's `failure`. The
  newest-by-id, most-recently-updated (29.6-RESEARCH Pitfall 8, Ken Muse) and all-must-pass rules all produce
  BLOCKED here, so this datum does not settle the tie-break.

The ADR uses none of this. As a result:
- Decision 2 ("not needed on this evidence") and Consequences lines 172-174 ("consistent with the measurement")
  are written as if the reopen run's check runs always end up newest.
- What-was-NOT-verified item 5 frames the remaining risk as a "sub-second window", but the observed inversion is
  persistent.
- Item 6 says the server-side outcomes are "consistent with the newest run per context being judged", without
  noting that under newest-by-id a head red on a single context, with b1-like ordering, would read passing after the
  reopen run completes. No attempt tested that configuration. Every red head had two red contexts (D-18 red set).

The ADR is the record that resolves ADR-024 item 2, so this omission ships an unsupported "resolved" claim.

**Fix:** Additive text only. Do not propose a workflow change; that is an operator ruling under D-11.
1. In "Measured evidence", add a paragraph:

   ```markdown
   **Check-run ordering under variant (b).** In b1, b2 and b3 some close-suite `skipped` check runs were created
   after the reopen suite's check runs for the same context (higher check-run id). At each attempt's `final`
   snapshot, the newest-by-id run (`29.6-snap.sh` `max_by(.id)`) for a red required context was the close run's
   `skipped` one: b1 IaC — Checkov (113280955772 > 113280907712), b3 SAST — Semgrep CE (113287866366 >
   113287831272). These persisted after the reopen run completed. Each PR stayed BLOCKED because its other red
   context's newest run was the reopen run's `failure`. Under any of the candidate tie-break rules the outcome is
   BLOCKED, so this does not discriminate them.
   ```
2. Scope Decision 2 and Consequences to what was measured. For example: "no change on the variant (a) server-side
   evidence; the variant (b) ordering inversion is recorded as an open risk and not ruled on".
3. Rewrite item 5 so it does not call the risk sub-second. Add a NOT-verified item: "A red head with exactly one
   red required context, under an ordering where that context's close-suite `skipped` run ends up newest, was not
   exercised. Its mergeability after the reopen run completes depends on the unresolved tie-break rule (item 6)."
4. Because the ADR's decision changes, bring the ruling back to the operator, since the D-11 gate ruling was given
   without this datum.

## Warnings

### WR-01: What-was-NOT-verified item 4 says the evidence cannot settle this, but it can

**File:** `docs/adr/adr033-closed-pr-reopen-race-does-not-merge-on-skipped-checks.md:205-209` (and line 67)

**Issue:** Item 4 says that at second resolution "it cannot be determined whether those skipped runs existed on the
head SHA when `gh pr merge` fired". It relies only on `completed_at`. But each attempt's `post-merge` snapshot in
`timeline.jsonl` was taken about 0.2 s after `t_merge_end`, and it lists every check run on the head SHA:
- b1 (11:09:21.044Z): only 3 of the 5 close-suite skipped runs exist. Checkov (red) and Gitleaks are absent.
- b3 (11:28:22.075Z): only Checkov and SCA exist. Semgrep (red), Container and Gitleaks are absent.
- b2 (11:18:51.639Z): Container, Semgrep and Checkov exist. SCA and Gitleaks are absent.

A run that is absent after the merge was also absent while the merge ran. So in b1 and b3 the Pitfall 8 window was
demonstrably not open for at least one red context. The red head's `failure` or the reopen run's queued run was the
newest for that context. Also, at every b post-merge snapshot the newest-by-id run for all five contexts was the
reopen suite's queued run. Variant (b) therefore probably never hit the Pitfall 8 window at all. Line 67's "six
attempts across two timings" overstates how much variant (b) tells us about Pitfall 8.

**Fix:** Replace item 4's last sentence with the measured result: "At the post-merge snapshot (about 0.2 s after
the merge ended), the close-suite skipped run for a red context was still absent in b1 (Checkov) and b3 (Semgrep),
so the window was not open for those contexts. Only b2 is undetermined." Qualify line 67 to say that only the
variant (a) attempts are known to have run inside the window.

### WR-02: Variant (b) is described as having no pre-merge read; the evidence shows it had the same read as (a)

**File:** `docs/adr/adr033-closed-pr-reopen-race-does-not-merge-on-skipped-checks.md:105, 165-167`

**Issue:** Line 105 ("Close, reopen and merge back to back with no wait") and lines 165-167 ("show the server path
only under variant (a) timing (reopen, then a pre-merge read, then merge)") imply that variant (b) skipped the
pre-merge read and merged faster after the reopen. Every b `meta.json` has `t_premerge_read` and
`t_premerge_read_end`. Reopen-to-merge timings:
- variant (b): b1 2.83 s, b2 2.90 s, b3 2.68 s;
- variant (a): a1 2.98 s, a2 2.81 s, a3 2.82 s.

The only difference between the variants is the close-to-reopen gap: about 1.4 to 1.6 s in (b) against about 15 to
18 s in (a). The "(reopen, then a pre-merge read, then merge)" gloss comes from the ADR-033 caveat in
`29.6-10-d11-gate.txt`, which the ADR was told to carry "verbatim in substance". 27-HUMAN-UAT item 3,
27-VERIFICATION row 3 and v3.0 audit item 6 carry only the label "variant (a) timing", without the gloss. That label
is accurate, because it means the attempts that waited for the close run.

**Fix:** In the ADR, say that both variants ran reopen → pre-merge read → merge with the same ~2.7-3.0 s
reopen-to-merge interval, and that variant (b) differs only in not waiting for the close run before reopening.
Note in the ADR that the D-11 gate's gloss was imprecise. The three planning records need no change.

### WR-03: A wrong measured timing in a record that says every value is quoted

**File:** `docs/adr/adr033-closed-pr-reopen-race-does-not-merge-on-skipped-checks.md:144-145`

**Issue:** The ADR says "about 3 to 4 s after the reopen started". From the `meta.json` files, `t_merge_start -
t_reopen_start` is a1 2.977 s, a2 2.806 s and a3 2.820 s. All three are under 3 s, and none is near 4 s. Line 8
promises that every measured value is quoted from evidence.

**Fix:** "about 2.8 to 3.0 s after the reopen started (a1 2.98 s, a2 2.81 s, a3 2.82 s)".

### WR-04: The title states a universal claim that the body disclaims

**File:** `docs/adr/adr033-closed-pr-reopen-race-does-not-merge-on-skipped-checks.md:1` and `docs/adr/README.md:43`

**Issue:** "A Closed-Then-Reopened Pull Request Is Not Merged on Its Close Run's Skipped Checks" reads as a general
property of GitHub. The body says six finite attempts do not prove impossibility (lines 70-71, 176-179), that
variant (b) never reached the server, and (per CR-01) the evidence contains an unrecorded ordering in which the
close run's skipped run is newest for a red context. Neighbouring ADRs (ADR-031, ADR-032) also use declarative
titles, but theirs state a configuration choice, not an empirical impossibility.

**Fix:** Scope the title to what was measured, for example "A Closed-Then-Reopened Red Pull Request Was Refused in
Six Race Attempts", and update the README row to match.
