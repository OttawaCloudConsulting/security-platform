#### Race procedure
- **D-07:** Drive the sequence with a **scripted tight loop**, a phase-local script run with `bash`. The script runs `gh pr close`, then `gh pr reopen`, then `gh pr merge`, back to back. At each step it logs an ISO timestamp, `mergeStateStatus`/`mergeable`, and the check runs on the head SHA (name, status, conclusion, run id). Do not drive it manually through the UI.
- **D-08:** Run **two variants**:
  - **(a) The Pitfall 8 window.** Close the PR, wait until the close run has completed and its skipped check runs exist on the head SHA, then reopen and merge immediately.
  - **(b) The UAT literal.** Close, reopen and merge with no wait.
- **D-09:** Make **3 attempts per variant**. **Stop at the first reproduction**, because one accepted merge proves the gap. A successful merge consumes the PR, so each attempt needs its own fresh PR and branch.
- **D-10:** The verdict is defined as follows.
  - **Race lost (gap proven):** `gh pr merge` succeeds while any of the five required contexts **from the reopen run** is queued, in progress, or missing on the head SHA.
  - **Blocked:** the merge is refused until the reopen run's five contexts complete.
  - Both outcomes are captured as evidence: the check-runs JSON plus the merge command's exit code and stderr. A red check is **not** required to call the race lost.

The phase has two halves of very different risk. The records half (items 1–2, the 27-VERIFICATION note, the audit line, the ADR index) is low risk. The homelab readback can use the existing GET-only `defectdojo-lifecycle-assert.sh snapshot` subcommand [VERIFIED: source read, origin/main].

The live-race half has three findings the planner must absorb before writing tasks.

1. **`OttawaCloudConsulting` is a User account, not an organization.** `gh api orgs/OttawaCloudConsulting` returns 404, `users/OttawaCloudConsulting` has `type: User`, and adoption-guide §11 already says so. The token has no `read:user` scope, so `plan` reads `null`. Two private repos return `200 []` on `rules/branches/main` and `404 Branch not protected` on classic protection. A Free private repo returns `403 "Upgrade to GitHub Pro…"` instead, so the account is probably on Pro or above (MEDIUM). GitHub's docs say Free private repos do not get rulesets, and a third-party issue reports that Free stores but does not enforce them. D-04's live proof is therefore mandatory, not ceremonial.
2. **The race test cannot discriminate if the head SHA was green before the close.** On PR #21's head `7c47270` every context has a `success` run (opened) and a newer `skipped` run (closed), and GitHub treats both as passing. A merge accepted right after reopen on a previously green SHA is ordinary GitHub behaviour: it would meet D-10's "lost" wording and trigger the D-11 stop without proving Pitfall 8. The configuration that does discriminate is a head SHA whose last real scan was **red** (`GATE_MODE=blocking` plus a deterministic finding). In that state an accepted merge means `skipped` overrode `failure`. **This needs operator confirmation (Open Question 1).**
3. **Timestamps are unreliable for ordering check runs.** On close run 36158851741 the run reported `completed` at 16:08:38 while its check runs carry `started_at` as late as 16:08:44, and skipped runs have `completed_at` *earlier* than `started_at`. `?filter=latest` returned both suites' runs. The script must order by check-run `id` and attribute each run to the close or reopen run by `check_suite.id`.

**Primary recommendation:** create a private User-owned throwaway repo with a Mode B caller and a one-file Dockerfile. Prove enforcement with ADR-019's `UNSTABLE`→`BLOCKED`→`CLEAN` sequence on one PR. Then run the race attempts with `GATE_MODE=blocking` and a red head SHA, using an operator-run `bash` script that logs per-name newest-by-`id` check runs with `check_suite_id`, `mergeStateStatus` before and after, and the merge exit code with verbatim stderr.

### Pattern 3: Ruleset write (create, then read-modify-write)
`set-required-checks.sh` accepts `--repo OWNER/REPO` and `--ruleset ID` but is **PUT-only**: it GETs `rulesets/{id}` and needs a `rules` key. adoption-guide §8 states plainly that the script does not implement the create path [VERIFIED: source and guide read]. Two steps follow.

1. **POST** a `Default` ruleset that mirrors `security-platform`'s live shape [VERIFIED: `gh api …/rulesets/14243983`]:
```bash
gh api --method POST repos/OttawaCloudConsulting/<scratch>/rulesets --input - <<'JSON'
{"name":"Default","target":"branch","enforcement":"active",
 "conditions":{"ref_name":{"include":["~DEFAULT_BRANCH"],"exclude":[]}},
 "bypass_actors":[],
 "rules":[{"type":"deletion"},{"type":"non_fast_forward"}]}
JSON
```
2. Run the script from the local `repos/security-platform` checkout, which is byte-identical to origin/main for this file:
```bash
bash scripts/set-required-checks.sh --repo OttawaCloudConsulting/<scratch> --ruleset <id> \
  --out <phase>/evidence/29.6-03-ruleset-merged.json                      # dry run first
bash scripts/set-required-checks.sh --repo OttawaCloudConsulting/<scratch> --ruleset <id> \
  --out <phase>/evidence/29.6-03-ruleset-merged.json \
  --verify-sha <head SHA of a report-only PR run with all five present> \
  --apply --yes-i-understand-lockout
```
The script adds `required_status_checks` (five contexts, `integration_id: 15368`, `strict_required_status_checks_policy: false`, `do_not_enforce_on_create: false`) and a `pull_request` rule (0 approvals). It carries `bypass_actors` forward, and reads back from `rules/branches/main`. Its lockout banner is hard-coded to talk about `security-platform`. That text is harmless here, but say so in the plan so the operator is not confused.
- `strict=false` matters: later attempts never go `BEHIND` after an earlier PR merges.
- Read `current_user_can_bypass` before the write, at the enforcement proof, and after each race attempt (`gh api repos/O/R/rulesets/<id> --jq .current_user_can_bypass`). It must read `"never"`. If it is anything else, an accepted merge could be a bypass. A User-account owner is still bound by a ruleset with `bypass_actors: []` (ADR-019 measured `"never"` on a User-owned repo) [VERIFIED: ADR-019].
- **Lockout escape is clear (D-05):** a ruleset does not gate its own administration. The owner can `PUT` `enforcement: "disabled"`, `DELETE repos/O/R/rulesets/<id>`, or delete the repo (D-06). Every merge does not need to stay possible: the repo is disposable and the cleanup path never runs through a merge.

### Pattern 4: Enforcement proof (D-04/D-05), the ADR-019 shape on one PR
1. PR-0 opened with `GATE_MODE` unset (report-only) → five `success`. Read context names live: `gh api repos/O/R/commits/$SHA/check-runs --jq '.check_runs[]|select(.app.id==15368)|.name'`. Save this as the D-01 source and dump codepoints to prove U+2014.
2. `gh variable set GATE_MODE --body blocking -R O/R`, then push an empty commit to PR-0 (`git commit --allow-empty`) → Checkov (and possibly others) red → `mergeStateStatus: UNSTABLE` (nothing required yet).
3. Create the ruleset and apply the contexts (Pattern 3), using `--verify-sha` = the step-1 SHA. Re-read the **same head SHA** → `BLOCKED`. Attempt `gh pr merge <n> --squash` → expect exit 1 and *"…is not mergeable: the base branch policy prohibits the merge."* (ADR-019 verbatim). This is gh's **client-side** decline (see Pattern 6).
4. Attribution: with the contexts still required, make the tree green. Either remove the finding (add `USER`/`HEALTHCHECK`) or unset `GATE_MODE` and push an empty commit → `CLEAN`. That proves `BLOCKED` came from the red required check, not from the `pull_request` rule.
5. Optional but cheap: a **server-side** refusal. While `BLOCKED`, `gh api -X PUT repos/O/R/pulls/<n>/merge -f merge_method=squash` should return HTTP 405 with a rule-violation message. ADR-019 NOT-verified item 2 left this open. It risks an accidental merge only if enforcement is broken, and that is exactly what it tests. Recommended, gated by the operator.

If step 3 does not produce `BLOCKED`, rulesets are not enforced on this private repo. Then fall back to **public** per D-04, record why, and redo steps 1–4.

### Pattern 5: Race attempt (D-07/D-08/D-09), red head SHA recommended (see Open Question 1)
Per attempt, using a fresh branch and PR from `main`, each touching a distinct file to avoid conflicts:
1. `GATE_MODE=blocking` stays set. Open PR-k with the finding still present (the Dockerfile on `main` already lacks USER/HEALTHCHECK, so any PR inherits the red). Wait until the opened run's five check runs complete with ≥1 `failure` and `mergeStateStatus == BLOCKED`. Snapshot.
2. `gh pr close <n>`. Log the timestamp.
3. **Variant (a):** poll every 2 s (cap 120 s) until the "close-run-complete" detector below is true, then go to 4 with no delay. **Variant (b):** go to 4 immediately.
4. `gh pr reopen <n>`, then immediately `gh pr merge <n> --squash`. Never `--admin`, `--auto` or `--delete-branch`. Capture rc, stdout and stderr verbatim.
5. Log snapshots before reopen, between reopen and merge, right after the merge, then every 3 s until the reopen run's five check runs are `completed` (or 180 s).

Close-run-complete detector (variant a). Do not gate on `gh run view` status alone: run 36158851741 reported `completed` 6 s before its last check run's `started_at`.
```bash
# the close run: newest pull_request run on this head SHA created at/after the close timestamp
gh api "repos/$R/actions/runs?event=pull_request&head_sha=$SHA&per_page=20" \
  --jq "[.workflow_runs[]|select(.created_at >= \"$T_CLOSE\")]|sort_by(.id)|last|{id,status,conclusion,check_suite_id}"

  [.check_runs[]|select(.app.id==15368)]|group_by(.name)|map(max_by(.id))
  |map({name,id,status,conclusion,suite:.check_suite.id,started_at,completed_at,html_url})'
```

Per-step snapshot (the D-07 log line). Write one JSON object per line:
```bash
snap() { # $1 = label
  jq -cn --arg label "$1" --arg ts "$(date -u +%Y-%m-%dT%H:%M:%S.%3NZ 2>/dev/null || date -u +%FT%TZ)" \
    --argjson pr "$(gh pr view "$PR" -R "$R" --json state,mergeStateStatus,mergeable,headRefOid)" \
    --argjson cr "$(gh api "repos/$R/commits/$SHA/check-runs?filter=all&per_page=100" \
        --jq '[.check_runs[]|select(.app.id==15368)|{name,id,status,conclusion,suite:.check_suite.id,run:(.details_url|capture("runs/(?<r>[0-9]+)").r)}]')" \
    '{label:$label, ts:$ts, pr:$pr, check_runs:$cr}'
}
```
On macOS, BSD `date` has no `%3N`, and the `||` fallback drops milliseconds. Use `python3 -c 'import datetime;print(datetime.datetime.now(datetime.timezone.utc).isoformat())'` if sub-second ordering matters. It does matter for variant (b).

Each `snap` costs 2 API calls and about 1–2 s. Do **not** call `snap` between reopen and merge in variant (b), because it widens the window you are trying to hit. Take the full snap only after the merge returns. Record just `date` timestamps around the two commands.

### Pattern 6: What `gh pr merge` does client-side (read from gh source)
`pkg/cmd/pr/merge/merge.go` `blockedReason()` returns a refusal only for `BLOCKED` ("the base branch policy prohibits the merge"), `BEHIND`, and `DIRTY`. `isImmediatelyMergeable()` treats `CLEAN`/`HAS_HOOKS`/`UNSTABLE` as mergeable. For any other status (including `UNKNOWN`, likely right after reopen) gh sends the merge mutation and **the server decides** [VERIFIED: github.com/cli/cli source via gh api, 2026-10-05]. Consequences:
- A "base branch policy prohibits" refusal means gh read `BLOCKED` and never asked the server. Record it as a **client-side** block (ADR-019 nuance).
- An error carrying a GraphQL/HTTP message (for example a repository rule violation or "required status check … expected") is a **server-side** block. That is the stronger evidence.
- The race verdict must name which one happened. If every refusal is client-side, the ADR must say the server path was not reached.

### Anti-Patterns to Avoid
- **Ordering check runs by `started_at`/`completed_at`.** Skipped runs have `completed_at < started_at`. Use `id`.
- **Trusting `?filter=latest`.** It returned the success and skipped runs from both suites on `7c47270`. It is per-suite, not per-name. Use `filter=all` and group in jq.
- **Reading classic `branches/main/protection`** as evidence. It 404s by design on a ruleset-governed repo. Read `rules/branches/main`.
- **Adding any bypass actor "for safety".** That makes an accepted merge uninterpretable. The escape path is ruleset disable/delete, not bypass.
- **Seeding a fake secret for a red Gitleaks check.** Push protection or GitGuardian side effects.
- **Running the race from the planning repo**, or any `git push` from it.
- **Letting `snap` run between reopen and merge in variant (b).**

## Common Pitfalls

### Pitfall 1: Green-prior false positive (critical)
**What goes wrong:** with the head SHA already `success`, an accepted merge right after reopen looks like "race lost" (D-10) but is normal behaviour. GitHub counts `success`, `skipped` and `neutral` as passing [CITED: docs.github.com/…/troubleshooting-required-status-checks].
**Avoid:** run the race on a **red** head SHA (Open Question 1). Then an accepted merge can only mean the newer `skipped` satisfied a context whose real scan failed.
**Warning sign:** `mergeStateStatus` before close is `CLEAN`/`UNSTABLE`. It should be `BLOCKED`.

### Pitfall 2: Unenforced ruleset on a private repo
**What goes wrong:** GitHub accepts and stores the ruleset, but the plan does not enforce it. Every merge succeeds, and that reads as "race lost".
**Avoid:** the Pattern 4 `UNSTABLE`→`BLOCKED`→`CLEAN` proof before any race attempt. On failure, go public (D-04).

### Pitfall 3: Close run "completed" before its check runs exist
**Avoid:** use the detector in Pattern 5 (five names, newest-by-id = `skipped`, suite = close run's suite).

### Pitfall 4: Interleaved suites in variant (b)
Close-run and reopen-run check runs can land within the same ~10 s, in any per-name order. The verdict needs, for every context at merge time, whether the newest-by-id run belongs to the reopen suite. Reconstruct this from the `id`s. The final `filter=all` dump after the merge has every id, so ordering is recoverable even if the live snap was skipped.

### Pitfall 5: Agent cannot run the writes
ADR-019 recorded the auto-mode classifier denying `gh pr create`, `POST …/pulls`, `gh variable set`, `gh pr merge`, and the `git push`. **Plan every write as an operator step** (`checkpoint:human-action`), and have the agent do the read-only verification afterwards. The race script is operator-run by design.

### Pitfall 6: Token scope gaps
The scopes are `gist, read:org, repo, workflow` [VERIFIED: `gh auth status`]. **No `delete_repo`** means D-06 needs `gh auth refresh -h github.com -s delete_repo` or the web UI. **No `read:user`/`user`** means `plan` is `null`. To record the plan: `gh auth refresh -s read:user` then `gh api user --jq .plan.name`.

### Pitfall 7: `v1` moves mid-phase
Record `git ls-remote https://github.com/OttawaCloudConsulting/security-platform.git refs/tags/v1 'refs/tags/v1.4.0^{}'` at the start and end of the live window, and assert they are equal. A Mode B run's resolved callee SHA can also be read from the run (`gh api …/actions/runs/<id> --jq .referenced_workflows`) [ASSUMED: field name per REST docs; verify in the first run].

### Pitfall 8: GitHub's tie-break rule is undocumented
The official docs say only that checks must pass on the latest commit and that a check plus a status with the same name must both pass. A secondary source (Ken Muse) says "only the most recently updated one will be used". Another secondary claim says all same-named checks must pass. The evidence is LOW and contradictory. **Write ADR-033 from what is measured, not from either claim.**

### Pitfall 9: Actions minutes on private
Each attempt is about three runs of five jobs, roughly 1 minute each, on private-repo minutes. Expect about 100–150 minutes across six attempts plus the proof. That fits Pro's 3,000 [ASSUMED: Pro quota]. On a public fallback, minutes are free.

## Open Questions

1. **Prior state of the head SHA for the race attempts (needs operator confirmation, because it reshapes the procedure).**
   - What we know: on a green head SHA, an accepted post-reopen merge is indistinguishable from normal behaviour and would trigger D-11 for a non-gap. D-10 does not forbid a red precondition, and D-05 already enables blocking.
   - Recommendation: run all six attempts with `GATE_MODE=blocking` and a red head SHA. Optionally, if the operator wants the literal "green" UAT wording too, run one extra variant-(b) attempt on a green SHA labelled in advance as non-discriminating, and exclude it from the D-11 stop. The planner should put this in a `checkpoint:decision` before the first race attempt, or the discuss step should amend D-10.
2. **Client-side vs server-side refusal.** If every "blocked" is gh's local `BLOCKED` decline, the server rule was never exercised in the race window. Recommendation: record which path occurred per attempt. Optionally, for one variant-(a) attempt, use `gh api -X PUT …/pulls/<n>/merge` instead of `gh pr merge` to hit the server directly. That deviates from D-07's literal command, so it needs operator approval.
3. **Plan name.** Operator may run `gh auth refresh -s read:user && gh api user --jq .plan.name` to record it. That is not required, because the live proof is the authority.
4. **Public fallback consequences.** A public scratch repo gets code scanning: SARIF verify steps run and analyses land. Jobs should still be green. Note this in the ADR if the fallback is used.
