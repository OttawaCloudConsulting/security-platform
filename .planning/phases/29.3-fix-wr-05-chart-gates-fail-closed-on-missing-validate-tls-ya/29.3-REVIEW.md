## Summary

Scope: the security-platform phase diff `72cb174..36100a1` (new `.github/workflows/chart-gates.yml`, the guard and hint changes in both gate scripts, and the Nexus README install step), plus ADR-030 and its index row in this repository. Intent was checked against 29.3-CONTEXT decisions D-01..D-24.

The script changes are correct and small. Both guards now print `FAIL: <LABEL>: ` and exit 1 before preflight. The labels in the scripts, the workflow header, the job `env:` literals and ADR-030 all match. The preflight hint reads its values from `Chart.yaml` and each `yq` read is guarded. The workflow does what D-07..D-22 specify. The mode is validated before the gate runs. Gate output is fenced by a random `stop-commands` token. Annotation data is escaped for `%` and `\r`. No `${{ }}` expression appears inside a `run:` body. The negative cases run on a `cp -a` copy of the checkout.

I found no BLOCKER. The defects are in how the workflow buckets outcomes, at the edges D-13 and D-22 leave loose, and in one ADR claim that its own Tradeoffs section contradicts:

- **WR-01:** the D-22 skip trusts the label text and ignores the positive run's exit code. A PR can therefore delete a guard template and still get a fully green job in `blocking` mode.
- **WR-02:** any exit 1 counts as a chart defect, even with no `FAIL:` line. A script abort is then only a warning in `report-only`.
- **WR-03:** ADR-030's "Improved" consequence says something the default configuration does not do.

Two operator-accepted tradeoffs are not re-raised as findings: report-only is the default (D-11), and a vacuous pass lands in the chart-defect bucket (29.3-CONTEXT specifics).

## Warnings

### WR-01: D-22 negative-case skip trusts the label text, not the positive run's exit code

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:270-287` (identical at `484-501`)
**Issue:** When a case's precondition is absent, the negative step skips with a `::notice` if `$pos` contains `^FAIL: <label>: ` anywhere. The step never checks that the positive gate run exited 1. Lines 210-213 classify PASS as exit 0 with a last line starting `PASS -`, and they do not check for `FAIL:` lines. Consider a PR that deletes `templates/validate-tls.yaml` and edits the script so it prints the label and still reaches the terminal `PASS -` line. Removing the `exit 1` from Guard 2 is not enough for this. With the template gone, `ISSUER-REQUIRED` (line 166) and the other checks that depend on the template also fail, and the script exits 1 through `FAILED - N check(s)`. Those checks have to be disabled too. The gate step then reports PASS. Negative case (a) finds the template absent and the label present, so it skips. The job is green in **every** mode, `blocking` included. ADR-030 decision 8 and the header (lines 46-51) say the negative cases make a regression on the guarded conditions "always red". In this path they do not.

On real risk: the PR can also edit `chart-gates.yml` itself, because `pull_request` runs the PR's workflow file. So this is not a security boundary. It is a hole in the stated invariant, and closing it costs a few lines.
**Fix:** In the gate step, write `rc` next to the output file, and require it in the D-22 skip:
```bash
# gate step, after the gate runs:
printf '%s\n' "$rc" > "${RUNNER_TEMP}/chart-gate-${CHART}.rc"
# negative step, D-22 branch:
pos_rc="$(cat "${RUNNER_TEMP}/chart-gate-${CHART}.rc" 2>/dev/null || echo missing)"
if [ "$pos_rc" = 1 ] && [ -f "$pos" ] && grep -q "^FAIL: ${label}: " "$pos"; then
```
Also consider treating "exit 0 with a terminal `PASS -` line but any `^FAIL:` line in the output" as the chart-defect bucket, not as PASS.

### WR-02: Any exit 1 counts as a chart defect, even with no FAIL line

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:216` (identical at `430`)
**Issue:** Both gates run under `set -euo pipefail`. An unguarded command failure, an unbound variable, or a bare `exit 1` added in a later edit ends the script with status 1 and prints no `FAIL:` line. The `FAILURES` array is printed only at the foot of the script, so an abort before then prints none. The workflow puts every `rc=1` in the chart-defect bucket. In the default `report-only` mode the job is then green, with one generic warning ("chart defect (exit 1)") and the last five output lines in the summary. That is the "gate never really ran" outcome that D-13 means to keep always red (exit 2, or any other code). It reaches the warning bucket only because the abort happens to use code 1.

I grepped both scripts and found no unguarded `$(helm|yq|jq ...)` call site at HEAD (the call sites use `if !`, `elif !` or `|| x_rc=$?`). So this is a latent gap that a future edit would open, not a failure you can trigger today.
**Fix:** A genuine chart defect always prints at least one `^FAIL: ` line, followed either by `FAILED - N check(s)` or by one of the guard labels. Require that:
```bash
1)
  if grep -q '^FAIL: ' "$out"; then
    why="chart defect (exit 1)"
  else
    echo "::error::check-${CHART}-chart.sh exited 1 without any FAIL: line (aborted, not a chart verdict)"; exit 1
  fi ;;
```

### WR-03: ADR-030's "Improved" consequence contradicts its own deletion tradeoff

**File:** `docs/adr/adr030-standing-chart-gates-fail-closed-and-run-in-ci.md:193-195`
**Issue:** The first consequence says "deleting or renaming a chart, `validate-tls.yaml` or `job-provision.yaml` can no longer pass a chart gate." Lines 200-203 of the same ADR say that in the default `report-only` mode such a PR "gets a `::warning` ... and the job stays green". Evidence 29.3-06 confirms `CHART_GATE_MODE` is not set. In the shipped configuration, then, the CI check for exactly the WR-05 scenario is green. Only the script fails. Since the check is also not required (D-10), nothing stops the merge. A reader who stops at "Improved" will think WR-05 is closed in CI when it is closed only at the script level. Because ADRs are append-only, this wording becomes permanent once accepted (it is already marked Accepted).
**Fix:** `docs/adr/` is append-only (CLAUDE.md), and this record is Accepted. Record the correction in the next ADR or addendum that touches chart gates, scoping the claim like this: "deleting or renaming a chart, `validate-tls.yaml` or `job-provision.yaml` now makes the gate script exit 1 with a named label; the CI job is red for it only when `CHART_GATE_MODE=blocking`." Reword lines 193-195 in place only if the orchestrator decides that ADR-030 is still open for edits within this phase.

## Info

### IN-01: Chart.yaml-derived strings can issue workflow commands in the `deps` step

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:175-184` (identical at `389-398`)
**Issue:** `name` and `repo` come from PR-controlled `Chart.yaml` through `yq -r`. They are echoed inside `::error::` on line 179, and `helm repo add` / `helm dependency build` echo them in their own output. None of this sits inside a `stop-commands` fence, and the values are not escaped. A YAML string with an embedded newline (`"https://x\n::add-mask::..."`) passes the `https://*` case and can emit workflow commands. The impact is low: the token is read-only, there are no secrets, and the PR controls the workflow file anyway. Still, it breaks the header's stance that untrusted text cannot issue commands (lines 188-189, 81-82).
**Fix:** Reject values that contain control characters before use (`case "$name$repo" in *[[:cntrl:]]*) ...exit 1;; esac`), and wrap the step's helm output in the same random `stop-commands` token pair the gate step uses.

### IN-02: Preflight hint prints `helm repo add null null` when `.dependencies` is missing

**File:** `repos/security-platform/scripts/check-defectdojo-chart.sh:96-104`, `repos/security-platform/scripts/check-nexus-chart.sh:82-91`
**Issue:** `yq -r '.dependencies[0].name'` returns the string `null` with exit 0 when the key is absent. The guarded reads therefore pass, and the hint prints `run: helm repo add null null && helm dependency build ...`, which does not work. The values are also interpolated unquoted into a line meant to be copied and pasted. In the DefectDojo gate, `DEP_VERSION` is read with plain `yq` plus manual quote stripping (line 86), while the new reads use `yq -r`, so the two reads are inconsistent.
**Fix:** Treat `null` or an empty value as a preflight failure, e.g. `[ -n "$DEP_NAME" ] && [ "$DEP_NAME" != null ] || { echo "PREFLIGHT FAIL: Chart.yaml has no .dependencies[0].name"; exit 2; }`, and use `yq -r` for `DEP_VERSION` too.

### IN-03: Byte-identity of the two jobs' step bodies is enforced only outside CI

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:62-66`
**Issue:** The header relies on the two jobs' step bodies staying byte-identical (D-09). The only check is the phase-local proof under `.planning/.../evidence/` in this documentation repo (D-23), which never runs in security-platform. A later edit to one job (for example, a fix for WR-01 or WR-02 applied to one job only) would drift without anything failing.
**Fix:** Use a YAML anchor, or a composite action under `.github/actions/chart-gate/` that both jobs call. Either keeps the two named check contexts and removes the duplication.

### IN-04: The workspace-unchanged check cannot see ignored files

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:250, 308-316` (identical at `464, 522-530`)
**Issue:** `git status --porcelain=v1` does not report changes under ignored paths. `kubernetes/*/charts/*.tgz`, the files the positive run depends on, are gitignored. The D-15 "never mutate the tree" check therefore cannot detect a mutation of the vendored tarballs. Today the negative step only reads the workspace (`cp -a`), so this is a limit of the check, not a live defect.
**Fix:** Add `--ignored` to both `git status` calls, or record a `sha256sum` of `kubernetes/${CHART}/charts/*.tgz` before and after.

### IN-05: The workflow header repeats the gate check counts

**File:** `repos/security-platform/.github/workflows/chart-gates.yml:10-11`
**Issue:** The header comment says "22 checks" and "18 checks". Each script says its count is a literal in exactly three places that move together. D-14 deliberately avoided checking the count in the workflow, so the workflow would not become a fourth place. The comment cannot break a run, but it will go stale silently when a check is added.
**Fix:** Drop the numbers, e.g. "asserts the chart's offline invariants (the count is in the script)".
