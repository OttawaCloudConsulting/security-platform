jobs.defectdojo-cleanup
  name: DefectDojo Cleanup
  (no needs:)
  if: github.event_name == 'pull_request' && github.event.action == 'closed' && vars.DEFECTDOJO_URL != ''
  runs-on: ubuntu-latest ; timeout-minutes: 10
  permissions: contents: read
  concurrency: identical group expression and cancel-in-progress: false as defectdojo-import
  NO job-level env:, NO shell: key
  steps (in order):
    dd-gate            byte-identical to the defectdojo-import dd-gate step (name, env, run)
    dd-delete          name "Delete this PR's ci/<branch> DefectDojo engagement"
                       if: steps.dd-gate.outputs.enabled == 'true' ; continue-on-error: true
                       env:
                         DD_URL:            ${{ vars.DEFECTDOJO_URL }}
                         DD_TOKEN:          ${{ secrets.DEFECTDOJO_API_TOKEN }}
                         DD_PRODUCT:        ${{ vars.DEFECTDOJO_PRODUCT || github.repository }}
                         DD_INSECURE:       ${{ vars.DEFECTDOJO_INSECURE }}
                         DD_CA_CERT:        ${{ vars.DEFECTDOJO_CA_CERT }}
                         DD_DEFAULT_BRANCH: ${{ github.event.repository.default_branch }}
                         DD_CLEANUP_RESULT_FILE: dd-cleanup-result.json
                       body reads runner-provided GITHUB_HEAD_REF (never ${{ }}).
    dd-cleanup-verify  name "Verify DefectDojo cleanup landed"
                       if: always() && steps.dd-gate.outputs.enabled == 'true' ; NO continue-on-error
                       env DD_DELETE_OUTCOME: ${{ steps.dd-delete.outcome }} ;
                           DD_CLEANUP_RESULT_FILE: dd-cleanup-result.json

Cleanup result file, JSON object:
  { "outcome": "deleted" | "nothing-to-delete" | "refused", "target", "product_name",
    "product_id" (null when unresolved), "deleted_ids": [ ... ] }

dd-delete decision sequence (python3 stdlib heredoc, same header-file and TLS-args rules as dd-import,
including the ::warning:: lines):
  1. head = GITHUB_HEAD_REF. If empty, or head == DD_DEFAULT_BRANCH, or DD_DEFAULT_BRANCH is empty:
     print "REFUSE: head ref <repr> is empty or the default branch — nothing deleted", outcome refused, exit 0.
  2. target = "ci/" + head (literal concatenation, never a pattern).
  3. GET /api/v2/products/?name_exact=<urlencoded DD_PRODUCT>&limit=100 (never ?name=, which is icontains).
     Keep results whose "name" == DD_PRODUCT exactly. 0 -> "NOTHING TO DELETE: no product named <repr>",
     outcome nothing-to-delete, exit 0. More than 1 -> "FAILED: <n> products exactly named <repr> — refusing
     to guess", exit 1.
  4. GET /api/v2/engagements/?product=<pid>&name=<urlencoded target>&limit=100. Keep results with
     name == target AND product == pid. 0 -> "NOTHING TO DELETE: no engagement <repr> in product <pid>",
     outcome nothing-to-delete, exit 0.
  5. Refuse (exit 1, delete nothing) if any kept engagement's name equals "ci/" + DD_DEFAULT_BRANCH
     (defence in depth).
  6. For each kept engagement: DELETE /api/v2/engagements/<id>/ and require HTTP 204; print
     "DELETED: engagement id=<id> name=<repr> product=<pid>".
  7. Re-GET step 4 and require 0 exact matches; else exit 1.
  8. Write the result file (outcome deleted, deleted_ids), exit 0.
  Every GET requires 200; any other code prints "FAILED: <method> <path> http=<code>" and exits 1.
  All query strings via urllib.parse.urlencode.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-03 | Tampering / DoS | dd-delete (irreversible) | mitigate | Product via `name_exact` plus client-side `==`; exactly one product required; engagement by exact `name` plus client `==` plus product-id re-check; empty head and default branch refused; `ci/<default>` refused again before any DELETE; no match is a no-op; re-GET confirms only the target is gone |
| T-27-01 | Tampering / Elevation | dd-delete run: body | mitigate | Head ref arrives via runner env GITHUB_HEAD_REF; zero `${{` in the body; queries built with urlencode |
| T-27-02 | Information disclosure | API token | mitigate | Same 0600 header-file pattern as dd-import; the token is only in the dd-gate and dd-delete step env |
| T-27-05 | Elevation | staff token scope | accept | Delete requires `is_staff` at 3.3.200 OS; staff is instance-wide. Documented in the adoption guide (27-09) and ADR-024 (27-10) with a dedicated-user/instance recommendation |
