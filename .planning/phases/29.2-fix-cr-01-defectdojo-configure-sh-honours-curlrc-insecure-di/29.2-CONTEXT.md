# Phase 29.2: Fix Phase 28 CR-01 (ambient curlrc can disable TLS verification) - Context

**Gathered:** 2026-09-29
**Status:** Ready for planning

<domain>
## Phase Boundary

**Which CR-01.** This phase fixes the **Phase 28 CR-01** from `28-REVIEW.md`: `defectdojo-configure.sh` reads the operator's curlrc, and an `insecure` line in it silently turns TLS verification off before the superuser token is sent. This is NOT the Phase 27 CR-01 (https-only URLs, ADR-025, released as `v1.1.1`), which PROJECT.md line 37 also calls "CR-01". Downstream artifacts must always say "Phase 28 CR-01".

**Goal (ROADMAP only says `[Urgent work - to be planned]`; this is the goal):** ambient curl configuration (`~/.curlrc`, `$CURL_HOME/.curlrc`) can no longer cause a DefectDojo API token to be sent to a peer whose TLS certificate was not verified. The fix covers every DefectDojo API client in `security-platform`. An offline negative case in the proof harness proves it: with a hostile curlrc against a self-signed listener, each target refuses, and the listener receives no HTTP request and no token.

Targets, all in `OttawaCloudConsulting/security-platform` (local clone `repos/security-platform/`):
1. `scripts/defectdojo-configure.sh`: operator-run, superuser token.
2. `scripts/defectdojo-lifecycle-assert.sh`: operator-run, superuser token (Phase 29).
3. The DefectDojo bodies in `.github/workflows/security.yml`: the "Import reports into DefectDojo (reimport-scan)" step (~L1373, curl at ~L1512) and the "Delete this PR's ci/<branch> DefectDojo engagement" step (~L1724, curl at ~L1783). These use the CI `ci-importer` token.

Also in scope (folded): Phase 28 **WR-01** and **WR-02**, the configure token-file edge cases.

The whole phase must hold the carried-forward contract: TLS is always verified, and there is no option to switch it off (28 D-10, ADR-025, lifecycle-assert header). This phase makes that claim true in the code. It does not reopen it.

NOT in this phase:
- Cutting a tag or moving `v1`. The `security.yml` change merges to `main` untagged, and Phase 29.4 cuts the release that covers both phases (D-02).
- The trivy-image `scan-target` dedup change (29.4), chart gate WR-05 (29.3), TRIAGE query WR-03 (29.5) and roadmap bookkeeping (29.7).
- Any consumer-facing setting for host resolution (D-07).

<decisions>
## Implementation Decisions

### Fix scope
- **D-01:** Fix all three targets: `defectdojo-configure.sh`, `defectdojo-lifecycle-assert.sh` and the two DefectDojo curl bodies in `security.yml`. The operator chose this over the recommended "operator scripts only", so the `ci-importer` token path is covered too. A self-hosted ARC runner (ADR-028) could carry a curlrc.
- **D-02:** **Release is batched with Phase 29.4.** 29.2 merges its `security.yml` change to `security-platform` `main` with no new tag and no `v1` move. 29.4 (which also changes `security.yml`) cuts one additive v1.x tag and moves `v1` for both (ADR-018, 27 D-16). The 29.2 SUMMARY must state that `v1` does not yet carry the fix. 29.4's plan must pick this up, so record it in STATE.md when this phase closes.
- **D-03:** **Fold in WR-01 and WR-02** (`28-REVIEW.md`) for `defectdojo-configure.sh`:
  - WR-01: a token file that is not a regular file (directory), or is unreadable (mode 000), must exit 2 (preflight) with a FATAL line, not a traceback with exit 1. Check `S_ISREG`, and wrap the `open()`.
  - WR-02: validate the token content so that the header file always holds exactly one well-formed `Authorization: Token <token>` header. A multi-line token, or a token with a `Token ` prefix, is refused with exit 2. The review suggests `[A-Za-z0-9]{20,128}`. The researcher confirms the DefectDojo 3.3.200 token format (DRF authtoken, 40 hex) and picks the pattern.
  - Where `lifecycle-assert.sh` has the same token-file gaps, apply the same checks. It already states that it follows "the defectdojo-configure.sh contract".

### Transport hardening (applies to every DefectDojo curl call in all three targets)
- **D-04:** Pass **`-q` as curl's first argument** on every DefectDojo API call, so that no curlrc is read. `-q` works only in first position; the plan and the tests must respect that.
- **D-05:** **Every call also fails closed on `%{ssl_verify_result}` not equal to `0`.** This is defence in depth. It covers GET, PATCH and the re-GET in configure, every lifecycle-assert request, and the CI import and cleanup requests. Add `%{ssl_verify_result}` to `-w`, and treat any value other than `0` (including a missing value) as a failure: exit 1, "TLS verification result X (must be 0)". This follows the harness's existing `write_dedup_py` `get()` pattern. The check runs after the request, so `-q` (D-04) is what actually keeps the token off an unverified peer. The check catches a regression of D-04.
- **D-06:** **Host-resolution hook: a single env var `DEFECTDOJO_RESOLVE`**, passed as one `--resolve <value>`. The same mechanism is used in all three targets.
  - The value must match a strict `host:port:address` pattern. Its host and port must equal those of `DEFECTDOJO_URL`, otherwise the script refuses with exit 2 (preflight).
  - When unset or empty, the hook does nothing.
  - The hook only chooses the IP. TLS verification against the URL's hostname still applies, so the hook cannot weaken TLS.
  - A curl config file option (`-K`) was rejected, because a config file could contain `insecure` again.
- **D-07:** **`DEFECTDOJO_RESOLVE` is harness-only in `security.yml`.** The workflow bodies read the env var, but the workflow never sets it. It is not a `workflow_call` input, a repository variable or a secret, and it is not documented in `docs/adoption-guide.md`. Only the proof harness sets it when it runs the extracted bodies. No new consumer surface is added to v1. A comment in the body must say that it is a test hook and unset in real use.
- **D-08:** **Never echo raw curl stderr** on failure in any of the three targets. The failure line prints only: method and path, the curl exit code, the HTTP code, `ssl_verify_result`, and a fixed error string (curl's `%{errormsg}`, or a mapped exit-code message). Header or trace text must never reach output. The researcher verifies that `%{errormsg}` exists on the curl versions in use (it needs curl >= 7.75: macOS system curl, ubuntu-latest, and the ARC runner image). If it is not available, map the exit codes. The review's "scrub `Authorization:` lines" option was rejected as a fragile denylist.

### Harness and proof (`scripts/defectdojo-import-proof.sh`)
- **D-09:** **The harness keeps a CURL_HOME curlrc, and it is now hostile.** For all live runs it contains `insecure` and `verbose` (plus anything else the researcher finds would weaken TLS or leak headers). Host resolution moves from the curlrc `resolve` line to `DEFECTDOJO_RESOLVE` (D-06). As a result, every live P-CONFIGURE, P-IDEMPOTENT and import/cleanup body run also proves that the curlrc is ignored.
  - The current P-TLS guard ("curlrc must hold exactly one resolve line and nothing that disables verification", ~L2133-2139) is inverted to assert that the curlrc is hostile.
  - The harness's own curl helpers must then also pass `-q` and `--resolve`, or the hostile curlrc breaks or weakens them: `api_call` ~L391, and the Python `cmd = ["curl", ...]` readers at ~L500, ~L779 and ~L2309.
  - The token-in-log checks must still pass with `verbose` present.
- **D-10:** **The offline negative case uses a python3 `ssl` listener**: a small `http.server` wrapped in an `ssl` context with a throwaway self-signed cert. It must run the same on macOS (LibreSSL curl) and ubuntu CI. Generate the cert without `openssl req -ext`, because LibreSSL does not support it (Phase 29 WR-06 precedent). Generating in python or using a plain `openssl req -x509 -subj` is fine; the researcher picks.
- **D-11:** **The negative case asserts, for each target:**
  - the listener logged **zero HTTP requests** (the handshake was refused, so no Authorization header ever arrived);
  - the target exited 1;
  - no success line was printed (`http=200`, `NO CHANGE`, `CHANGED:` or `VERIFIED:`);
  - the token is absent from all output.

  The case runs with its **own** CURL_HOME that contains `insecure` and `verbose`, and `DEFECTDOJO_RESOLVE` points at the listener. It must prove that the curlrc was ignored, not only that `-q` appears in the command. A static grep for `-q` is not sufficient on its own.
- **D-12:** **The negative case covers all three targets**: `defectdojo-configure.sh`, `defectdojo-lifecycle-assert.sh`, and each extracted `security.yml` DefectDojo body. They run offline, next to the existing P-HTTP / P-CONFIGURE-GUARD cases (~L581-730). The label is Claude's discretion, for example `P-CURLRC`.
  - `lifecycle-assert.sh` is not in the harness today, so it is newly invoked offline.
  - `.github/workflows/defectdojo-import-proof.yml` `on.pull_request.paths` must gain `scripts/defectdojo-lifecycle-assert.sh`.
- **D-13:** New offline cases for WR-01 and WR-02 join P-CONFIGURE-GUARD: a directory at the token path, a mode-000 token file, a multi-line token, and a `Token `-prefixed token. Each must exit 2 with a FATAL line and send no request.
  - All existing assertions must keep passing: P-HTTP, P-CONFIGURE-GUARD, P-CONFIGURE, P-IDEMPOTENT, P-TLS (inverted per D-09), and the 88-assertion import proof.
  - The live proof run on kind (`defectdojo-import-proof.yml`) must end PROOF PASS on the PR.

### Records
- **D-14:** Write a **new ADR-029**. It extends ADR-025 and covers:
  - DefectDojo API clients ignore ambient curl config (`-q` first);
  - `ssl_verify_result` must be 0 on every call;
  - the harness-only `DEFECTDOJO_RESOLVE` hook and its validation;
  - no raw curl stderr in output.

  It names the Phase 28 CR-01 (and WR-01/WR-02) as the trigger. It states that `v1` does not carry the `security.yml` part until the 29.4 release. Add its row to `docs/adr/README.md`. ADR-025 (and every other accepted ADR) stays byte-unchanged, because ADRs are append-only. This follows the precedent of ADR-025 superseding ADR-024 decision 13 in its own text.
- **D-15:** **Doc touches:**
  - correct the header comments of all three targets (configure.sh L37-41 currently contradicts itself: "always verified" next to "a curlrc under CURL_HOME is honoured");
  - update the comment block of each `security.yml` body;
  - add one line to the bootstrap section of `kubernetes/defectdojo/README.md` (~L230) saying that the operator's curlrc is ignored.

  The primary blueprint `development-security-stack-option-1.md` and `docs/adoption-guide.md` are NOT changed, because nothing consumer-facing changes (D-07).

### Amendments after research (operator decisions, 2026-09-30)
- **D-16 (amends D-05 for the `security.yml` bodies):** `security.yml` still maps the released v1 input `DEFECTDOJO_INSECURE=true` to `-k` (ADR-025, `docs/adoption-guide.md`), and `-k` yields `ssl_verify_result=18`. In the two `security.yml` bodies, the `ssl_verify_result` check therefore runs only when `tls_mode != "insecure"`. `-q` (D-04) applies unconditionally in every mode. The operator scripts (configure, lifecycle-assert, homelab-validate) have no insecure mode and always run the check. The v1 `DEFECTDOJO_INSECURE` behaviour stays unchanged, so the 29.4 release stays additive. Per research, success also requires curl exit 0 AND verify 0 AND the expected HTTP code, because `ssl_verify_result` is 0 on a refused connection.
- **D-17 (amends D-01):** `scripts/defectdojo-homelab-validate.sh` becomes a **fourth target**. It sends the real homelab admin password (~L565, ~L622) and an API token (~L804) with no `-q`, and echoes curl stderr on failure (~L467, ~L575, ~L630). Apply D-04 (`-q` first), D-05 (verify must be 0), D-06 where it has a resolve need, and D-08 (no raw stderr). The P-CURLRC negative case (D-11/D-12) covers it too, where it can run offline. `defectdojo-live-smoke.sh` (throwaway kind cluster only) stays out of scope and is recorded as tech debt.
- **D-18 (clarifies D-08):** A failure line may include the DefectDojo HTTP **response body**, truncated. This is the server's JSON, not curl output. Raw curl stderr, verbose output and trace output stay banned.

<code_context>
## Existing Code Insights

### Reusable Assets
- The harness `write_dedup_py` `get()` already checks `verify != "0"` from `-w '%{http_code} %{ssl_verify_result}'`. It is the model for D-05.
- The harness `api_call` already emits `%{http_code} %{ssl_verify_result}`.
- `run_body`, `print_masked`, `proof_pass` / `proof_fail` / `proof_abort`, and the dummy-token offline pattern (0600 token file written with printf, token-in-log grep) in the P-CONFIGURE-GUARD section are reused for the new negative cases.
- The P-EXTRACT mechanism extracts the committed `security.yml` bodies into runnable files. The negative case runs those extracted bodies, not copies.

### Established Patterns
- Token handling: the token is never on argv, is sent only as `-H @0600-file` (O_EXCL / noclobber) inside a private temp dir, is never echoed, and xtrace is never enabled.
- Every curl uses `--proto =https --proto-redir =https`. D-04 adds `-q` in front of these. It must be the literal first argument.
- Exit codes: 0 success, 1 refusal/API/verification failure, 2 preflight.
- `configure.sh` is bash wrapping a python3 heredoc. `lifecycle-assert.sh` is bash with an `args=()` array. The `security.yml` bodies are python in `run:` blocks. D-04 to D-08 must be implemented in each idiom.

### Integration Points
- `security.yml` is the released reusable workflow. Its bodies are extracted and executed by the harness, so the D-06 env read must work both in Actions (unset) and in the harness (set).
- The harness live flow sets `CURL_HOME` globally (`export CURL_HOME=...` ~L2133). After D-09 it is hostile for everything, including the harness's own helpers.
