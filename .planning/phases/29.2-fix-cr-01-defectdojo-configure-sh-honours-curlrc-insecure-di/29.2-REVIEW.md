## Summary

Scope: the hunks in `repos/security-platform` from `fdabac9` to `47319b2`. The local HEAD is `415618c`, whose tree is identical to `47319b2`: `git diff 415618c 47319b2` is empty. ADR-029 was reviewed against that code.

I checked the phase's core guarantees at every DefectDojo API call site in the four clients, and no BLOCKER turned up:

- **`-q` is curl's first argument everywhere.** This holds for configure.sh `api()` (L154), lifecycle-assert `api_transport()` (L462, which is now its only curl call site; the old direct curl in `cmd_assert_closed` goes through it), all six homelab-validate call sites (L481, L538, L588, L606, L645, L833), and dd-import and dd-delete in security.yml.
- **The order of checks is right.** Each site checks the curl exit first, then `ssl_verify_result == "0"`, then the HTTP code. The only exception is the documented D-16 insecure carve-out in the two workflow bodies. A missing verify value fails closed.
- **curl stderr is never shown.** It goes to `/dev/null` or `subprocess.DEVNULL` at every site, and nothing reads `proc.stderr`.
- **The token stays out of argv and failure lines.** It never appears on argv or in a failure line. The DEFECTDOJO_RESOLVE hook is checked after the https refusal and before the token file is read.
- **The dd-import stop-on-failure logic works.** It also gives a non-zero exit, which dd-verify turns red.

The problems are robustness and consistency issues in the hardening:

- Two of the three token-file validators do not match the contract ADR-029 decision 6 describes.
- The static CURLRC gate is a single-string denylist.
- The proof harness can print `PROOF PASS` with fewer assertions and no signal beyond a SKIP line.
- lifecycle-assert does not stop after a transport or TLS failure the way the other clients do.

**Acknowledged, not re-reported.** DI-01 (resolved), DI-02 (P-INSECURE has no offline coverage), DI-03 (live-smoke curls without `-q`), DI-04 and DI-05 (resolved), and ADR-029's "What was NOT verified" items 1-10: environment-scoped weakening such as `CURL_CA_BUNDLE` and `SSLKEYLOGFILE`, `DD_TOKEN` content not validated, SecureTransport not exercised, and so on. I found none of their severities understated.

## Warnings

### WR-01: lifecycle-assert and homelab-validate accept token files with several trailing newlines, which breaks ADR-029 decision 6

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:333-335`, `repos/security-platform/scripts/defectdojo-homelab-validate.sh:445-446`

**Issue:** ADR-029 decision 6 says, for all three operator scripts, that the token must fullmatch `[0-9a-f]{40}` "after at most one trailing line ending is stripped". Both bash headers repeat "one trailing CR/LF allowed". The bash scripts actually read `cred="$(< "$CRED_FILE")"`. Command substitution strips **every** trailing newline, and the one `${cred%$'\r'}` strip then runs on that result. Tested locally: a file holding `<40 hex>\n\n\n\n` passes the bash check (`bash-accepts-multi-newline`), while the same file is rejected by configure.sh's Python check (`py-rejects`).

There is no header-injection risk, because the header still gets exactly one line. The problems are these:

- The accepted contract is false for two of the three clients.
- The three clients now disagree about the same token file.
- None of the P-TOKEN-GUARD cases (multiline, prefix, dir) covers this, so later drift will not be caught.

Also, neither script pins `LC_ALL`/`LC_COLLATE`. The bash `=~` ranges `[0-9a-f]` go to the libc `regcomp`, and on older or non-glibc libcs these ranges follow locale collation. That is a second, smaller way the bash and Python validators can differ.

**Fix:**

```bash
# read the file byte-exact (no command-substitution newline stripping)
IFS= read -r -d '' cred < "$CRED_FILE" || true
cred="${cred%$'\n'}"; cred="${cred%$'\r'}"      # strip exactly one LF or CRLF
if [[ ! "$cred" =~ ^[0-9a-f]{40}$ ]]; then ...  # run with LC_ALL=C for the test
```

Add a `token-trailing-blank-lines` case to P-TOKEN-GUARD for lifecycle-assert and homelab-validate.

### WR-02: The CURLRC gate is a single-string denylist and misses job-level and workflow-level `env:`

**File:** `repos/security-platform/scripts/check-workflow-uploads.sh:671-720`

**Issue:** Check 20 needs exactly one `["curl", "-q", "-sS"` and no `["curl", "-sS"` in each body. The following would pass the gate while reading the runner curlrc:

- a second curl call written any other way, such as `["curl", "--silent", ...]`, `["curl"] + args`, `"curl -sS ..."` with `shell=True`, or `subprocess.run(["curl", "-k", ...])`.

The other checks are presence tests that are easy to satisfy:

- `"%{ssl_verify_result}" in run` and `"stderr=subprocess.DEVNULL" in run` are satisfied by any single occurrence anywhere in the body.
- `"proc.stderr" not in run` misses any other variable name, for example `p.stderr` or `res.stderr`.

The D-07 check ("the workflow never sets DEFECTDOJO_RESOLVE") looks only at the step's `env:` mapping. A job-level `jobs.<id>.env` or a workflow-level `env:` would put the hook into both bodies, and the gate would pass. ADR-029 decision 7 presents this gate as enforcing the curl-config contract. In practice the runtime P-CURLRC case is the real proof, and the gate is only advisory.

**Fix:** Count every `"curl"` list literal or `curl` token in the run text and require that each one is followed immediately by `"-q"`. For example, use `re.findall(r'\[\s*"curl"\s*,\s*"([^"]+)"', run)`, check that every capture is `-q`, and fail if `re.search(r'["\']curl["\']', run)` finds more matches than that. Also fail when `DEFECTDOJO_RESOLVE` appears in `jobs.<jid>.env` or in the top-level `env`. State in the gate header and in ADR-029 that the gate is a regression tripwire, not the proof.

### WR-03: `proof_skip` is not counted and `proof_finish` pins no total, so a missing sub-proof still prints `PROOF PASS`

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:392-395` (`proof_skip`), `398-406` (`proof_finish`), `1453` (homelab-token-get skip), `1184` (configure-token-mode000 skip)

**Issue:** Two cases can be skipped:

- `homelab-token-get` is skipped when `kubectl` is not on PATH, and it is the only offline proof that the homelab token GET refuses an unverified peer.
- `configure-token-mode000` is skipped when running as root, which is plausible on an ARC runner image.

A skip prints `PROOF: <ID> SKIP ...`. It never reaches `PROOF_N` or `PROOF_FAILED`, and `proof_finish` prints `PROOF PASS - ${PROOF_N} assertions` with nothing compared to an expected count. A run that loses these proofs therefore ends `PROOF PASS - 29 assertions` (or 28). Any consumer that greps `^PROOF PASS - ` sees green. This includes the plan verify chains quoted in deferred-items.md.

Coverage caveat on the same case: in P-CURLRC for homelab-validate, `get_login_form` fails TLS first, so the login POST that carries the admin password (L588) and the foreign-Origin POST (L645) are never reached at runtime. Their `-q` is verified only by reading the source, not by the harness, so ADR-029's "six call sites" claim is only partly exercised.

**Fix:** Add a `PROOF_SKIPPED` counter and print it in the verdict line (`PROOF PASS - N assertions, K skipped`). Then either fail when `K > 0` in `--hook`, or have `mode_scheme_only` and `mode_hook` assert the expected `PROOF_N` (30 and 151) so that a skipped case fails. Record in ADR-029 that the password-carrying POSTs are covered only by reading the source.

### WR-04: lifecycle-assert `measure_dispositions` keeps sending the token after a transport or TLS failure

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:611-627`

**Issue:** `measure_dispositions` calls `api_get` for the fp, oos and ra findings and then the risk acceptance. On any failure, including a transport failure or a non-zero `ssl_verify_result` from `api_transport`, it writes `{read_error: ...}` and moves on to the next request. That can send up to three more token-bearing requests to a peer that just failed TLS verification. dd-import (ADR-029 decision 3, "STOPPED") and homelab-validate (`API_TLS_FAILED`, "the token is not sent to the same peer again") both stop on the first such failure by design.

Because `-q` is argv[1], a failed handshake never carries the header, so this is not a leak. The verify check is defence in depth, and this is where the defence is weakest: if `-q` regressed, the case the verify check exists to catch (ADR-029 "What was NOT verified" item 2, a curlrc `cacert` swap that gives verify 0) would not be stopped here. The same applies to a non-zero verify value with curl exit 0, where the token has already been sent. The script's behaviour also differs from its own header ("anything else is an API error and the run fails"): the run does eventually fail, but only after more requests.

**Fix:** Separate transport failure from HTTP failure in `api_transport`, for example with a global `TRANSPORT_FAILED=1`, and abort on it in every caller that currently falls back:

```bash
if api_get "/api/v2/findings/${id}/" "${WORK}/disp-${role}.json"; then
  ...
elif [[ "${TRANSPORT_FAILED:-0}" -eq 1 ]]; then
  abort "D11-TRANSPORT" "$API_ERROR"
else
  jq -n --arg e "$API_ERROR" '{read_error: $e}' > "${WORK}/disp-${role}-slim.json"
fi
```

## Info

### IN-01: The lifecycle-assert and homelab-validate headers give the wrong XDG curlrc path

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:92`, `repos/security-platform/scripts/defectdojo-homelab-validate.sh:123`

**Issue:** Both headers say `$XDG_CONFIG_HOME/.curlrc`. curl reads `$XDG_CONFIG_HOME/curlrc`, with no leading dot. configure.sh (L43) and ADR-029 have it right.

**Fix:** Change both headers to `$XDG_CONFIG_HOME/curlrc`.

### IN-02: The DEFECTDOJO_RESOLVE check accepts values that are not IPv4 and out-of-range ports, which then give exit 1 instead of the documented exit 2

**File:** `repos/security-platform/scripts/defectdojo-configure.sh:121`, `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:287-296`, `repos/security-platform/.github/workflows/security.yml` (both `RESOLVE_RE`)

**Issue:** `(?:[0-9]{1,3}\.){3}[0-9]{1,3}` accepts `999.1.1.1`. In lifecycle-assert, when the URL names the same port, port `99999` passes the `${#u_port} -le 5` check (Python's `urlsplit().port` raises and refuses it). curl then fails at run time with exit 1, but every header and ADR-029 decision 4 promise exit 2 for a malformed hook. The impact is low because this is a test-only hook and hostname verification is kept.

**Fix:** Check the address with `ipaddress.IPv4Address(...)` in Python, check each octet `<= 255` in bash, and require `1 <= port <= 65535`.

### IN-03: The harness `api_call` callers still echo curl stderr files and ignore `ssl_verify_result`

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:441, 1819, 1854, 2325-2330`

**Issue:** Harness helpers such as `mint_token`, P-DEDUP-MODE and P-DISPOSITION still send `2>"${...}.err"` and print it on failure. Several judge success on `rc` and the HTTP code alone, without the verify value. Under `-q`, `--cacert` and no verbose this is safe, and it is test code. It is still the pattern D-08 bans in the product scripts, and it would print verbose header text if `-q` were ever dropped from `api_call`. The final P-TLS trace-absence assertion is the only thing guarding against that.

**Fix:** Send the harness helpers' stderr to `/dev/null` as well, and check `verify == 0` in every `api_call` caller.

### IN-04: The P-TLS hostile-curlrc self-check does not assert the `location` directive it writes

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:2959-2965`

**Issue:** The live curlrc writes `location` (L2959), but the check loop lists `'^location-trusted$'` and not `'^location$'`. The abort message also names only `location-trusted`. This is minor: `location-trusted` implies following redirects.

**Fix:** Add `'^location$'` to the directive list so the self-check matches the header comment and ADR-029 decision 7.
