## Warnings

### WR-02: The CURLRC gate is a single-string denylist and misses job-level and workflow-level `env:`

**Status:** open, carried forward from the 2026-09-30T17:04:50Z review. The code is unchanged and only the line numbers have been updated.

**File:** `repos/security-platform/scripts/check-workflow-uploads.sh:666-720`

**Issue:** This is unchanged since the prior review. Check 20 needs exactly one `["curl", "-q", "-sS"` and no `["curl", "-sS"` in each body. The following would pass the gate while reading the runner curlrc:

- a curl call written any other way, such as `["curl", "--silent", ...]`, `["curl"] + args`, a `shell=True` string, or `["curl", "-k", ...]`.

The other checks are presence tests that are easy to satisfy:

- `"%{ssl_verify_result}" in run` and `"stderr=subprocess.DEVNULL" in run` pass on any single occurrence anywhere in the body.
- `"proc.stderr" not in run` misses any other variable name.

The D-07 check looks only at the step `env:`. A `jobs.<id>.env` or a top-level `env:` that sets `DEFECTDOJO_RESOLVE` would reach both bodies, and the gate would still pass. ADR-029 decision 7 presents the gate as enforcing the contract, but in practice it is only a tripwire. The runtime P-CURLRC case is the real proof.

**Fix:** Capture every curl list literal with `re.findall(r'\[\s*"curl"\s*,\s*"([^"]+)"', run)` and require that each capture is `-q`. Fail if `re.findall(r'["\']curl["\']', run)` finds more matches than that. Also fail when `DEFECTDOJO_RESOLVE` appears in `jobs.<jid>.env` or in the workflow-level `env`. State in the gate header that the gate is a regression tripwire, not the proof.

### WR-03: `proof_skip` is not counted and `proof_finish` pins no total, so a missing sub-proof still prints `PROOF PASS`

**Status:** open, carried forward from the 2026-09-30T17:04:50Z review. The code is unchanged and only the line numbers have been updated.

**File:** `repos/security-platform/scripts/defectdojo-import-proof.sh:401-415` (`proof_skip`, `proof_finish`), `1271` (configure-token-mode000 skip when root), `1573` (homelab-token-get skip without kubectl)

**Issue:** This is unchanged. A skip prints a line but touches neither `PROOF_N` nor `PROOF_FAILED`, and `proof_finish` prints `PROOF PASS - ${PROOF_N} assertions` without comparing that number to anything. The gap fix made this more pressing:

- Operators and plan verify chains now depend on specific totals. 29.2-11 and 29.2-12 record `45` (`--scheme-only`) and `166` (live).
- Nothing in the script enforces those totals.

As a result:

- A root runner produces `PROOF PASS - 44`.
- A runner without kubectl produces `PROOF PASS - 44` or `165`.
- A future edit that silently drops a GUARD_CASES label also still ends in `PROOF PASS`.

A consumer that greps `^PROOF PASS - ` sees green in each case. The coverage caveat from before still applies: the password-carrying homelab POSTs (login and foreign-Origin) are never reached in P-CURLRC, so their `-q` is verified only by reading the source.

**Fix:** Add a `PROOF_SKIPPED` counter, print it in the verdict line (`PROOF PASS - N assertions, K skipped`), and have `mode_scheme_only` and `mode_hook` assert the expected totals (45 and 166). A skip or a dropped case then fails loudly. Alternatively, derive the expected guard count from `${#GUARD_CASES[@]}` and assert that every label produced exactly one PASS.

### WR-04: lifecycle-assert `measure_dispositions` keeps sending the token after a transport or TLS failure

**Status:** open, carried forward from the 2026-09-30T17:04:50Z review. The code is unchanged and only the line numbers have been updated.

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:636-657`

**Issue:** This is unchanged. When `api_get` fails, including a transport failure or a non-zero `ssl_verify_result`, the function writes `{read_error: ...}` and moves on. That can send up to three more token-bearing requests to a peer that just failed verification.

dd-import (ADR-029 decision 3, "STOPPED") and homelab-validate (`API_TLS_FAILED`) both stop on the first such failure.

Because `-q` is argv[1], this is defence in depth rather than a leak. It is weakest in exactly the case the verify check exists for: if `-q` regressed, verify would be non-zero while curl still exits 0, and the token would already have been sent.

**Fix:** Have `api_transport` set a global `TRANSPORT_FAILED=1` on a curl exit other than 0 or on verify != 0. Abort in every caller that currently falls back:

```bash
if api_get "/api/v2/findings/${id}/" "${WORK}/disp-${role}.json"; then
  ...
elif [[ "${TRANSPORT_FAILED:-0}" -eq 1 ]]; then
  abort "D11-TRANSPORT" "$API_ERROR"
else
  jq -n --arg e "$API_ERROR" '{read_error: $e}' > "${WORK}/disp-${role}-slim.json"
fi
```

### IN-02: The DEFECTDOJO_RESOLVE check accepts values that are not IPv4 and out-of-range ports, which then give exit 1 instead of the documented exit 2

**Status:** open, carried forward from the 2026-09-30T17:04:50Z review. The code is unchanged and only the line numbers have been updated.

**File:** `repos/security-platform/scripts/defectdojo-configure.sh:121`, `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:287-298`, `repos/security-platform/.github/workflows/security.yml:1415`, `repos/security-platform/.github/workflows/security.yml:1815`

**Issue:** This is unchanged. `(?:[0-9]{1,3}\.){3}[0-9]{1,3}` accepts `999.1.1.1`. In lifecycle-assert, port `99999` passes the `${#u_port} -le 5` check when the URL names the same port. curl then fails with exit 1, where exit 2 is documented.

**Fix:** Parse the address with `ipaddress.IPv4Address` in Python, check each octet `<= 255` in bash, and require `1 <= port <= 65535`.

### IN-05: `read_token_file` is copied verbatim into two scripts, with no static parity check

**Status:** new in this review.

**File:** `repos/security-platform/scripts/defectdojo-lifecycle-assert.sh:345-358`, `repos/security-platform/scripts/defectdojo-homelab-validate.sh:450-463`

**Issue:** The function body is duplicated. The two copies differ only in the variable they assign (`cred` or `token_val`). WR-01 was a drift between clients, so this is where drift is most likely to come back. Behavioural parity is covered at runtime by P-TOKEN-GUARD and P-TOKEN-ACCEPT for all three clients, which lowers the risk. Those cases run only in the harness, though, and not in the cheap offline gate.

**Fix:** Pick one of two options:

- Add a check to `check-workflow-uploads.sh`, or a small sibling gate, that extracts both function bodies and requires them to be identical apart from the assigned name.
- Move the function into a sourced `scripts/lib/token-file.sh` that returns the token on a fixed variable.
