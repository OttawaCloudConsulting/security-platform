# Phase 29.2 Plan 05: security.yml DefectDojo bodies curlrc / verify fix and CURLRC gate Summary

The two DefectDojo bodies in the released reusable workflow (`dd-import` and `dd-delete`) now call curl with `-q` as argv[1] in every TLS mode. A request succeeds only if curl exits 0, `ssl_verify_result` is 0 (this check is skipped only on the released `DEFECTDOJO_INSECURE=true` path, D-16), and the HTTP code is the expected one. The bodies never read curl stderr, and they refuse a malformed `DEFECTDOJO_RESOLVE` test hook with exit 2 before any connection. dd-import stops at the first transport or TLS failure. A new 20th static check, CURLRC, guards all of this. `--scheme-only` is now green (`PROOF PASS - 30 assertions`). One harness timing race is still open and is deferred to 29.2-06 (see Deferred Issues).

**`v1` does not yet carry this fix (D-02).** The fix is on local branch `fix/phase-29.2-curlrc`. It has no tag and `v1` has not moved. 29.4 cuts the additive v1.x tag.

## What was built

The change is in security-platform, on branch `fix/phase-29.2-curlrc`, commit `f5a3926`. The branch is 5 commits above origin/main `fdabac9`, is not pushed (`git ls-remote` is empty), and has no tag.

**security.yml, dd-import**
- It imports `urllib.parse`. At module level it reads `resolve = env.get("DEFECTDOJO_RESOLVE", "")`, with a comment saying this is a test hook set only by `scripts/defectdojo-import-proof.sh` and unset in real use. It also defines `RESOLVE_RE`, copied verbatim from configure.sh, and a `resolve_matches_url()` helper. The helper checks the regex, a lower-cased host equal to `urlsplit(url).hostname`, and a port equal to the URL port (default 443; a bad URL port counts as a mismatch).
- In `main()`, directly after the https refusal and before the `TLS mode:` label and `write_private(hdr_path`, it runs `if resolve and not resolve_matches_url():`. On a mismatch it prints `FAILED: DEFECTDOJO_RESOLVE must be host:port:IPv4 with the host and port of DEFECTDOJO_URL (test hook; leave it unset)` and returns 2.
- The curl head is `["curl", "-q", "-sS", "--proto", "=https", "--proto-redir", "=https", "-o", resp_path, "-w", "%{http_code} %{ssl_verify_result} %{errormsg}"] + tls_args`, followed by `--resolve resolve` when the hook is set, then the unchanged `-H`, `-F` and `--form-string` parts. curl stderr goes to `stderr=subprocess.DEVNULL`.
- **Transport failure** means `proc.returncode != 0 or (tls_mode != "insecure" and verify != "0")`. On one, dd-import:
  - prints `FAILED: <file>: curl exit N, http C, TLS verification result V (must be 0): <errormsg>` and `STOPPED: no further report is sent after a transport or TLS failure`
  - appends the record, with `http_code` as measured and `test_id` None, so `bad` counts it
  - leaves both loops through a `stopped` flag
  - still writes DD_RESULTS_FILE and the `attempted=... failed=...` line
  - returns 1 (`return 1 if (bad or stopped) else 0`)
- The HTTP-mismatch branch prints `body[:500]` only. The `proc.stderr` fallback is gone.
- Behaviour change you can observe: after a stop, the table entries that were not reached are neither attempted nor recorded as skipped. The proof run therefore shows `attempted=1 skipped=0 failed=1`.

**security.yml, dd-delete**
- It adds `import re`, the same module-level `resolve`/`RESOLVE_RE` with the test-hook comment, `resolve_matches_url()`, a `Preflight` exception mapped to `rc = 2` in the wrapper (inside the try/finally, so cleanup still runs), and a module-level `tls_mode` that `main()` sets through `global tls_mode`.
- The resolve validation runs directly after the https refusal and before the default-branch refusals, the `TLS mode:` label and the header write.
- `api()` uses the same argv head, `--resolve`, DEVNULL, parse and transport predicate. It prints `FAILED: <METHOD> <path>: curl exit N, http C, TLS verification result V (must be 0): <errormsg>` and raises Failed. The HTTP-mismatch branch no longer falls back to stderr.

**YAML comments (D-15).** Both comment blocks gain a "Runner curl config (ADR-029, Phase 28 CR-01)" paragraph covering:
- `-q` first, so no runner curlrc is read (hosted or self-hosted ARC, ADR-028)
- the exit-0 plus verify-0 rule, and its DEFECTDOJO_INSECURE exception
- dd-import's stop at the first failure (in dd-import's block)
- curl stderr is never read or printed
- DEFECTDOJO_RESOLVE is a proof-harness test hook that the workflow never sets and that is not a consumer setting

No comment line contains `"curl", "-q"`, `startswith(` or `--proto`. No added line contains `${{`. No `env:` mapping or `workflow_call` input changed.

**check-workflow-uploads.sh.** Check 20, CURLRC, sits after SCHEME and uses the same loop over (defectdojo-import, dd-import) and (defectdojo-cleanup, dd-delete). For each step it fails unless all of the following hold:
- `run.count('["curl", "-q", "-sS"') == 1`
- `["curl", "-sS"` is absent
- `%{ssl_verify_result}` is present
- `stderr=subprocess.DEVNULL` is present
- `proc.stderr` is absent
- `DEFECTDOJO_RESOLVE` is read
- the step `env` mapping has no `DEFECTDOJO_RESOLVE` key (D-07)

`CHECK_COUNT = 20`. CURLRC is added to the check-name list and to the header table under a new "Phase 29.2" heading.

## Deferred Issues

- **DI-01: a P-CURLRC listener race in the harness, owned by 29.2-06** (see `deferred-items.md` and `evidence/29.2-05-flake-runs.txt`).
  - Symptom: 3 of 33 `--scheme-only` runs ended `PROOF FAIL - 1 of 30` with `P-CURLRC FAIL dd-import|dd-delete: no HANDSHAKE-FAIL at the listener; [listener CONNECT=1 HANDSHAKE-FAIL=0 REQUEST=0]`. The body still exited 1 with the verify-18 FAILED line, and REQUEST was 0, so the token was never sent.
  - Cause: the listener logs HANDSHAKE-FAIL only when `wrap_socket` raises, which can happen after the body has exited, and `curlrc_counts` reads the log without waiting.
  - Why it is not fixed here: the harness is outside this plan's files, and an extra commit would break the plan-pinned commit counts for 05 and 06.
  - 29.2-06's own verify greps `^PROOF PASS - ` and will hit this intermittently unless it fixes the race first.
