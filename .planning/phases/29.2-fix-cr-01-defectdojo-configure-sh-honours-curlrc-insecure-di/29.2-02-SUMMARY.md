# Phase 29.2 Plan 02: token-file and DEFECTDOJO_RESOLVE guard cases (RED) Summary

The harness now has 16 offline preflight guard cases: P-CONFIGURE-GUARD WR-01/WR-02, P-RESOLVE-GUARD and P-TOKEN-GUARD. They cover configure, lifecycle-assert, homelab-validate and the committed dd-import and dd-delete bodies. Each case runs while the P-CURLRC listener and the hostile curlrc are live, and each one requires the following:

- exit 2
- a refusal line
- 0 CONNECT at the listener
- no `http=` line
- neither dummy token and no `X-Other` in the log

Against the unfixed code, 14 of the cases fail. The other 2 pass by design as regression guards.

## What was built

**security-platform, branch `fix/phase-29.2-curlrc`, commit `55dfd67` on top of `b11f677`. Not pushed. The branch is 2 commits above origin/main.**

- `GUARD_CASES` is a table of `ID:label` pairs. `guard_not_evaluated` uses it to emit a FAIL for every guard case when the fixture or control fails.
- `guard_token KIND PATH` creates the token fixture for each case. The kinds are `valid`, `dir` (`mkdir -m 700`), `mode000`, `multiline` (two 40-hex lines), `header` (`<hex>\nX-Other: 1`) and `prefix` (`Token <hex>`). The content is written only by the printf builtin. The function always sets `CURLRC_TOK` and `GUARD_TOK2`, so the sed mask can never become an empty pattern.
- `guard_token_rm` does `rmdir` for directories and `chmod 600` before `rm -f` for files. `guard_show_log` masks both tokens.
- `assert_guard_refused ID LABEL DESC REGEX [NEEDLE] [EXTRA_WHY]` checks exit 2 and a line matching REGEX. When NEEDLE is set, which only happens for the configure token cases, that same line must also contain the token path. It then checks `CURLRC_C == 0`, no `http=`, both tokens absent and `X-Other` absent.
- `prove_guard_refusal` is called from `prove_curlrc_refusal` after dd-delete and before `curlrc_fixture_down`:
  - **configure:** 4 P-CONFIGURE-GUARD cases, which expect `^FATAL: DEFECTDOJO_ADMIN_TOKEN_FILE` plus the path. mode000 is guarded by `id -u` and calls `proof_skip` when running as root. There are also 2 P-RESOLVE-GUARD cases, which expect `^FATAL: DEFECTDOJO_RESOLVE`.
  - **lifecycle:** 3 P-TOKEN-GUARD cases, which expect `^ERROR: DEFECTDOJO_ADMIN_TOKEN_FILE`, and 2 P-RESOLVE-GUARD cases, which expect `^ERROR: DEFECTDOJO_RESOLVE`.
  - **homelab:** 3 P-TOKEN-GUARD cases, which expect `^ERROR: --token-file`. The wrapper and argv are the same as plan 01, with `KUBECONFIG=<empty file under PROOF_DIR>` and `DEFECTDOJO_RESOLVE=`.
  - **dd-import and dd-delete:** each has a `resolve-host` case. The body must print a `DEFECTDOJO_RESOLVE` line and no `TLS mode:` line, and dd-import must write no results file.
- The bad hook values are `other.curlrc.test:<port>:127.0.0.1` and `*:<port>:127.0.0.1`.
- The header's Modes and Assertion groups text now names P-RESOLVE-GUARD and P-TOKEN-GUARD.
