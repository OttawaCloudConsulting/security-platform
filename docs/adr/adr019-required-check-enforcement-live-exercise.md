# ADR-019: Required-Check Enforcement, Live-Exercised

**Status:** Accepted
**Date:** 2026-09-16
**Addresses:** VAL-02 — required-check enforcement exercised live, on a real repository's ruleset, with GitHub's refusal of a merge captured verbatim and the target's branch protection restored afterwards

## Context

- **The v2.0 milestone audit listed exactly one end-to-end flow as UNVERIFIED:** *"Blocking gate, required check, merge blocked — UNVERIFIED — dry-run only, never applied."* Both prior records say the same thing in their own words: ADR-017's "What was NOT verified" item 4 records that `scripts/set-required-checks.sh --apply` "has never been run", and ADR-018's item 7 records that "this phase's branch-protection work on both pilot repositories stayed a dry run (`--out`, never `--apply`)". Before this phase, no repository in this project had ever had a required status check actually enabled, so nothing had ever been refused.
- **`OttawaCloudConsulting/terraform-pipelines` was the exercise target, not `security-platform`.** Its own Terraform sources produce real findings under `GATE_MODE=blocking` — two of the five contexts concluded `failure` on the exercise pull request with no vulnerability seeded for the purpose — so the red required check the exercise needs is the repository's own scan output rather than a planted fixture. ADR-017's `leave-unrequired` decision for `security-platform`'s own `main` was made on measured grounds (its validation-only `fixtures/` tree guarantees findings on every run, which would lock `main` against the very pull request that would revert the change) and was not re-opened.
- **`terraform-pipelines`' `main` carries no `.github/workflows/` directory at all.** `gh api "repos/OttawaCloudConsulting/terraform-pipelines/contents/.github/workflows"` returned `404 Not Found`. Five contexts left required on that branch would sit permanently *pending* on every future pull request that did not itself carry the workflow — which blocks a merge exactly as a failing check does. The end state was therefore fixed as **restore** before the first write, not decided after the exercise succeeded.
- **The ruleset offers no admin escape.** `bypass_actors: []` and `current_user_can_bypass: "never"`, read live before the write, at the moment of the refusal, and after the restore. A refusal measured under those values is enforced rather than advisory: no actor, including the repository owner, could have merged past it.
- **The operator's go/no-go was recorded before the first byte reached GitHub.** `proceed`, timestamped 2026-09-16T17:39Z, written as the oldest file in the phase's evidence directory — at which moment `rules/branches/main` still read `copilot_code_review,deletion,non_fast_forward`.
- **Every live write in the exercise was performed by the operator in their own terminal, not by the agent.** The executor's auto-mode Bash classifier denied five writes across three of the phase's plans: `gh pr create` and its REST `POST …/pulls` equivalent, `gh variable set GATE_MODE`, and the two operator scripts carrying `gh pr merge --squash` and the `git push` that re-triggered the checks. The two remaining writes — the forward `--apply` and the restore — were routed to the operator from the outset rather than attempted, on the strength of those denials plus the two earlier ones Phase 20 measured against `scripts/set-required-checks.sh`. Every value recorded below comes from the agent's own `gh api` reads, taken independently of whoever ran the write.

## Decision

- **Record the exercise as measured, on a pilot repository, with that repository's steady state restored.** The five `security / …` contexts were made required on `terraform-pipelines`' `main` for a bounded window, the refusal was witnessed, and the ruleset was reversed from the pre-exercise capture. This ADR is the record; it does not extend required checks to `security-platform`, and it does not change any decision ADR-017 made.
- **The bounded-window-plus-mandatory-restore procedure is the recommended shape for a first adoption on a repository whose default branch does not yet carry the workflow** — capture the ruleset before touching it, require the contexts, exercise a pull request, then restore from the capture and prove the restore with a diff. That condition, not caution in general, is what makes the restore mandatory: contexts that no run on the default branch will ever produce are permanently-pending required checks. This is written into `docs/adoption-guide.md` section 8 as the phase's most reusable output.
- **Four assumptions are retired by observation rather than by argument.** (1) *The exact `pull_request` rule parameter set GitHub accepts on `PUT /repos/{o}/{r}/rulesets/{id}`* — ADR-017's item 4: the six-key merged document the script builds was accepted with the five parameters it sends (`required_approving_review_count: 0`, `dismiss_stale_reviews_on_push`, `require_code_owner_review`, `require_last_push_approval`, `required_review_thread_resolution` all `false`), and GitHub server-added three the script never sent — `required_reviewers: []`, `allowed_merge_methods: ["merge", "squash", "rebase"]`, and `require_extra_approval_for_unattributed_changes: true`. A parameter set is now measured where it was previously only dry-run. (2) *Whether `copilot_code_review` round-trips through `PUT` on a repository carrying that preview rule type* — the phase's research flagged a possible `422`, unanswerable without a write. It did not `422`: the rule round-tripped with `review_on_push: true` and `review_draft_pull_requests: true` byte-identical, on the forward write and again on the restore. (3) *Whether the existing token scope sufficed for a ruleset write* — the operator's own `gh` authentication wrote the ruleset twice, forward and back, both exit 0 and neither raising a scope error — the restoring `PUT` additionally emitted zero bytes on stderr, while the forward run's output arrived as one abridged combined paste and its stderr was never captured separately; the agent's token was never used for a write and this says nothing about it. (4) *The literal text `gh pr merge` emits when it declines* — this project had no prior art for that wording, so it was captured rather than predicted; it is quoted in full below.
- **The required-check list, the five-not-six correction and the `leave-unrequired` decision for `security-platform` are inherited unchanged from ADR-017 and restated here only so a reader of this record alone does not reintroduce a sixth context or conclude that this exercise overturned that decision.**

## Consequences

**Improved:** measured on one pull request (PR #14, `OttawaCloudConsulting/terraform-pipelines`) across three commits (`a792e1a8b1054c99ae9406993b5d91d223dbe02f`, `969dc2c8e12fc6c29f42cab1a9a0bde9eca686c7`, `34bf29cb2fef09434339e48ba0a466d28241766b`) sharing one tree hash (`57a81e0988c72b9772ca9f912ae8073eca9b5951`, read locally on all three and confirmed at the third, `34bf29cb`, from GitHub's own commits API) — four `mergeStateStatus` readings with exactly one ruleset write between the second and the third: `CLEAN` with five green checks and nothing required (run `35144256399`); `UNSTABLE` with two of the five red under `GATE_MODE=blocking` and still nothing required (run `35150200030`); **`BLOCKED` on that same head SHA `969dc2c8`, with the same two red checks and nothing pushed in between, once the five contexts were made required**; then `CLEAN` again at `34bf29cb` (run `35167607668`) with all five green and the five contexts still required, confirmed byte-identical to the post-write capture. `mergeable` read `MERGEABLE` at every one of the four readings, and `main` stayed at `c490bed09f43bae5440594db7e76011e8951f26c` throughout. The `UNSTABLE` → `BLOCKED` transition on one unchanged head SHA is the deliverable; the `BLOCKED` → `CLEAN` return with the requirement still in force is what attributes it to the red required check rather than to `copilot_code_review`, to the `pull_request` rule, or to a review requirement.

**Improved:** GitHub refused the merge. `gh pr merge --squash` exited `1` and emitted, verbatim and unreformatted:

```text
X Pull request OttawaCloudConsulting/terraform-pipelines#14 is not mergeable: the base branch policy prohibits the merge.
To have the pull request merged after all the requirements have been met, add the `--auto` flag.
To use administrator privileges to immediately merge the pull request, add the `--admin` flag.
```

Neither bypass flag was passed: the attempt used `--squash` only, and the sole occurrences of `--admin` and `--auto` in the transcript are GitHub's own hint lines above. The two red contexts at that moment were `security / SAST — Semgrep CE` and `security / SCA — Trivy Filesystem` — **two, not one**; the phase's inherited assumption that Semgrep alone would go red was falsified in the safe direction and is corrected here so a future reader does not expect a single named context.

**What the refusal proves, stated precisely.** This is `gh`'s **client-side** decline, not a server-side rejection. What was observed: no HTTP status code appears anywhere in the transcript, and the message's shape is a policy statement followed by two CLI flag hints rather than an API error body. What is inferred from that shape: `gh` read `mergeStateStatus`, declined locally, and never sent a request to `repos/…/pulls/14/merge`. The honest claim is therefore that **the `gh` CLI declined to merge because GitHub reported the base branch policy prohibits it** — the gate observed being enforced through the client a developer actually uses, which is the operationally meaningful path, and not a claim that the REST merge endpoint returned an error. Nothing in this record should be cited as evidence about that endpoint.

**Tradeoff — the blocking window was repository-wide for its duration, in two separate senses.** The `GATE_MODE=blocking` window lasted 66 seconds (`2026-09-16T21:03:13Z` from GitHub's own `created_at` on the variable, to `21:04:18Z` after the delete) with exactly one run inside it, audited against the full run list; the next most recent run on the repository had started an hour earlier. The *required-check* window was longer: from the forward `PUT` (`updated_at` `2026-09-16T19:20:36.158-04:00`) to the restore (`2026-09-16T21:30:36.682-04:00`), about two hours and ten minutes, during which any pull request on that repository would have faced the same five required checks. ADR-017 already records repository-wide scope as a structural tradeoff of the `GATE_MODE` mechanism; the ruleset half of it has the same shape, and the mitigation is the same — keep the window short, audit what ran inside it, and restore.

**Tradeoff — the pilot repository's steady state is unchanged, but two residues persist and no `git revert` in this repository touches either.** The restore is proven twice over: `diff rules-before.txt rules-restored.txt` is empty against two independent readings, and the full ruleset document compares equal on every key except the server-owned `updated_at`, which must move or no write happened. PR #14 is `CLOSED` with `mergedAt: null` and its branch deleted (the ref 404s). What remains: eighteen code-scanning analyses attributable to the exercise branch sit in the repository's code-scanning tab, uploaded as SARIF by the runs that produced the red and then the green conclusions, and the closed pull request stays in the repository's history with its full timeline. Both match what the Phase 20 pilots already left on the same repository.

**Tradeoff — `copilot_code_review` is a preview rule type that can degrade to a non-blocking comment.** During the exercise it requested a review and Copilot returned `COMMENTED`, not a blocking verdict, with *"Copilot was unable to review this pull request because the user who requested the review has reached their quota limit."* An adopter relying on that rule as a gate should know it fails open on quota exhaustion. Relatedly, `require_extra_approval_for_unattributed_changes: true` — which GitHub added server-side on the write and which defaults to `true` — did **not** block: `reviewDecision` was empty at both the `BLOCKED` and the `CLEAN` readings, and both commits on PR #14 were attributed to a GitHub account.

## What was NOT verified

What WAS measured and must not be re-litigated: the four merge-state readings on three commits sharing one tree hash; the forward `PUT` returning 200 with all three pre-existing rule types (`copilot_code_review`, `deletion`, `non_fast_forward`) carried forward byte-identically alongside the two added ones; the five contexts each pinned to `integration_id` 15368 with their separator proven `U+2014` by codepoint dump on the live names rather than by eye; `bypass_actors: []` and `current_user_can_bypass: "never"` before, during and after; the refusal text above; and the restore, proven by an empty rule-type diff from two independent reads plus full-document equality excluding `updated_at`.

1. **ADR-017 item 4 and ADR-018 item 7 are NARROWED by this record, not closed.** Both are written about `security-platform`'s own `main`, which this exercise did not touch. ADR-017's item 4 reads, verbatim: *"The exact `pull_request` rule parameter set GitHub requires on `PUT /repos/{o}/{r}/rulesets/{id}` has been exercised only against a local dry run, not against a live write — the operator's `leave-unrequired` decision (18-05 Task 3) means `scripts/set-required-checks.sh --apply` has never been run against this repository's own ruleset."* What this exercise closes: the script's `--apply` path is now live-exercised against a real ruleset, the parameter set GitHub accepts is measured, and the mechanism is proven to refuse a merge. What it does not close: the words *"against this repository's own ruleset"* still hold — `security-platform`'s `main` remains un-required, which is ADR-017's standing decision on measured grounds and is deliberately left in force. ADR-018's item 7 asks whether any repository has required checks actually enabled; the honest answer after this phase is that one repository had them enabled, for a bounded window of about two hours, on purpose, and deliberately does not now. Neither of those two files was edited to record this — they are append-only per this repository's `CLAUDE.md`, and this record closes what it closes by reference.
2. **The server-side merge endpoint was never exercised.** Settling the client-side-versus-server-side question would require `gh api -X PUT repos/…/pulls/14/merge` under the same fresh-`BLOCKED` precondition; it was out of scope and was not run, and it can no longer be run against PR #14, which read `CLEAN` before it was closed. A future exercise wanting that observation must plan for it deliberately, because the obvious way to obtain it is also the way to accidentally merge.
3. **`require_extra_approval_for_unattributed_changes`' semantics remain unverified.** Two Context7 queries against GitHub's published REST documentation returned no match for the parameter. What is verified is only that it did not obstruct this pull request, whose two commits were both attributed to an account; the reading that commit-author-to-account linkage is what "unattributed" means is an inference from the name, not a documented fact.
4. **The settle-poll's contract has a first-read limitation, now on record rather than latent.** With no previous value to compare against, the first non-sentinel reading wins whether or not it is terminal: the baseline read `UNSTABLE` at 20:05Z and resettled to `CLEAN` at 20:15Z on the same head SHA, because a third-party GitGuardian check completed in between. The practical rule for an adopter is to wait for **every** check run on the head SHA to complete — twelve existed at each reading here, only five of them ours — before reading merge state, and to pass the prior value on every subsequent read.
5. **Whether a `--restore` flag belongs in `scripts/set-required-checks.sh` is deferred, not decided.** The restore here was a one-off operator script built from the phase's own before-capture, cross-checked offline against the body GitHub had already accepted. Adding a first-class restore path would cost a commit in a separate repository (`security-platform`, the canonical host per ADR-018), an adoption-guide update, and a re-run of the standing gate — none of which this documentation repository can do on its own, and none of which this phase's evidence establishes a need for.
6. **The end state on `security-platform` is unchanged and unaddressed by this exercise.** Required-check adoption on the host repository remains deferred exactly where ADR-017, 18-05 and 19-07 left it.
7. **The script's exit-3 drop guard was not re-proven at this commit.** Exits 2, 4 and 5 were rehearsed live by the operator immediately before the apply and observed exactly; exit 3 is not offline-triggerable, because the script's own merge carries every pre-existing rule type forward and therefore cannot construct a document that drops one. It stays covered by 18-03's record.
8. **Nothing here bears on fork or Dependabot runs.** Whether a fork pull request can read repository `vars` at all — ADR-017's item 1, routed onward unresolved — and whether `actions/upload-artifact` succeeds on a fork or Dependabot-triggered run are both untouched by this exercise, which ran entirely on a same-repository branch.
