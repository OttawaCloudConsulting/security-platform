# ADR-016: SARIF Upload Attribution and Scan Artifact Retention

**Status:** Accepted
**Date:** 2026-09-11
**Addresses:** CICD-02, CICD-03 — scan results reach the GitHub Security tab with per-analysis attribution, and every scan report is retained as a build artifact for a stated period

## Context

By the end of Phase 16 the pipeline's five parallel jobs already produced **six SARIF files and seven-plus JSON reports on every pull request — and nothing consumed any of them.** They were written to the runner's working directory and discarded when the job ended. A `code-scanning/analyses` probe against `OttawaCloudConsulting/security-platform` returned HTTP `404 "no analysis found"` and `actions/artifacts` returned `total_count: 0`. The scanners worked; the reporting layer did not exist.

Four constraints shaped how that layer had to be built:

- **GitHub keys a code scanning analysis on `tool.driver.name` plus `category`, not on the file name.** Two of the six SARIF files carry the identical driver name `Trivy` — the filesystem scan in the `sca` job and the image scan in the `container` job. Uploaded without distinct categories, the second upload in a run replaces the first, and one of the two scans silently disappears from the Security tab.
- **The scanning workflow is a reusable `workflow_call`, so its permission set is capped by its caller.** A called workflow can only *downgrade* what it inherits; it cannot grant itself `security-events: write`. A caller that does not grant it produces a green run with an empty Security tab — a failure with no red anywhere.
- **ADR-001 requires the upload steps specifically to stay tolerated.** It removed `continue-on-error: true` from every *scanner* step while explicitly retaining it on SARIF and artifact upload steps, "reporting infrastructure, not enforcement". That is in direct tension with this project's no-silent-fallback rule, and the tension had to be resolved rather than picked a side of.
- **Two of the stack's tools cannot emit SARIF at all.** Measured from `--help`: `pip-audit -f` accepts only `columns`, `json`, `cyclonedx-json`, `cyclonedx-xml` and `markdown`; `npm audit` offers only `--json`. Neither has a SARIF path, native or flagged.

## Decision

- **Each SARIF file is uploaded individually under a unique, hand-assigned `category`.** The six categories are `semgrep`, `checkov`, `trivy-fs`, `tflint`, `trivy-image` and `gitleaks`. Categories are **sticky by design**: GitHub treats a category as the identity of a recurring analysis, so renaming one later does not update its history — it **orphans** the existing alerts under the old name and starts a fresh series under the new one. These six strings are therefore a published contract, not an implementation detail.
- **`security-events: write` is granted on the CALLING JOB in `pr-security.yml` and re-declared at workflow level in `security.yml`.** The grant sits on the calling job rather than at the caller's workflow level so the scope is not handed to unrelated jobs; the callee re-declares it because a called workflow can only downgrade an inherited set, never widen it, and a callee that omits the scope entirely inherits nothing useful. `actions: read` is carried alongside it purely for private-repo portability — a public repo does not need it, and a consumer repo that is private does. No other write scope is requested anywhere in the scanning workflow.
- **Upload success is asserted on `steps.<id>.outcome`, never on the presence of `sarif-id`.** The `upload-sarif` action populates its `sarif-id` output *before* `wait-for-processing` can reject the SARIF, so a non-empty `sarif-id` is not evidence the upload landed. The step `outcome` is, and it is the only signal the assertions read.
- **Every upload step keeps `continue-on-error: true`, and every one is paired with an intolerant assertion step.** This is how ADR-001 and the project's no-silent-fallback rule are both honoured: the tolerated upload preserves ADR-001's judgement that reporting infrastructure must not block a merge, while the paired assertion — which does *not* tolerate failure — means a 403 or a rejected SARIF surfaces as a red step instead of being swallowed. Eleven such assertions exist, six for SARIF uploads and five for artifacts.
- **Five artifacts are retained with an explicit `retention-days: 90`:** `semgrep-results`, `checkov-results`, `sca-results`, `trivy-image-results` and `gitleaks-results`. The period is written into the workflow rather than left to the repository default because CICD-03 requires a *stated* retention period; an implicit default is not stated, is invisible in the workflow file a consumer copies, and can be changed by anyone with repository settings access without a commit. 90 days is the maximum available without a repository-settings change. These five names are also a contract — a future DefectDojo importer (DEFECT-01) will address them literally.
- **Each tool's native JSON is retained unnormalised; no common schema is introduced.** Measured against the DefectDojo source tree, `dojo/tools/` already contains dedicated parsers for `checkov`, `gitleaks`, `npm_audit`, `npm_audit_7_plus`, `pip_audit`, `sarif`, `semgrep`, `tflint` and `trivy`. Every tool in this stack has a native parser, so normalising would *destroy* import fidelity rather than add it. The runner carries npm 10.x, so the applicable npm parser is `npm_audit_7_plus`, not the legacy `npm_audit` one.
- **The `sca` job emits its SARIF from a second direct `trivy fs --format sarif` run rather than from `trivy convert`.** Measured 2026-09-11 against trivy 0.74.0 with the byte-exact CI invocation: `trivy convert` sets `originalUriBaseIds.ROOTPATH` to the path of the **input JSON file** (`file:///<cwd>/trivy-fs.json/`), while a direct `--format sarif` run sets it to the **scan root** (`file:///<repo root>/`). Both emit the same relative result `uri`, so under convert the base resolves to a path that is not a directory in the repository. `trivy convert` is **retained in the `container` job**, where it remains this phase's documented conversion step — the image scan's locations point at image layers rather than repository files, so the base is moot there.
- **Criterion 4 is satisfied for npm audit and pip-audit through the ARTIFACT SET plus the documented `trivy convert` step, not through a hand-rolled converter (user decision D-01).** No converter is written and no third-party converter action is introduced. The concrete cost of the alternative is measurable, not stylistic: pip-audit's JSON carries **no severity field at all**, so any hand-rolled SARIF would have to emit `level: warning` for every result, flattening critical and informational findings into one indistinguishable band. Both tools' reports reach the retained `sca-results` artifact in their native form, where a DefectDojo parser already exists for each.
- **The workflow trigger stays `pull_request`-only; `push: branches: [main]` is deliberately NOT added (user decision D-02).** Stated plainly, because it is the consequence a reader is most likely to be surprised by: **`main` is never analysed**, so no alert this phase produces is associated with the default branch. The unfiltered Security tab therefore reads empty, and CICD-02's first criterion must be verified under the Security tab's branch/PR filter or through the `code-scanning/analyses` API with an explicit `ref`. Revisiting the trigger is deferred to Phase 19 (VAL-01).

## Consequences

**Improved:** the pipeline stopped discarding its own output. On PR #8, run `34638828775`, the repository went from `total_count: 0` artifacts and a `404 "no analysis found"` to **seven analyses across the six distinct categories** on `refs/pull/8/merge` and **five artifacts, all non-zero, every `expires_at` exactly 90 days after the run's `created_at`**. Three inline code scanning annotations rendered on `fixtures/main.tf` line 38 — tflint `terraform_module_version` and Checkov `CKV_TF_1`/`CKV_TF_2` — while the other 88 results across the seven analyses produced none, because none of them sits on a changed line. All eleven intolerant assertions ran green and none skipped.

**The measured SARIF inventory** (produced by running each tool against `repos/security-platform`, then confirmed against the live analyses API on run `34638828775`):

| Job | SARIF file | `tool.driver.name` | runs | results | Locations resolve to repo files? | Category |
|---|---|---|---|---|---|---|
| `sast` | `semgrep.sarif` | `Semgrep OSS` | 1 | 3 | Yes — workflow and Dockerfile paths present in the tree | `semgrep` |
| `iac` | `checkov.sarif` | `Checkov` | 1 | 14 | Yes — `fixtures/main.tf` | `checkov` |
| `sca` | `trivy-fs.sarif` | `Trivy` | 1 | 6 | Yes — `fixtures/package-lock.json`; the base is correct only because of the direct-SARIF decision above | `trivy-fs` |
| `sca` | `tflint.sarif` | `tflint` **and** `tflint-errors` | **2** | 3 and 0 | Yes — `fixtures/main.tf` | `tflint` |
| `container` | `trivy-image.sarif` | `Trivy` | 1 | 56 | No — all 56 point at the scanned image, line 1:1 | `trivy-image` |
| `secrets` | `gitleaks.sarif` | `Gitleaks` | 1 | 9 | No — the flagged paths exist only in git history | `gitleaks` |

Two notes on that table. **Six categories produce seven analyses, not six:** tflint's single SARIF carries two `runs[]` entries with two different driver names, and GitHub creates one analysis per driver. "One category equals one analysis" is false in this repository, and any future count assertion must expect seven. **Driver-name case differs between endpoints:** the analyses API reports `checkov` and `Gitleaks`, while the check-runs endpoint reports `Checkov` and `gitleaks`. Branch protection matches the *check-run* name, so any required-check list must be built from `commits/{sha}/check-runs`, never from `code-scanning/analyses`.

**Tradeoff — no alert is ever associated with the default branch.** This is D-02's direct cost. A reader who opens the Security tab without a filter sees nothing and will reasonably conclude the uploads are broken. Verification of CICD-02 must go through the branch/PR filter or an API call with an explicit `ref`, and any future consumer documentation has to say so before it says anything else about the Security tab.

**Tradeoff — npm and pip findings reach the artifact set but not the Security tab.** D-01 resolves Criterion 4 through retention rather than conversion, so `npm-audit-1.json` and `pip-audit-1.json` are downloadable from `sca-results` and importable into DefectDojo, but they contribute no code scanning alerts, no annotations and no check runs. Anyone auditing dependency findings from the Security tab alone will under-count them.

**Tradeoff — 90 days is a ceiling, not a choice.** Raising retention beyond 90 days requires a repository-settings change, which is outside what a copy-pasted workflow file can express. A DefectDojo landing more than 90 days after a given run will find that run's artifacts expired, and the reports will have to be regenerated rather than recovered.

**Tradeoff — successful uploads add check runs that Phase 18 must evaluate before making anything required.** Run `34638828775` carried twelve check runs on the head SHA where Phase 16 measured six: the same six plus six new `github-advanced-security` checks. The rule is **one check per `tool.driver.name`, not per category** — `Trivy` appears exactly once despite owning two categories, and the sixth new check is tflint's `tflint-errors` driver. One of those new checks, `Checkov`, concluded **failure** while all five job checks were green and the pull request remained mergeable, because the repository's fixtures exist to produce error-severity findings. Adding code scanning checks to a required-status-check list would block that pull request today. This is recorded as an input to Phase 18's decision, not as a recommendation.

**Tradeoff — the zero-cost claim holds for this public repository and does not transfer.** Code scanning SARIF upload is free on public repositories; on a **private** repository it requires a paid GitHub Code Security licence. Every decision above is reachable at zero cost here, and a private consumer repository adopting this workflow would need either that licence or a fallback to the artifact set alone. Phase 20's adoption documentation (DIST-08) owns stating that before a consumer commits to the pipeline.

## What was NOT verified

Two things this ADR relies on nearby were measured and should not be re-litigated: PR diff annotations **do** render with no base analysis on the default branch to diff against — three of them did, on the line the fixture edit was constructed to touch — and `security_events` token scope is **not** required to read code scanning on a public repository.

Three things remain **not verified**, and are recorded in those words so that Phases 18 through 20 do not build on them:

1. **Whether a Dependabot-triggered run can obtain `security-events: write` is not verified.** Dependabot runs execute with a restricted token, and this phase never observed one. The SARIF and artifact verification steps therefore *skip* rather than fail on Dependabot and fork pull requests, which means an upload failure on such a run would currently be invisible. The observation is handed to Phase 18.
2. **Whether `actions/upload-artifact` itself succeeds on a fork or Dependabot run is not verified.** Its `ACTIONS_RUNTIME_TOKEN` differs from `GITHUB_TOKEN`, and run `34638828775` — a same-repository, non-Dependabot pull request — cannot distinguish the two cases.
3. **How GitHub's ingester treats a `ROOTPATH` that resolves outside the repository is not verified.** The direct-SARIF decision sidesteps the question in the `sca` job rather than answering it, so the broken-base shape was never uploaded and its rendering behaviour remains unmeasured.
