# ADR-017: Configurable Gate Mode and Required Checks

**Status:** Accepted
**Date:** 2026-09-12
**Addresses:** CICD-04, CICD-06 — a repository-wide switch between advisory and enforcing scan behaviour, and the required-status-check list that makes the enforcing state actually block a merge

## Context

- **Every scan step has carried an unconditional `continue-on-error: true` since Phase 15.** ADR-001 removed the flag from the four original scanner steps but D-04 (Phase 16) reintroduced it across all eleven gated steps for as long as the pipeline stayed deliberately report-only; nothing in the workflow let a consumer choose otherwise. Report-only was hardcoded, not configured.
- **A called `workflow_call` reads the CALLING repository's variables, but a caller's workflow-level `env` is NOT propagated into the callee.** That asymmetry makes a repository variable the only mechanism that lets a copy-paste consumer switch modes without editing YAML — an `env:` block on the caller's workflow would have to be repeated inside the callee to have any effect, which defeats the "no YAML edit" goal outright.
- **A `workflow_call` string input with no default resolves to the empty string, and an explicitly-passed empty value counts as *provided*, suppressing a declared default.** A bare `with: gate_mode: ${{ vars.GATE_MODE }}` passthrough is therefore a trap for any consumer whose repository has not set the variable: the empty string is passed, not omitted, and the callee's own `report-only` default never fires.
- **GitHub does not validate a `type: string` `workflow_call` input against a value list.** Nothing upstream of the workflow itself rejects a typo like `blockign`; the workflow has to validate its own resolved value or a misspelled mode silently falls through to whichever tolerance branch the comparison operator favours.
- **A caller job that `uses:` a reusable workflow emits no check run of its own.** The caller contributes only the `<job-id> / <called-job-name>` prefix that appears on each callee job's own check; there has never been, and will never be, a bare `security` check run to add to a required list.
- **`PUT /repos/{o}/{r}/rulesets/{id}` replaces the entire ruleset document.** A required-check-list update that does not first read the current document back and preserve every unrelated field it did not intend to touch will silently delete rules, actors, and conditions that have nothing to do with the check list.
- **This repository's `fixtures/` exists to make every scanner fire.** Checkov (14), Trivy filesystem (6), Trivy image (56), Semgrep (3), Gitleaks (9) all report findings against the committed fixtures on every run, and the live ruleset governing `main` reports `bypass_actors: []` and `current_user_can_bypass: "never"` — there is no admin override baked into the ruleset itself.

## Decision

- **The flag is a single global string enum `blocking` | `report-only`, defaulting to `report-only` (D-01/D-02/D-03)** — not a boolean and not per-job flags. A boolean was considered and rejected: it reads as clear at the call site but forces every future third mode (e.g. a severity-tiered mode) into a breaking rename; the string enum leaves room to grow without breaking the input's name.
- **It is resolved exactly once, at workflow level, through the input-then-variable-then-literal chain**, so every one of the eleven gated steps reads the same already-resolved value rather than re-deriving it.
- **It is applied to exactly eleven scan-step tolerances as `== 'report-only'`, never as `!= 'blocking'`.** The first form fails closed on a typo — an unrecognised string is treated as not report-only, i.e. blocking; the second fails open — an unrecognised string is treated as not blocking, i.e. tolerated — leaving a repository un-gated while its required checks still report green. Per-step expressions repeated on all eleven lines individually were considered and rejected: they work, but repeat the fallback semantics eleven times and leave the variable-resolution path nowhere to plug in once.
- **The eleven ADR-001 upload and artifact tolerances stay unconditional** — a transient SARIF-upload or artifact-upload hiccup must not block a merge regardless of gate mode; only scan-step tolerances are gated.
- **The caller in this repository passes no `with:` block at all**, which is what makes "switch modes without editing YAML" literally true: the repository variable alone selects the mode. A literal `with:` block was the thing an empty-string passthrough would have forced, and it would have destroyed exactly this property.
- **A literal `with: gate_mode: blocking` is nonetheless the documented form for a PUBLIC repository intending to block from the start**, as the mitigation for the unresolved fork-variable question recorded below — a public repository that cannot rely on `vars` reaching a fork PR can still pin the mode explicitly at the call site.
- **Enum validation is one intolerant step inside each of the five jobs, never a sixth job.** A terminal per-job gate step reading `steps.*.outcome` was considered and would have avoided the skipped-step problem entirely, but it contradicts the locked D-04 tolerance-per-step design and was rejected on decision grounds, not technical ones. A sixth job was rejected because it would emit a sixth check run and break the frozen five-check set the required-check list depends on.
- **Three SCA scan guards gained `always() &&`** so blocking mode does not skip a later scanner in the same job after an earlier one in that job has already failed — without the guard, a scanner whose own verify step then runs would fail on a missing report rather than on its own finding.
- **The required-check list is FIVE byte-exact contexts, pinned to `integration_id` 15368**: `security / SAST — Semgrep CE`, `security / IaC — Checkov`, `security / SCA — Trivy Filesystem`, `security / Container — Trivy Image`, `security / Secrets — Gitleaks`. A severity-cutoff knob on the list itself was considered and rejected: pip-audit's JSON carries no severity field at all, so no cutoff could apply uniformly across the five jobs it would have to gate. Requiring the six per-driver code-scanning checks in addition to the five job checks was considered and rejected: 17-05 observed the `Checkov` code-scanning check (app 57789) concluding `failure` on a PR that stayed mergeable and later merged, so requiring it would have blocked that PR on a check the job-level gate never asked it to satisfy.
- **A `pull_request` rule accompanies the required-status-checks rule**, because status checks alone do not require a pull request to exist before merging — extending ADR-002's mandate that branch protection have real enforcement authority, never editing ADR-002 itself.
- **Classic branch protection was considered and rejected for this repository as a mechanism, not merely undocumented**: the repository is governed by a ruleset, and the classic `branches/main/protection` endpoint 404s by design on a ruleset-governed repository — the 404 is a false negative, not evidence of anything, per the Phase 14 finding this decision inherits.
- **Ruleset changes are read-modify-write only, shipped as `scripts/set-required-checks.sh`, dry-run by default** — it reads the current ruleset document, merges in the five contexts, and only writes back the full document with `--apply`, so an update can never silently drop an unrelated rule, actor, or condition.
- **Correction to D-06: the required-check set is FIVE contexts, not the six D-06 originally stated, because the `security` caller job emits no check run of its own.** Three independent observations back this, cited by identifier so a reader can go and look: 14-02's live evidence, where a one-job callee produced exactly one check named `security / Placeholder` (`<caller-job-id> / <called-job-name>`), never a bare `security` check alongside it; this phase's research read of the Phase 17 head SHA `fbe0071d6934d19524f5bf9345e91396080fa882`, returning twelve check names, none of them bare `security`; and this phase's own run `34668611172` (18-04), whose scripted assertion recorded `bare_security: false` against the live check-run list. If the number six appears anywhere else in this project as the size of the required-check set, it is wrong.
- **Correction to D-07 step 1: "confirm the checks appear green when clean, red when seeded, while still in report-only" describes an unobservable state, because red-on-findings cannot occur in report-only by D-04's own definition** — `continue-on-error: true` on every gated step is precisely what keeps a job green regardless of findings. The corrected three-step ordering, as actually executed: step 1 (18-04) confirms the five checks appear and concludes green in report-only against seeded fixtures; step 2 (18-05) flips `GATE_MODE` to blocking on the identical tree and confirms the same five checks turn red; step 3 (18-05) flips back and confirms green returns. Red is observable only after the flip to blocking, never inside report-only.
- **This repository's own `main` was left `leave-unrequired`** (operator decision, 18-05 Task 3): the five contexts are proven required-check-ready by `scripts/set-required-checks.sh`'s dry run, but were deliberately not applied here. The measured reason is the hazard, not caution for its own sake — `fixtures/` makes every one of the five checks fire findings on every PR by construction, the live ruleset reports `bypass_actors: []` and `current_user_can_bypass: "never"`, and a ruleset does not auto-exempt repository admins. Applying the five contexts as required today, with `GATE_MODE` unset (report-only, all five green) that risk is currently zero — but the moment a future PR sets `GATE_MODE=blocking` without also relaxing the ruleset, `main` would lock against every PR including the one meant to revert it. CICD-04 is satisfied by the proven, dry-run-verified script and by this record; it does not require this repository to require the checks on itself.

## Consequences

**Improved:** measured on one pull request (PR #9, `OttawaCloudConsulting/security-platform`) across three commits (`31dbb0d`, `5973e8e`, `835c43e`) sharing one tree hash (`ce7ec652e09d07f9cee035410bbc05d47e0a79a8`) — one repository-variable flip, two verdicts, then a return to the first: all five `security / …` checks `success` under report-only (run `34668611172`), all five `failure` under blocking (run `34669534855`) on the byte-identical tree, then all five `success` again after the variable was deleted (run `34669700643`) — switched entirely by `gh variable set`/`gh variable delete`, with `git diff` between the first and last commits producing no output. Artifact count (5, same names) and code-scanning categories (6, same set) were unchanged between report-only and blocking, re-measured fresh under blocking rather than assumed from the report-only baseline.

**Tradeoff — blocking is severity-agnostic.** A low-severity finding blocks a merge exactly as a critical one does; there is no per-severity threshold in this design, because pip-audit's JSON carries no severity field at all and any threshold could not apply uniformly across the five jobs.

**Tradeoff — the flag is repository-wide, not scoped per branch or per PR.** `GATE_MODE` governs every run in the repository for as long as it is set; it cannot be varied per branch, per PR, or per actor. 18-05 kept its own blocking measurement window to roughly 2.5 minutes and confirmed no unrelated run executed inside it, but that discipline is operational, not structural — the workflow itself enforces no such scoping.

**Tradeoff — the `always() &&` guards changed report-only behaviour too, deliberately.** Before this phase, a scanner later in a job that ran after an earlier scanner in the same job had already produced a step failure would, under `continue-on-error`, sometimes be skipped by GitHub's default step-skip behaviour on a prior failure. The guard makes every gated scan step in a job run regardless of an earlier sibling step's outcome, in both modes — a behaviour change to report-only, accepted because leaving it inconsistent between modes would have meant blocking mode exercised different code paths than report-only ever tested.

**Tradeoff — the five job names and the caller's job id are now load-bearing configuration.** `security` (the caller job id) plus the five job names (`sast`, `iac`, `sca`, `container`, `secrets`, rendered as `security / SAST — Semgrep CE` and so on) compose the required-check-list strings. Renaming any one of them silently converts a required check from a real gate into a permanently-pending one — a future PR would never be mergeable, because the check name the ruleset expects would never be produced again.

**Tradeoff — an invalid gate mode fails fast and noisily.** Each job's enum-validation step runs before checkout, so a typo'd `GATE_MODE` value fails the job at its very first substantive step. The `always()`-guarded upload and verify steps still run afterward and fail on missing report files, adding noise to an already-failed job. This was chosen deliberately over a late failure discovered only after a scan had already run to completion.

## What was NOT verified

What WAS measured and must not be re-litigated: the five check-run names and `integration_id` 15368, read from `commits/{sha}/check-runs` on three separate occasions — 14-02's single-job placeholder check, this phase's research read of the Phase 17 head SHA `fbe0071d6934d19524f5bf9345e91396080fa882` (twelve names, none a bare `security`), and this phase's own run `34668611172` (18-04); the two live verdicts (`success` under report-only, `failure` under blocking) on one byte-identical tree; the artifact and code-scanning-category survival under blocking (5 artifacts, 6 categories, both re-measured rather than inherited); and the ruleset's pre-existing rule set on `main` (`deletion`, `non_fast_forward`), confirmed unchanged before, during, and after every measurement in this phase.

What remains open, in those words:

1. **Whether a fork PR can read repository `vars` at all is not verified**, and is deliberately routed to Phase 19 (VAL-01) rather than answered here. The consequence is stated plainly: a public repository running `GATE_MODE=blocking` via the repository variable could see a fork PR silently degrade to report-only while the five required checks still report green — the literal `with: gate_mode: blocking` form documented above exists specifically to give a public-repository operator a way to avoid depending on the answer.
2. **ADR-016's open question — whether a Dependabot-triggered run can obtain `security-events: write` — is not resolved by this phase either.** It was handed to Phase 18 explicitly and is handed onward unresolved.
3. **Whether `actions/upload-artifact` itself succeeds on fork and Dependabot runs remains an observation, not a measurement**, inherited from 17-04: it authenticates with `ACTIONS_RUNTIME_TOKEN`, not `GITHUB_TOKEN`, and no run measured in Phases 17 or 18 was a fork or Dependabot run.
4. **The exact `pull_request` rule parameter set GitHub requires on `PUT /repos/{o}/{r}/rulesets/{id}` has been exercised only against a local dry run**, not against a live write — the operator's `leave-unrequired` decision (18-05 Task 3) means `scripts/set-required-checks.sh --apply` has never been run against this repository's own ruleset.
